# 15. 거리를 제대로 재기

> 전체 목차는 [README.md](README.md) 를 본다.

"입력지점 1.00mm" 라고 적어 놓고 **실제로는 1.79mm 에서 눌리고 있었다.**

홀 출력은 거리에 대해 직선이 아닌데 직선으로 읽고 있었다. 이 편은 그것을 곡선으로
바꾸고 심으로 검증한 기록이다.

## 한 것

- 데이터시트 **두 점**으로 곡선을 계산해 스위치 표에 LUT 로 넣었다. 실측이 필요 없다
- 심 1·2·3mm 로 검증했다 — **직선이 틀린 양까지 예측대로** 나왔다
- 곡선 경로에서 나눗셈을 전부 걷어냈다 (역수 표)
- 래피드 트리거를 깊이 구역마다 다시 재단했다
- 데드존과 표시 스퀄치를 떼어 놓았다

```
설정      곡선 문턱   예전 직선    예전엔 실제로 여기서 눌렸다
0.50 mm      144        370          1.09 mm
1.00 mm      328        739          1.78 mm
2.00 mm      885       1478          2.66 mm
```

---

## ★ 자석은 거리의 세제곱으로 멀어진다

무압과 바닥, 두 점만 알고 그 사이를 곧게 이어 읽고 있었다. 그런데 자석이 멀어지면
자기장은 훨씬 빠르게 떨어진다. **어긋나는 곳이 하필 가운데**고, 거기가 사람이 실제로
쓰는 액추에이션 구간이다.

```
u = (읽은값 − 무압) / (바닥 − 무압)

  u  1 ┤                                    ╭─╯   ← 실제 (곡선)
       │                            ╭───╯
       │                  ╭────╯          ╱
       │        ╭────╯           ╱─╯
       │  ╭─╯          ╱──╯                       ← 우리가 쓰던 직선
     0 ┼──────────────────────────────────
       0        1        2        3      3.4 mm
```

같은 u 를 두 선에서 읽으면 가로로 벌어진다. **그 차이가 곧 오차**이고, GEON RAW HE
에서 최대 0.80mm 다.

## ★ 재지 않고 계산으로 얻는다

63키를 심 끼워 눌러 재야 할 것 같지만 아니다. 축방향 자화 원통 자석의 축상 자기장은
식이 알려져 있다.

```
B(z) = (Br/2) · [ (z+L)/√((z+L)²+R²) − z/√(z²+R²) ]
```

미지수가 둘(유효 갭 z0, 잔류자속 Br)이고, 제조사가 주는 두 점이면 식도 둘이다.

```
B(z0)          = 바닥 자속
B(z0 + travel) = 초기 자속
```

비를 취하면 Br 이 소거되어 z0 에 대한 1차원 근찾기가 된다.

★ **z0 하나만 맞추면 안 된다.** 처음에 그렇게 했다가 나머지 한 점이 30% 넘게
어긋났다. 비로 풀어야 둘을 동시에 만족한다.

★ **자석 형상은 몰라도 된다.** 양 끝점을 고정하고 나면 곡선 모양이 형상 가정에 거의
무관하다 — Ø4x2.0 과 Ø4x2.5 의 중간 구간 차이가 거리로 2um 다. 물리 형태가 이미
모양을 결정해 버린다.

## ★ 정규화하면 개체차가 사라진다

`u` 로 만들면 곡선 **모양**은 자석 세기와 센서 오프셋에 무관하다. 아핀 변환이
분자·분모에서 소거되기 때문이다.

그래서 **종류당 표 하나면 63키가 다 맞는다.** 키별로 필요한 두 점은 이미 갖고 있다 —
살아 있는 무압 기준값(base)과 보정에서 얻은 스트로크.

## ★ 거리를 균일 분할한다

u 를 균일 분할하면 곡선이 가파른 구간에서 해상도가 무너진다. **첫 칸 하나가 거리로
0.6mm 를 덮어 버린다.** 거리를 균일하게 잡고 u 를 저장해야 전 구간 해상도가 같다.

33칸, Q15. 데이터시트에서 계산되는 값이라 EEPROM 에 둘 이유가 없다.

```c
static const uint16_t curve_geon_raw_he[33] =
{
      0,   362,   743,  1144,  1565,  2010,  2478,  2973,
   ...
  32767,
};
```

곡률은 스위치마다 다르고, 정하는 것은 **자속의 비**다.

| 스위치 | 자속 비 | 행정 | 직선 오차 |
|---|---:|---:|---:|
| GEON RAW HE | 4.50 | 3.40mm | 0.80mm |
| Gateron Jade | 5.83 | 3.50mm | 0.95mm |
| Gateron Fox | 6.67 | 4.00mm | 1.18mm |
| Gateron KS-20 | 8.87 | 4.10mm | 1.37mm |

★ **모르는 스위치에는 곡선을 넣지 않는다.** 일반형(generic)은 직선으로 읽고 화면이
"직선으로 읽는 중" 이라고 말한다. 짐작한 값이 실측인 척하는 것이 제일 나쁘다.

---

## ★ 화면이 펌웨어보다 먼저다

펌웨어를 먼저 바꾸면 **모든 키의 감각이 한꺼번에 달라지는데 그게 맞는지 볼 방법이
없다.** 그래서 순서를 지켰다 — VIA HE 의 스위치 화면에 두 선을 같이 그리고, 누르면
지금 자리가 두 선 사이 어디인지 점으로 보이게 먼저 만들었다.

그 덕에 심 시험이 **곧바로 판정**이 됐다.

## ★ 검증 — 직선이 틀린 양까지 예측대로

버니어로 두께를 잰 심을 키캡 밑에 끼우고 끝까지 눌렀다.

**하나. 심 1·2·3mm 를 넣으면 눈금이 1mm 씩 따라왔다.**

```
실제가 곡선이면    간격 1.00mm
실제가 직선이면    간격 0.6~0.7mm     ← 3mm 심에서는 벌써 1mm 가까이 어긋난다
```

**둘. 곡선을 끄고(일반형 3.5mm 선택) 실제 2.00mm 를 눌렀다.**

```
읽힌 값              1.25 mm
곡선 모델의 예측     1.23 mm     ← 0.02mm 차이
실제가 직선이었다면  2.06 mm     ← 0.81mm 어긋난다
```

**두 번째가 결정적이다.** "곡선이 맞다" 가 아니라 **"직선이 틀린 양까지 예측대로"**
이기 때문이다. 모델이 곡선의 모양을 맞게 알고 있다는 뜻이다.

★ 덤으로 알아낸 것 — **키캡이 판에 닿기까지 여유가 0.4mm 쯤 있다.** 한 장짜리 절대
측정은 이 여유를 빼고 봐야 한다. 심을 두 장 쓰면 여유가 상쇄되어 이 함정을 피한다.

---

## ★ 뜨거운 자리는 뜻밖에 RGB 였다

역변환에 이진 탐색이 생겼다. 표시 경로라 한가한 줄 알았는데 **RGB 의 HE 효과가 매
프레임 65키의 깊이를 묻고 있었다.**

```
              스캔 한 바퀴   RGB 태스크 평균   125us 초과
직선 (R18)       28 us            21 us          590회
곡선 첫 판        28 us            34 us         1177회   ← 64비트 나눗셈
32비트로          28 us            29 us
역수 표           28 us            26 us
RGB 는 거리를 안 쓴다   28 us      25 us            0회   ← 곡선 전보다 좋다
```

**스캔은 처음부터 끝까지 28us 다.** 판정은 카운트 비교라 곡선이 안 탄다.

### 역수 표 — 나눗셈을 곱셈으로

나눌 값이 미리 정해져 있으면 역수를 한 번 만들어 두고 곱하면 된다. 곡선 칸 간격의
역수를 부팅 때, 키별 스트로크의 역수를 `keysThrRebuild` 에서 만든다. 스캔 경로에는
곱셈과 시프트만 남는다.

★ **상수로 박지 않는다.** 곡선에서 계산되는 값이라 손으로 적어 두면 곡선을 고칠 때
짝이 어긋난다. 32칸 나눗셈 몇 번은 부팅에서 보이지도 않는다.

### 그런데 제일 큰 답은 "그 자리에 거리가 필요 없다" 였다

효과가 원하는 것은 "반쯤 눌렸다" 뿐인데, 곡선을 태워 mm 로 바꾼 다음 다시 행정으로
나눠 0~255 로 되돌리고 있었다. `keysGetLevel8()` 로 센서 비율을 그대로 준다 — 탐색도
나눗셈도 없다.

**초과가 0 이 됐다.** 문제는 평균이 아니라 꼬리였고, 이진 탐색의 예측 안 되는 분기가
프레임을 가끔 길게 끌고 있었다.

---

## ★ 이동량은 위치가 아니다

절대 위치(입력·해제·데드존·바닥)는 곡선을 태우면 끝이다. 그런데 RT 의 두 값은
**이동량**이라 곡선에서는 같은 mm 라도 어디서 움직였느냐에 따라 카운트가 딴판이다.

RT 0.50mm 를 카운트 하나로 잡았을 때 실제 되돌림 거리 —

```
깊이 1.31mm    0.95mm     너무 둔하다
깊이 2.27mm    0.50mm     ← 설정대로인 곳은 여기 하나뿐
깊이 3.31mm    0.24mm     설정의 절반
```

**깊이 눌린 상태일수록 두 배로 예민해진다.** 타이핑에서 손가락이 머무는 곳이 거기다.

매 표본마다 역변환을 할 수는 없다 (35kHz × 64셀). 그래서 **미리 구워 둔다** — 정규화
값 u 의 상위 3비트로 여덟 구역을 잡고 구역마다 문턱을 만든다. 뜨거운 루프가 하는 일은
곱셈 하나와 시프트 하나다.

```
구역   기준점 깊이   문턱     실제 되돌림
  0     0.54mm      147      0.50 mm
  3     2.27mm      371      0.50 mm
  7     3.31mm      710      0.50 mm
```

★ **구역을 정하는 자리는 지금 깊이가 아니라 기준점(peak)이다.** 되돌림은 거기서
시작하는 이동이라 문턱도 그 자리의 기울기로 재야 맞다.

★ **바닥 구역은 뒤에서 재야 한다.** 그냥 더하면 행정을 넘어가 잘리는데, 그러면 문턱이
커지기는커녕 **작아져서**(481 → 160) 바닥에서 재입력이 제일 쉽게 걸린다 — 고치려던
것과 정반대다. `keys rt` 가 구역 여덟 개를 다 찍게 해 둔 덕에 눈으로 바로 보였다.

---

## ★ 이름표가 정직해지면 드러나는 것들

곡선을 넣으면 **같은 mm 가 카운트로 2.7배 작아진다.** 그래서 지금까지 가려져 있던
것들이 한꺼번에 나왔다.

### 얕은 입력지점

```
0.10mm ->  26 카운트   0.7x    잡음 p-p 40 보다 낮다
0.30mm ->  82          2.1x
0.50mm -> 144          3.6x
```

**노이즈가 나빠진 게 아니다.** 예전 "0.30mm" 는 실제로 0.72mm 였고 문턱이 222 였다.
같은 물리 지점의 여유는 하나도 안 변했다 — 0.72mm 는 지금도 222 다. 바뀐 것은
**사용자가 적은 숫자를 그대로 받게 됐다**는 점이고, 행정의 맨 위는 자석이 멀어 원래
신호가 약하다.

그래서 하한을 둔다. **근거는 실측 잡음이다** — p-p 40 의 1.5배인 60카운트(≈0.22mm)로
잡았다. RT 반응 행정의 하한과 같은 수다. 그보다 위는 사용자가 정할 몫이라 막지 않는다.

★ 하한을 **화면이 아니라 환산 지점에 둔다.** 값을 바꾸는 길이 여럿이라(VIA 채널·
키별 명령·CLI) 화면에서만 막으면 반드시 하나가 샌다.

### 잡음도 mm 로 봐야 한다

"가만히 뒀는데 화면에 0.1mm 가 뜬다" 를 쫓다가 두 가지를 놓치고 있었다.

★ **카운트로만 재고 있었다.** 곡선은 맨 위가 평평해서 같은 카운트 편차가 거기서는
거리로 여섯 배쯤 부풀려진다. "잡음 p-p 22 카운트" 는 작아 보이지만 화면에서는 0.10mm 다.

★ **3초 창을 여러 번 도는 것과 한 창을 길게 보는 것은 다르다.** 드물게 튀는 사건은
창마다 흩어져 어느 창에서도 최악값이 안 된다. `keys noise` 에 시간 인자를 넣었다.

60초, 175만 회 스캔으로 얻은 답 —

```
대부분 셀      0.02 ~ 0.06 mm
최악 한 셀     0.10 mm
```

곁가지로 하나 접었다 — **LED 전류는 ADC 에 안 실린다.** 밝기 상한을 3배로 올린 직후라
의심했는데 끄고/17/54/효과를 바꿔 가며 재도 p-p 41~42 로 같았다.

### 데드존과 표시 스퀄치는 다른 일이다

화면 떨림을 데드존으로 막았다가 되돌렸다.

```
데드존    눌림을 정할 때 무시할 구간.   사용자 취향이고 0 도 정답이다
스퀄치    화면 숫자가 안 떨게 하는 것.   잡음 바닥에서 나오는 값이다
```

묶어 뒀더니 데드존을 0 으로 내리면 화면이 다시 떨었다. 그러면 0 이 못 쓰는 값처럼
보이고, 그러니 기본값을 올리고 싶어진다 — **순서가 거꾸로다. 설정값이 화면 사정에
끌려다니면 안 된다.**

"기본값은 0.12 로 두고 UI 에는 0 으로 보이자" 는 길도 있었지만 안 갔다. 이 편에서
고친 것들이 정확히 그 부류다.

★ **자를 때도 자르지 말고 깨운다.** 데드존으로 그냥 잘랐더니 **처음 0.12mm 가 통째로
사라져** 키가 둔해진 것처럼 느껴진다는 말을 들었다. 판정 문턱은 그대로였지만(입력 83,
해제 23 카운트로 변화 없음) 보이는 쪽이 늦으면 사람은 늦다고 느낀다. 한 번 넘어서면
그 뒤로는 진짜 값을 주고, 쉬는 자리로 돌아오면 다시 잠근다.

### 데드존은 더하기가 아니라 밑바닥이다

```
입력 1.00 / 데드존 0.20   →  1.00mm 에서 눌린다   데드존이 한 일이 없다
입력 1.00 / 데드존 1.50   →  1.50mm 에서 눌린다   데드존이 입력지점을 덮어쓴다
```

더하기로 바꾸면 입력지점 숫자가 거짓이 되므로 그대로 두고, 대신 순서가 무너지지 않게
막았다 — `0 ≤ 데드존 ≤ 해제지점 < 입력지점`.

★ **잘렸으면 잘렸다고 말한다.** `keys rt` 가 `0.40 mm (23 카운트) <- 해제지점에서
잘림` 으로 찍는다. 조용히 자르면 "0.40 을 넣었는데 왜 그대로 동작하지" 를 못 푼다.

## ★ 곡선을 장치가 만든다 — 정수로

여기까지는 곡선을 `tools/he_magnet_fit.py` 가 오프라인에서 뽑아 소스에 상수로 붙였다.
커스텀 스위치(사용자가 정의하는 슬롯)를 넣으면서 **장치가 부팅 때 만들게** 했다.

담아 오는 것은 여전히 두 점뿐이다. 33칸 표(66바이트)를 올려받는 쪽도 만들어 봤지만
접었다 — 32바이트 리포트에 조각내야 하고, 받은 표가 단조인지·끝이 32767 인지 검사하는
코드가 솔버만큼 들고, 무엇보다 두 점과 표를 같이 담으면 **진실이 둘이 되어 조용히
갈라진다.**

### 부동소수를 안 쓴다

이 코어는 `rv32imac` — FPU 가 없다. 길이는 µm, `shape()` 은 Q24, 제곱근은 64비트 정수
뉴턴법이다. `z0` 는 이분법으로 푸는데, 나눗셈 없이 **교차곱 잔차의 부호만** 본다.

```
g(z) = shape(z) * rest − shape(z + T) * bottom
```

비를 직접 만들면 정밀도를 잃는다. 잔차는 int64 다 — `shape` 이 Q24 면 1.6e7 이고 자속이
2000 이면 3.3e10 으로 int32 를 넘는다.

### 여기서 두 번 넘어졌다

**단위가 섞였다.** 이 코드베이스의 `um` 은 실은 **0.01mm** 인데(340 = 3.40mm) 자석
치수는 진짜 µm 로 잡았다(2000 = 2.0mm). 그대로 더하니 3.40mm 를 0.34mm 로 읽었고, 두
점의 비가 모델이 낼 수 있는 범위를 벗어나 이분법이 근을 못 찾았다 — **곡선이 통째로
안 나왔다.**

**정수 제곱근의 내림 오차가 55배 증폭됐다.** `shape()` 이 거의 같은 두 값의 차라
(`axis(z+L) − axis(z)`, 둘 다 0.9 언저리) 상쇄가 크다. `isqrt` 의 상대 1e-4 짜리 내림이
곡선에서는 **0.47%(154/32767)** 가 됐다.

고침은 제곱근에 소수 8비트를 주는 것이다 — `sqrt(v << 16) = sqrt(v) << 8`.

| | shape 최대 상대오차 | 곡선 최대 차이 |
|---|---|---|
| 소수 0비트 | 1.77 % | 154 / 32767 |
| **소수 8비트** | **0.007 %** | **17 / 32767** |
| 소수 16비트 | 0.001 % | 17 / 32767 |

16비트까지 줘도 더 안 좋아진다 — 거기부터는 Q24 몫이다.

### 실측 — 앱과 1.76µm

`keys sw` 가 만들어진 33칸을 그대로 찍는다. 앱의 `heMakeCurve`(float) 출력과 대조하면 —

```
최대 차이 17 / 32767 = 0.05 %
거리로    1.76 µm      (잡음 바닥 100µm, 고치려는 오차 940µm)
```

★ **곡선을 눈으로 볼 수 있어야 한다.** 두 점에서 부팅 때 만드는 값이라, 틀려도 화면에서는
"거리가 좀 이상하다" 로만 나타난다. 33칸을 그대로 찍어 앱과 diff 하면 어느 쪽이 틀렸는지
한 번에 갈린다 — 위 버그 둘을 그걸로 잡았다.

## 배운 것

**하나. 화면을 먼저 만들면 실측이 곧바로 판정이 된다.** 두 값을 나란히 놓고 보는
화면이 없었으면 심을 끼워도 무엇과 비교할지 몰랐을 것이다.

**둘. "곡선이 맞다" 보다 "직선이 틀린 양까지 맞다" 가 훨씬 센 증거다.** 방향을 뒤집어
재면 모델이 모양을 아는지까지 확인된다.

**셋. 짐작하기 전에 붙어 본다.** 이 편에서 짐작이 틀린 것이 셋이다 — LED 전류가
잡음을 만들 것이다(아니었다), 밝기가 인코딩을 느리게 할 것이다(아니었다), 64비트
나눗셈이 RGB 비용의 전부일 것이다(절반이었다). 전부 재서 갈렸다.

**넷. 설정값과 화면과 판정, 셋이 같은 것을 말해야 한다.** 이 편의 버그는 대부분 그
셋이 갈라진 자리에서 나왔다.
