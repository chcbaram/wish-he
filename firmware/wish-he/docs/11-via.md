# 11. VIA 붙이기

> 전체 목차는 [README.md](README.md) 를 본다.

키맵·레이어·매크로는 10편에서 QMK 를 얹어 해결한다. 이 편은 그 위에 붙는 설정 채널
— **VIA 표준 명령과, HE 에만 있는 확장**이다.

처음 이 편을 쓸 때는 확장 쪽 절반만 있었다. 지금은 다 들어갔다.

## 명령 ID 를 먼저 옮겼다

처음에 잡은 `0x01 INFO` / `0x02 BOOT` / `0x03 RESET` 이 **VIA 와 정면으로 겹쳤다.**

```
0x01  id_get_protocol_version
0x02  id_get_keyboard_value
0x03  id_set_keyboard_value
```

QMK 의 `via.c` 를 얹는 순간 한 채널을 두 주인이 쓰게 된다. 도구와 펌웨어를 같이
고쳐야 하는 종류의 변경이라 **쓰는 사람이 우리뿐일 때** 옮겼다.

```
0x0B   부트로더 점프      VIA id_bootloader_jump 와 같은 자리
0xC0~  우리 확장          VIA 가 쓰지 않는 대역
0xC4   (장치 -> 호스트)   트래킹 프레임 태그
```

부트로더 점프를 VIA 자리에 맞춘 것은 덤이 있다 — **표준 VIA 도구로도 진입시킬 수
있다.** `via.c` 가 보기 전에 우리가 가로챈다.

우리 명령은 `hidCmdHandler()` 에서 먼저 걸러지고, 모르는 것은 `raw_hid_receive()` 로
넘어가 VIA 가 처리한다. 두 주인이 아니라 **문지기 하나에 방이 둘**이다.

## 기술자가 여섯으로 늘었다

```
IF0  HID 부트 키보드      IN 0x82   MPS 8    bInterval 1
IF1  HID NKRO + 시스템/컨슈머  IN 0x85   MPS 32   bInterval 1
IF2  raw HID (VIA 설정)   OUT 0x04 / IN 0x84   MPS 32   usage 0xFF60
IF3  HE 라이브 트래킹     IN 0x86   MPS 32   usage 0xFF61   ← IN 전용
IF4  CDC 통신 (IAD)       INT 0x83
IF5  CDC 데이터           OUT 0x01 / IN 0x81
```

번호는 `usb.c` 의 **등록 순서**가 정한다 (`hidKbdInit → hidExkInit → hidIfInit →
hidTrkInit → CDC`). 7편의 함정이 여기서도 산다 — 순서를 바꾸면 인터페이스 번호가
통째로 밀린다.

> ★ **MPS 32 는 못 늘린다.** VIA 규약이라 늘리면 호환이 깨진다. 이 32가 프레임에
> 담기는 개수를 전부 정한다 — 배치 4개, 트래킹 7키, 통계 7값, 보정 스트로크 14개.
> 나눗셈이 전부 `(32 - 헤더) / 항목크기` 다.

`HID_INTERVAL_HS` 만 4에서 1로 내렸다. 근거는 트래킹 스냅샷 주기다 — 64키를 7키씩
나누면 10프레임이고, 125us 폴링이면 한 장이 1.25ms 다.

## 스트리밍을 인터페이스로 갈랐다

처음에는 명령 응답과 트래킹 프레임이 EP `0x84` 하나를 나눠 썼다. 그러면 **표준 VIA
도구와 공존이 안 된다.**

VIA 는 "명령을 보내면 다음 IN 리포트가 그 응답"이라고 가정한다. 그 사이에 `0xC4`
프레임이 끼면 짝이 어긋난다. 우리 포크는 태그로 거르면 되지만, 표준 도구는 그럴 수
없다.

그래서 트래킹만 **IN 전용 인터페이스(IF3, usage `0xFF61`)** 로 뺐다. 이제 명령 채널에는
명령 응답만 흐른다.

가르고 나니 중재도 갈렸다.

| | 겹쳤을 때 |
|---|---|
| 명령 채널 (`hid_if.c`) | **미뤘다 보낸다** — `tx_pending` 에 세워 두고 IN 완료에서 흘린다. 50ms 넘게 막히면 복구한다 |
| 트래킹 채널 (`hid_trk_if.c`) | **버린다** — `if (is_tx_busy) return;` |

응답은 빠지면 도구가 멈추지만, 트래킹은 최신값이 중요하지 빠짐없이 가는 게 중요한
게 아니다. **같은 상황에 다르게 답하는 것이 맞다.**

리셋·연결 해제·재설정에서 `track_on` 을 강제로 내린다. 도구가 `0xC3 00` 을 안 보내고
사라져도 스트림이 남지 않는다.

## 확장 명령 한 상

응답은 **받은 것을 그대로 되돌려 놓고** 그 뒤에 값을 싣는다.

```
[0] 명령 에코   [1..] 인자 에코   [그 뒤] 값
```

상태 바이트를 따로 두지 않는다. VIA 의 `hidCommand` 가 **에코가 안 맞으면 거절**하므로
에코 자체가 검사다. 에코 길이를 하나 틀리면 도구가 "Receiving incorrect response" 로
멈춘다 — 실제로 키별 설정에 값 두 바이트를 늘리고 `HID_KEYCFG_LEN` 을 안 고쳐서 한 번
겪었다.

| ID | 무엇 | 요청 | 응답 |
|---|---|---|---|
| `0x0B` | 부트로더 점프 | — | 에코만. 50ms 뒤 실행 |
| `0xC0` | 보드 정보 | — | `[1..]` 보드 이름, `[16..]` 펌웨어 버전 |
| `0xC1` | 리셋 | — | 에코만. 50ms 뒤 실행 |
| `0xC2` | 물리 배치 | `[1]` 시작 | `[2]` 개수 `[3..]` 6바이트 x 개수 |
| `0xC3` | 트래킹 켜기/끄기 | `[1]` 0/1 | `[2]` 키 수 `[3]` 프레임당 `[4..5]` 전 행정 |
| `0xC5` | 키별 설정 | `[1]` 0=읽기 1=쓰기 `[2]` 인덱스 `[3..]` 값 | 읽기 19바이트 |
| `0xC6` | 스위치 종류표 | `[1]` 인덱스 | `[2]` 전체 `[3]` 일반형 수 `[4..5]` 행정 `[6..9]` 자속 두 점 `[10..]` 이름 |
| `0xC7` | 보정 | `[1]` 0상태 1시작 2저장 3취소 4스트로크 | 상태 + `[8..]` 완료 비트맵 |
| `0xC8` | 프로파일 | `[1]` 0상태 1선택 2복사 `[2]` 인덱스 | `[2]` 현재 `[3]` 개수 |
| `0xC9` | 진단 통계 | `[1]` 0읽기 1지우고읽기 `[2]` 페이지 | `[4..]` LE32 x 7 (14값, 2페이지) |
| `0xCA` | 하드웨어 제원 | `[1]` sub `[2]` 페이지 | 0~1 LE32 x 7, 2 MCU 이름, 3 만든이 |
| `0xCB` | 커스텀 스위치 슬롯 | `[1]` 0읽기 1쓰기 2상태 `[2]` 슬롯 | `[3..4]` 행정 `[5..8]` 자속 두 점 `[9]` kind `[10..]` 이름 |

`0xC4` 는 OUT 명령이 아니다 — 장치가 미는 트래킹 프레임의 태그다.

### 끝을 개수로 알린다

`0xC2` 는 전체 개수를 응답에 싣지 않는다. **끝을 넘겨 물으면 개수 0 이 온다** —
호스트는 0 이 올 때까지 인덱스를 늘리면 되고, 프로토콜에 길이 필드가 하나 줄어든다.

이걸로 웹 도구는 **JSON 파일 없이 장치만 보고** 배치를 그린다. 펌웨어의 레이아웃이
바뀌면 도구가 따라간다. 스위치 종류표(`0xC6`)도 같은 이유로 장치가 준다 — 설정에는
종류의 **인덱스**가 저장되므로, 표를 도구가 들고 있으면 펌웨어에서 항목 하나를 끼워
넣는 순간 모든 키의 mm 가 조용히 어긋난다.

### 키별 설정은 쓰기와 읽기 길이가 다르다

```
쓰기 14바이트   [0..1] 입력지점  [2..3] 해제지점  [4..5] RT 재입력  [6..7] RT 해제
                [8..9] 바닥구간  [10..11] 데드존  [12] RT 플래그    [13] 스위치 종류

읽기 19바이트   위 + [14..15] 행정 카운트  [16..17] 전 행정  [18] bit0 보정됨
```

`[13] 스위치 종류` 는 **비트 7 이 서면 커스텀 슬롯**이다 (`0x80 | 슬롯`). 내장 뒤에
번호를 이어 붙이면, 나중에 내장 표에 한 줄을 더하는 순간 구조체는 안 바뀌므로
**버전도 안 올라가고 기록도 유효한 채로** 모든 키의 스위치가 조용히 한 칸씩 밀린다.

뒤쪽 다섯 바이트는 **장치가 계산해 주는 읽기 전용**이다. 쓰기에 넣을 것이 아니다.

`인덱스 >= KEYS_MAX` 는 **전 키**를 뜻한다. 슬라이더를 끄는 동안 63키를 하나씩 쓰면
왕복이 63번인데, 이 규칙 하나로 한 번이 된다.

> ★ 새 항목은 **뒤에만** 붙인다. 32바이트에 여유가 있는 동안은 옛 펌웨어가 짧게 읽어도
> 앞쪽이 그대로라 살아 있다. 펌웨어도 짧게 온 요청은 있는 만큼만 처리한다.

### 커스텀 스위치는 두 점만 오간다

내장 표에 없는 스위치를 사용자가 정의한다. 슬롯 넷이고, 담는 것은 **이름 + 전 행정 +
데이터시트 두 점**이 전부다 (18바이트, 한 프레임).

33칸 곡선은 **장치가 부팅 때 만든다.** 두 점이면 곡선이 결정되기 때문이다 — 축상
자기장 식의 미지수가 둘인데 두 점의 비를 잡으면 자석 세기가 약분되어 하나만 남는다.

★ **표를 올려받는 쪽도 만들어 봤지만 접었다.** 66바이트라 32바이트 리포트에 조각내
보내야 하고, 받은 표가 단조인지·끝이 32767 인지 검사하는 코드가 솔버만큼 든다.
무엇보다 두 점과 표를 같이 담으면 **진실이 둘이 되어 조용히 갈라진다.**

★ "FPU 가 없어 소프트플롯이 딸려온다" 는 이유로 처음엔 올리는 쪽으로 잡았다가
뒤집었다. **사실이 아니었다** — 배정밀도 루틴이 `strtod` 경유로 이미 링크돼 있었고,
정수 isqrt 를 쓰니 libm 도 안 붙는다.

자속이 0 이면 곡선 없이 그 행정의 **직선**으로 읽는다. "행정은 아는데 데이터시트가
없다" 가 실제로 있고, 그게 없어진 `GENERIC` 이 하던 일이다.

심 실측으로 곡선을 재는 길은 나중에 얹는다. `kind` 바이트와 528바이트(33칸 x 2B x
8슬롯)를 예약해 뒀으니 버전을 안 올리고 들어간다. 두 점(제조사가 말한 것)과 표(내가
잰 것)는 파생 관계가 아니라 **독립된 출처**라 둘 다 두고 `kind` 로 고른다 — 차이
자체가 정보다.

## VIA 표준과 커스텀 채널

`quantum/via.c` 와 `dynamic_keymap.c` 를 그대로 얹었다. 프로토콜 `0x000C`.

```
VIA_ENABLE  RAW_ENABLE  DYNAMIC_KEYMAP_ENABLE
레이어 8   매트릭스 8x8   매크로 16개
```

커스텀 메뉴는 채널 넷을 쓴다.

| 채널 | 무엇 | 값 |
|---|---|---|
| 3 | 조명 (QMK 표준) | 밝기·효과·속도·색 |
| 14 | QMK 키 처리 | `hold_okp` |
| 15 | NKRO | 켬/끔 |
| 16 | **HE 설정** | 아래 |

```
1 입력지점   2 해제지점   3 스위치 종류   4 RT 재입력   5 RT 해제
6 바닥구간   7 데드존     8 RT 플래그
```

9번(일반형 전 행정)은 **비워 두고 다시 쓰지 않는다.** 그 일은 커스텀 슬롯이 맡는다.
번호를 재사용하면 옛 앱이 9번을 물었을 때 엉뚱한 값을 받는다 — 안 받는 편이 낫다.

16비트 값은 **빅엔디안**이다 (VIA 규약). 우리 확장 명령(`0xC5`)은 리틀엔디안이라
**같은 값이 채널에 따라 바이트 순서가 다르다** — 도구 쪽에서 자주 헷갈리는 자리다.

### 채널 16 은 JSON 에 없다

`layout-via.json` 의 `menus` 에는 조명 탭과 QMK 탭만 있다. HE 탭은 **정의 파일에 안
넣었다** — 키를 골라 값을 주는 화면이라 VIA 의 선언형 메뉴로는 안 그려진다. 포크한
웹앱이 채널 16 을 직접 몬다.

`"keycodes": ["qmk_rgb_matrix_keycodes"]` 를 빠뜨리면 **키맵 탭에서 조명 키코드가
통째로 사라진다.** 메뉴가 아니라 키코드 목록이라 다른 자리에서 티가 난다.

`customKeycodes` 여섯 개(`PF1`~`PF4`, `PF>`, `PF<`)는 펌웨어의 `QK_KB_0` 부터의 순서와
**정확히 맞아야 한다.** 순서가 곧 값이다.

### 저장은 채널마다 주인이 다르다

`id_custom_save` 가 오면 HE 채널은 `keysSave()` 를 부른다. HE 설정은 QMK EEPROM 이
아니라 `keys.c` 의 제 기록에 살기 때문이다. 조명·QMK 는 QMK 가 알아서 한다.

> ★ `via_custom_value_command_kb()` 안에서 `raw_hid_send()` 를 부르면 안 된다.
> 응답은 `via.c` 가 받은 버퍼 그대로 되돌린다 — getter 는 그 버퍼에 값을 **덮어쓰기만**
> 한다.

## EEPROM 백엔드 — RAM 그림자 + 미룬 굽기

SDK 의 `eeprom_emulation` 을 쓰지 않았다. 16KB 를 통째로 RAM 에 들고, 더러워진
**섹터 하나씩** 나중에 굽는다.

```c
static uint8_t eeprom_buf[16384];       /* 부팅 때 한 번 읽는다 */

eeprom_write_byte()  ->  dirty_mask |= 1 << (i / 4096);   /* 표시만 */
eeprom_task()        ->  200ms 조용하면 더러운 섹터 하나를 굽는다
```

읽기는 플래시를 아예 안 본다. 쓰기도 그 자리에서는 표시만 한다.

★ **한 번에 한 섹터만 굽는다.** XIP 라 플래시를 지우는 동안 인터럽트를 막아야 하는데,
4KB 하나면 그 창이 짧다. 네 섹터를 한꺼번에 지우면 그동안 USB 리포트가 빠진다 —
12편에서 실제로 잰 문제다.

```
0x000000 ~ 0x020000   부트로더 (건들지 않는다)
0x020000 ~ 0x080000   앱 384KB
0x080000 ~ 0x0C0000   ★ 기존 데이터 영역 — 절대 쓰지 않는다
0x0C0000 / 0x0C1000   보정값 A/B (핑퐁, 4KB)
0x0C4000 ~ 0x0C8000   QMK EEPROM 16KB (4섹터)
0x0C8000 / 0x0CA000   HE 설정 A/B (핑퐁, 8KB)
0x0CC000 ~ 0x100000   빈 곳 208KB
```

> ★ 그 영역을 지키는 것은 **규율뿐이다.** `flashWrite()`/`flashErase()` 에는 주소
> 검사가 없다. CLI 의 `flash erase` 만 `0x0C0000` 아래를 막는다. 새 저장 자리를 만들 때
> 반드시 `HW_FLASH_USER_BEGIN` 위에서 잡을 것.

QMK EEPROM 16KB 의 속:

```
   0 ~   37   EECONFIG_BASE (매직·디버그·기본 레이어·조명 8B)
  37 ~  549   사용자 데이터 512B  — 조명 프로파일 4칸(+0) · hold_okp(+32)
 549 ~  553   VIA 매직 + 레이아웃 옵션
 553 ~ 4649   키맵 1024B x 4 프로파일
4649 ~ 16384  매크로 11735B (프로파일 공유)
```

## 기록은 셋이고, 버전도 셋이다

| 기록 | 무엇 | 자리 | 버전 |
|---|---|---|---|
| `keys_cal_t` | 이 개체를 잰 값 (키별 두 점) | `0x0C0000` / `0x0C1000` | 7 |
| `keys_set_t` | 취향 (프로파일 네 벌) | `0x0C8000` / `0x0CA000` | 8 |
| `keys_sw_t` | 커스텀 스위치 정의 | `0x0CC000` / `0x0CD000` | 1 |

★ **수명이 다르면 기록을 나눈다.** 보정은 이 개체를 잰 값이라 절대 나누면 안 되고,
스위치 정의는 데이터시트 값이라 **나누라고 있는 것**이다. 설정은 프로파일마다 한 벌인데
스위치 정의는 보드에 한 벌이다. 한 기록에 섞으면 앞으로 스위치 정의를 고칠 때마다
보정(63키 누르기)이 같이 날아간다.

★ **버전도 기록마다 갖는다.** 예전에는 `keysBlobValid` 가 `KEYS_CFG_VERSION` 하나를
셋에 같이 썼다. 그러면 보정 구조를 한 번 고치려고 올릴 때 설정도 통째로 무효가 된다 —
고칠 이유가 없는 것까지 버리는 셈이다.

실제로 값을 했다. `GENERIC` 을 표에서 빼면서 내장 번호가 한 칸씩 밀려 **설정은 버려야
했는데**(안 버리면 사용자가 배정해 둔 스위치가 조용히 옆 것으로 바뀐다), 보정은 그대로
지켰다.

> ★ 옛 판을 옮겨 심는 마이그레이터는 없앴다. 사용자가 "기존 데이터는 지워져도 된다,
> 호환 때문에 지저분한 것보다 낫다" 고 정했다. 대신 위 구조 덕에 **앞으로는 덜 버린다.**

## 프로파일은 둘이 나란히 돈다

같은 인덱스를 쓰지만 사는 곳이 다르다.

| | HE 설정 | 키맵 · 조명 |
|---|---|---|
| 어디 | `keys.c` 의 제 기록 (플래시 핑퐁) | QMK EEPROM |
| 크기 | 프로파일당 1580B, 전체 6340B | 키맵 1024B + 조명 8B |
| 자리 | `0x0C8000` / `0x0CA000` | EEPROM 553 / 37 |
| 바뀔 때 | `keysProfSelect()` | `keymapProfileOffset()` 이 주소를 접는다 |

★ **보정값은 프로파일을 안 따른다.** 보정은 이 보드의 실측이고 설정은 취향이다.
입력지점을 만질 때마다 보정 섹터를 다시 굽는 것도 낭비다.

★ **매크로도 공유다.** 글자 대신 치는 것이라 프로파일마다 다를 이유가 없다. NKRO 도
공유다 — 장치의 성질이지 취향이 아니다.

프로파일 전환은 USB ISR 에서 올 수 있다. 그래서 플래시를 만지는 일은 전부 미룬다 —
`keysProfTouch()` 로 표시하고 메인 루프가 굽는다. 조명 다시 읽기도
`rgb_reload_req` 로 미룬다.

## 웹앱 포크

VIA 앱을 포크해 **HE 탭**을 붙였다 (별도 저장소). 표준 VIA 로는 못 하는 것이 있어서다
— 키를 골라 값을 주는 화면, 라이브 깊이, 보정, 펌웨어 굽기.

```
홀이펙트   입력 지점 · 래피드 트리거 · 데드존
교정       바닥값 수집
스위치     종류 선택 · 전 행정 · ADC↔거리 그림
장치       펌웨어 · 프로파일 · 백업 · 진단 · 정보
```

**설정은 고른 키에만 간다.** 아무것도 안 고르면 값 컨트롤이 꺼진다 — 예전에는 빈
선택을 "전부"로 읽었는데, 실수로 63키를 한꺼번에 바꿔 놓기 쉬웠고 되돌릴 수도 없었다.
전 키에 쓰려면 "모두 선택"을 명시해야 하고, 그때는 브로드캐스트 한 번으로 나간다.

포크가 얹은 것 중 프로토콜과 얽힌 것:

| 무엇 | 어떻게 |
|---|---|
| 브라우저에서 펌웨어 굽기 | `0x0B` 로 IAP 진입 → VID/PID 가 바뀌어 다시 열거되면 4KB 페이지로 쓴다. 굽는 중에 `requestDevice()` 를 절대 안 부른다 |
| 장치가 주는 배치·스위치표 | `0xC2` / `0xC6` — 정의 파일이 없거나 낡아도 맞는다 |
| 키보드 통째 백업 | 프로파일을 돌며 키별 설정·키맵·조명을 담고, 매크로와 QMK 설정을 따로 담는다. **보정값은 뺀다** — 보드마다 다르다 |
| 라이브 깊이 | `0xFF61` 을 따로 연다. 프레임에 첫 키 인덱스가 있어 몇 개 빠져도 제자리에 들어간다 |
| 한 줄로 세운 HID | 앱 전체가 약속 하나에 왕복을 잇는다. VIA 자신의 키맵 읽기와 엇갈리면 서로 물린다 |

★ 응답 에코 검사는 **포크가 만든 것이 아니라 VIA 것**이다. 확장 프로토콜이 에코를
싣는 이유가 이것이다.

## 실측 — 상한이 7편과 같은 자리였다

```
$ python3 tools/he_track.py --rate
키 64개, 프레임당 7키, 배치 63자리, 전 행정 4.00mm
스냅샷 1724장 / 3.0s = 574/s
```

이론값 800 에 못 미친다. 그런데 프레임 수로 환산하면 답이 나온다.

```
574 스냅샷/s x 10프레임 = 5740 프레임/s
7편에서 잰 연속 전송 상한          5900/s
```

**같은 천장이다.** 파이썬도 대역폭도 아니고, 7편에서 확인한 완료 → 재프라임 왕복이
정하는 값이다. dTD 체이닝으로 이 상한을 올리면 **키보드 리포트와 트래킹이 같이
빨라진다** — 아직 안 했다. 지금 574장/s 로 부족한 자리가 없다.

### ★ 사용자 영역은 손으로 더하지 않는다

`hold_okp` 를 `+0`, 조명 프로파일 칸을 `+p*8` 로 잡았더니 0번 프로파일이 `hold_okp` 와
**같은 바이트**에 앉았다. 조명 첫 바이트가 `enable:2 | mode:6` 이라 양쪽으로 깨졌다.

| | 무슨 일이 났나 |
|---|---|
| 프로파일을 바꾸면 | `profRgbStore(0)` 이 그 바이트에 `enable\|mode` 를 쓴다. 다음 부팅에 `hold_okp` 가 그 값을 읽고 `> 1` 이라 **1 로 잘린다** — 꺼 뒀어도 켜져서 돌아온다 |
| 탭홀드를 토글하면 | 0 이나 1 이 앉아 0번 프로파일의 조명 **켬/모드가 날아간다** |

`_Static_assert` 는 총량(32 ≤ 512)만 봤다. 512 안에서 둘이 같은 자리에 앉은 것은
검사 대상이 아니었다.

**구조체로 선언해서 고쳤다.** 자리를 컴파일러가 잡으면 겹칠 수가 없다.

```c
typedef struct PACKED
{
  rgb_config_t rgb[KEYMAP_PROFILE_COUNT];   /* +0   8B x 4 */
  uint8_t      hold_okp;                    /* +32         */
} ee_user_t;

#define EE_USER(field)  ((void *)(EECONFIG_USER_DATABLOCK + offsetof(ee_user_t, field)))
```

★ **조명 칸이 맨 앞을 지킨다** — `_Static_assert` 로 못 박았다. 이미 쓰고 있는 보드가
있어서, 조명을 밀면 네 칸이 한 칸씩 어긋나 1번 조명이 0번에 나타난다. 옮기는 것은
`hold_okp` 하나다 — 업데이트하면 **한 번 다시 정해 주면 되는** 불리언이다.

새 항목은 이 구조체에 필드로 더한다.

### 실측 — 고치기 전후

같은 보드에서 같은 순서로 돌렸다. 0번 프로파일 조명을 6번 효과로 두고, 1번으로
나갔다가(여기서 칸에 제대로 저장된다) `hold_okp` 를 토글하고, 0번으로 돌아와 효과를
읽는다.

```
V260816R38   0번 효과 = 0    ← 6 이어야 하는데 hold_okp 가 덮었다
V260817R39   0번 효과 = 6    ← 그대로
```

★ **1번으로 나가는 단계를 빼면 재현이 안 된다.** 0번에서 바로 나가면
`profRgbStore(0)` 이 RAM 의 성한 값으로 덮어써서 깨진 것이 도로 고쳐진다. 저장이
끝난 뒤에 건드려야 드러난다.

반대 방향(`hold_okp` 가 조명에 덮이는 쪽)은 `hold_okp` 를 부팅 때 한 번만 읽으므로
리셋을 거쳐야 보인다. 1 로 두고 프로파일을 두 번 옮긴 뒤 리셋해도 1 이다.

한 가지 예상이 빗나갔다 — 새 자리가 지운 상태(`0xFF` → 1 로 잘림)일 줄 알았는데
시험한 보드는 **0** 이었다. 업데이트하고 나니 탭홀드가 꺼진 채로 올라왔다.
