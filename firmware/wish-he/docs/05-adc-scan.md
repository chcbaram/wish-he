# 5. 센서가 내는 값 들여다보기

> 전체 목차는 [README.md](README.md) 를 본다.

키를 눌렸다/말았다로 판정하기 전에, **센서가 실제로 어떤 숫자를 내는지부터** 본다.
핀맵과 ADC 배정은 [00-hardware.md](00-hardware.md) 4절에 있다.

## 한 것

- ADC0/ADC1 시퀀스 모드 + 내장 DMA, 각 4채널 = 동시 8채널
- `PY00~PY03` MUX 주소를 그레이 코드로 8스텝
- CLI `keys dump` / `keys raw` / `keys time` / `keys adc`

```
cli# keys dump
       ch0  ch1  ch2  ch3  ch4  ch5  ch6  ch7
  s0   42280 44741 42964 43579 43536 43809 45003 45823
  s1   42827 44741 42690 45763 45140 43604 43055 43262
  ...
  s7   44741 42964 43715 44741 44456 45243 42918 44593
  scan : 52 us
```

## 스캔 한 바퀴 38us — 8kHz 예산의 30%

```
cli# keys time
scan   : 25796 회 / 초
주기   : 38 us
8kHz 예산 125us 대비 : 30 %
timeout: 0
```

**이 숫자가 이후 설계를 상당히 단순하게 만든다.** 64키 전체를 38us 에 읽으므로
8kHz(125us)를 맞추는 데 타이머 트리거도, HDMA 도, 정교한 파이프라이닝도 필요 없다.
스캔을 그냥 자유 구동으로 돌리고 USB 완료 콜백에서 최신값을 실어보내면 된다
(12편에서 그렇게 간다).

시퀀스 DMA 는 **HDMA 채널을 쓰지 않는다.** ADC 가 자체 AHB 라이터로 직접 메모리에
쓰므로 `hw_def.h` 의 채널 배분과 무관하다. 계획 단계에서 `HW_DMA_CH_ADC` 를 잡아두려
했는데 필요가 없었다.

## 스캔 구조

```c
for (step = 0; step < 8; step++)
{
  gpio_write_port(HPM_GPIO0, GPIO_DO_GPIOY, mux_addr[step]);   /* 주소 */
  keysSettle();                                                /* 16 사이클 = 40ns */

  adc0_done = adc1_done = false;
  adc16_trigger_seq_by_sw(HPM_ADC0);
  adc16_trigger_seq_by_sw(HPM_ADC1);
  keysWaitDone();                                              /* ISR 플래그 스핀 */

  gpio_write_port(HPM_GPIO0, GPIO_DO_GPIOY, mux_addr[step + 1]);  /* ★ 다음 주소 먼저 */
  /* 그 다음에 결과를 읽는다 — 다음 스텝의 세틀링이 이 처리와 겹친다 */
}
```

마지막 두 줄의 순서가 핵심이다. 그래서 주소 테이블에 되돌이용 원소가 하나 더 붙는다.

```c
static const uint8_t mux_addr[8 + 1] = { 6, 7, 5, 4, 0, 1, 3, 2,  6 };
```

## 겪은 함정

### ① `SEQ_INT_EN` 은 시퀀스가 아니라 **큐 원소별** 비트다

완료 인터럽트가 영영 오지 않아 스캔이 통째로 타임아웃했다.

```
cli# keys time
scan   : 174 회 / 초
주기   : 5747 us
timeout: 174        <- 174번 스캔해서 174번 다 타임아웃
```

`adc16_seq_config_t.queue[i].seq_int_en` 을 "시퀀스 완료 인터럽트를 쓸 것인가"로 읽고
전부 `false` 로 뒀는데, 실제로는 **"이 큐 원소가 끝나면 알려라"** 다. 하나도 안 켜면
`INT_STS` 의 `SEQ_CMPT` 가 서지 않는다.

```c
/* 마지막 원소에만 켠다 — 시퀀스 끝에 한 번만 받는다 */
seq_cfg.queue[i].seq_int_en = (i == (KEYS_SEQ_LEN - 1));
```

### ② `CONT_EN` 은 "연속 반복"이 아니라 "큐 끝까지 진행"이다

①을 고쳤는데도 타임아웃이 그대로였다. 진단 명령을 넣어 보니 **변환이 딱 하나만**
일어나고 멈춰 있었다.

```
cli# keys adc
ADC0
  트리거 후 INT_STS : 0x00000000 (spin 200000)
  ISR done flag     : 0
  DMA 버퍼          : 0x82F0A4E6 0xDEADBEEF 0xDEADBEEF 0xDEADBEEF
                       ^^^^^^^^^^ 첫 채널만 쓰였다
```

레지스터 설명이 답이었다.

> **CONT_EN** — *if set, HW will continue process the queue **till end(seq_len)** after trigger once*
> **RESTART_EN** — *if set **together with cont_en**, HW will continue process the whole queue after trigger once*

이름 때문에 `CONT_EN` 을 "끝나면 계속 반복"으로 읽고 껐는데, 그러면 **트리거 1회에
변환 1개**만 하고 선다. 반복은 `RESTART_EN` 쪽이다.

```c
seq_cfg.cont_en    = true;    /* 한 번 트리거 -> 큐 끝까지 */
seq_cfg.restart_en = false;   /* 끝나면 멈춘다 */
```

고친 뒤:

```
  트리거 후 INT_STS : 0x01000000 (spin 8)
  ISR done flag     : 1
  DMA 버퍼          : 0x82F0A528 0x86E1AEC5 0x8AC2A818 0x8E83AAA2
```

패킹된 워드를 풀어보면 `adc_ch` 가 15, 14, 12, 8 로 등록 순서 그대로고 `seq_num` 도
0,1,2,3 이다.

### ③ ADC 채널 번호는 패드 번호와 다르다

`PB00~PB07 → ch8~ch15`, `PB08~PB15 → ch0~ch7` 로 8만큼 돌아가 있다. 그래서 이 보드가
쓰는 8개는 오름차순도 아니고 `PB03` 을 건너뛴다.

```c
static const uint8_t adc0_seq_ch[4] = { 15, 14, 12,  8 };  /* PB07 PB06 PB04 PB00 */
static const uint8_t adc1_seq_ch[4] = {  0, 13,  9, 10 };  /* PB08 PB05 PB01 PB02 */
```

### ④ `PY` 패드는 IOC 만으로 연결되지 않는다

`IOC` 를 ALT0(GPIO)으로 잡아도 패드가 SoC 에 붙지 않는다. **`PIOC` 도 ALT3 으로** 함께
넘겨야 한다.

```c
HPM_IOC->PAD[IOC_PAD_PY00 + i].FUNC_CTL  = IOC_PY00_FUNC_CTL_GPIO_Y_00;
HPM_PIOC->PAD[IOC_PAD_PY00 + i].FUNC_CTL = IOC_PAD_FUNC_CTL_ALT_SELECT_SET(3);
```

## 스캔 구조와 예산 배분

10편에서 QMK 를 얹은 뒤 스캔이 느려져서 경로를 끝까지 다시 짚었다.

### 한 스텝이 하는 일

```
MUX 주소 쓰기  →  세틀링  →  ADC0/1 트리거  →  완료 대기
              →  다음 MUX 미리 걸기  →  DMA 버퍼 8개 읽기  →  판정
```

"다음 MUX 를 결과 읽기 **전에** 미리 건다"가 핵심이다. 다음 스텝의 세틀링이 이번
스텝의 결과 처리와 겹쳐서 공짜가 된다. 그래서 주소 표에 되돌이용 원소가 하나 더 붙는다.

```
MUX 순서    06 07 05 04 00 01 03 02 06     9번째는 0번 스텝 주소와 같아야 한다
ADC0 시퀀스 0F 0E 0C 08
ADC1 시퀀스 00 0D 09 0A
```

MUX 순서는 **그레이 코드**다 — 스텝당 주소선이 한 비트만 바뀌어 인접 채널 크로스토크가
줄어든다. 세틀링은 16 사이클(400MHz 에서 40ns)이고, 스캔은 타이머가 아니라 슈퍼루프에서
**자유 구동**한다.

### ADC 완료를 폴링으로 받는다

인터럽트로 받으면 스캔 한 바퀴에 **ISR 이 16번**(ADC 2개 x 8스텝) 든다. 하는 일이
플래그 하나 세우는 것뿐인데 초당 24만 번이다 — 7편에서 같은 이유로 걷어냈다.
상태 레지스터를 직접 보면 0번이다.

### 남는 속도를 어디에 쓰나

스캔이 빨라지면 그 여유를 **레이트**에 쓸 수도 있고 **잡음**에 쓸 수도 있다. 둘은
맞바꾸는 관계다.

|  | 레이트에 쓰면 | 잡음에 쓰면 |
|---|---|---|
| 유효 키 레이트 | 30 kHz | 13.4 kHz (3개 누적) |
| 표본 하나의 잡음 | 그대로 | 이론상 √3 = 1.73배 감소 |

25us 간격으로 3개를 더하면 센서 상관시간(10.6us)의 2.4배라 무상관이 성립한다.
버스트 오버샘플링(간격 320ns, ρ≈0.97)과 달리 이건 진짜로 평균이 된다.

처음에는 레이트를 골라 잡음은 데드밴드로 눌렀고, 13편에서 **3개 이동합**을 넣어
둘을 같이 가져갔다 — 블록이 아니라 이동합이라 판정 횟수를 잃지 않는다.

### 눈금은 절대값이 아니다

```
                        우리(누적 3개)
  안 눌림 raw          7474 ~ 8383
  전 스트로크          2514 (61키 평균)
```

이 숫자들은 **이 보드의 아날로그 경로에서 나온 값**이고 다른 장비의 눈금과 맞을 이유가
없다. 판정은 키별 러닝 최대 기준값과의 **차이**로만 하고, mm 환산은 `keys cal` 로 잰
키별 실측 스트로크를 쓴다.

> ★ 그런데 여기서 크게 한 번 틀렸다.
>
> 스위치 전 행정을 기본값 **4.0mm** 로 놓고 분석을 두 번 쌓았는데, 실제로 꽂힌 것은
> **3.4mm** 스위치였다. 화면에 키를 끝까지 눌렀을 때 **3.385mm** 로 찍힌 것이 처음부터
> 답이었다 — 4.0mm 스위치를 3.385mm 까지 눌렀다고 읽는 대신, 3.4mm 스위치를 끝까지
> 눌렀다고 읽었어야 했다. 전제를 고치니 카운트/mm 가 22% 달라졌다.
>
> **판정에는 영향이 없었지만 mm 표시가 전부 18% 어긋나 있었다.** 자세한 것은 13편.

### 잡음 바닥은 어디인가 — LED 부하를 흔들어 봤다

누적을 넣고도 이론(1.73배)에 못 미친 1.31배가 걸렸다. 연속 스캔 사이 상관계수가
0.45 인데 센서 상관시간 10.6us 에 스캔 간격 28us 면 0.07 이어야 한다. 그 차이가
**펌웨어가 만드는 것**인지 하드웨어 바닥인지 갈라야 해서, 가장 유력한 용의자인 LED
전류부터 흔들어 봤다.

```
  LED 꺼짐              p-p 평균 39
  LED 백색 3% (~156mA)  p-p 평균 39
  LED 백색 6% (~312mA)  p-p 평균 39
```

**꿈쩍하지 않는다. 전원 결합이 아니다.**

그러면 남는 설명은 하나다 — 홀 센서의 **1/f 플리커 잡음**이다. 백색 성분은 28us 간격
평균으로 지워지지만 1/f 는 상관시간이 길어 3샘플(84us) 창으로는 안 지워진다. 관측된
상관계수와 맞는다.

**지금 p-p 39 가 이 하드웨어의 바닥이다.**
누적을 늘려도 비례해서 좋아지지 않는 이유이기도 하다. 더 내리려면 센서 내부의 초핑
기법이라야 하는데 우리가 손댈 수 있는 영역이 아니다.

> ★ 곁가지로 하나 나왔다 — **LED 전류 상한이 펌웨어에 없다.**
>   83개를 25% 백색으로 켜면 83 x 3 x 20mA x 0.25 = 1.25A 로 USB 예산(500mA)의
>   두 배가 넘어 보드가 브라운아웃되고 USB 가 끊긴다. 시험 중에 실제로 겪었다.
>   RGB 를 실제로 쓰기 전에 전역 전류 상한을 넣어야 한다.

### 그래서 어디를 고칠 것인가

처음에는 구조 탓으로 봤다. **스텝 안에서 생값만 누적하면 될 것을** 우리는
`keysFilter` 8번에 `keysTrack` 까지 스텝 안에서 하니 두 배 걸리는 게 당연해 보였다.

재보니 구조가 아니었다.

```
스캔 1회 (8 step x 8 ch)      -O0        -O2
  mux + 세틀링              5.998 us   1.262 us
  + ADC 변환 대기          23.732     19.528     (하드웨어 변환 시간)*
  + 데드밴드 필터          13.915      2.619
  + 기준값 추적·판정       18.395      5.067
  ─────────────────────────────────────────────
  합계                     62.040     28.476
```

> \* 이 표는 DMA 도착을 기다리기 **전에** 잰 것이다. 아래 "최종 분해"가 실제 값이다.

이식 중 추적이 쉽게 하려고 둔 `-O0` 였다. USB 폴링만 보고 "최적화는 무관하다"고
결론냈던 게 잘못이었다 — 폴링은 USB 하드웨어가 정하고, 스캔은 코어가 정한다.

**두 번째는 명령어 캐시였다.** `-O2` 로도 문맥에 따라 값이 갈렸다.

```
                                  측정 루프   메인 루프
  keysUpdate() 반복만                29 us       —
  qmkUpdate() · usbUpdate() 와 섞임    —        63 us
```

사이에 낀 코드가 XIP 플래시 캐시에서 스캔 코드를 밀어내, 매 스캔이 플래시에서 다시
읽혔다. 스캔 경로(`keysUpdate` · `keysTrack`)를 `ATTR_RAMFUNC` 로 ILM 에 올렸다.
128KB 중 1KB 도 안 쓰고 있던 자리다.

```
  메인 루프 스캔    62 us  ->  33 us      (유효 30 kHz)
  라이브 트래킹    241/s  ->  620/s
  keyboard_task    8 us  ->   2 us (평균)
```

> 한동안 31us 로 적어 두었는데 그건 **DMA 도착을 기다리지 않던 상태**의 숫자다.
> 같은 일을 하지 않았으니 비교 대상이 아니다. 제대로 기다리면 33us 다.

최종 분해는 이렇다.

```
  mux + 세틀링          1.29 us
  ADC 변환 + DMA 도착  23.72        ← 여기가 바닥이다
  데드밴드 필터         2.69
  기준값 추적·판정      4.77
  ─────────────────────────
                       32.5 us
```

**23.7us 는 ADC 하드웨어 시간이라 스텝 루프를 어떻게 짜도 줄지 않는다.**
`adc_clk_div` 와 `sample_cycle` 을 건드리면 줄지만 그 둘은 잡음과 맞바꾸는 값이라
함부로 줄이지 않는다 — 나중에 실제로 재 보고 정한다.

남은 여지는 **겹치기**뿐이다. 지금은 23.7us 를 아무것도 안 하고 기다린 뒤 7.5us 를
처리하는데, 스텝 N 이 변환되는 동안 스텝 N-1 을 처리하면 그 7.5us 가 통째로 숨는다.

```
  지금    [설정][변환 2.96us 대기][처리 0.93us]  x 8   = 33 us
  겹치면  [설정][변환 2.96us | 그 안에서 N-1 처리]  x 8 = 26 us 대
```

DMA 버퍼가 다음 스텝에 덮어써지므로 값을 한 번 복사해야 한다 (8워드, 약 50ns).
잡음도 ADC 설정도 건드리지 않는다.

```
13편  남는 여유로 3개 누적한다
      -> 잡음을 낮추면서 레이트도 지키는 상태가 된다
```

래피드 트리거는 0.1mm 를 다룬다. 우리 스트로크가 평균 836 카운트니 0.1mm 가 21
카운트다 — **잡음을 √3 줄이는 것이 그 눈금에서 의미가 있다.**

> 드리프트 보정도 손볼 데가 있다. 지금은 512ms 마다 전 키를 한 번에 처리해서 **그
> 스캔만 무거워진다** — 주기가 흔들린다. 메인 루프 틱마다 키 하나씩 64개를 돌아가며
> 처리하면 고르게 퍼진다. 13편에서 판정이 주기에 민감해지기 전에 나눠 두는 게 낫다.
