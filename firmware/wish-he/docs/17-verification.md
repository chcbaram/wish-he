# 17. 손 없이 시험한다 — 값 주입과 누적 검증

첫 배포가 끝났는데 **키 동작·래피드 트리거·USB 에 숨은 버그가 있는지 확인한 적이
없었다.** 기능을 넣는 데 시간을 다 썼기 때문이다.

- 회귀 검사가 성능 비교뿐이었다 — 그것은 **"느려졌나" 만 본다**
- ADC 값을 갈아 끼워 **실제 키를 안 누르고** 스캔 뒤 전부를 시험한다
- 잡은 것 셋. 그중 둘은 **손으로는 만들 수 없는 조건**이었다
- 재현 절차를 코드로 굳혀 누적한다 — 고친 것이 다시 깨지면 잡히도록

---

## 왜 성능 지표로는 안 보이나

굽기 전후로 `qmk info` / `keys time` 을 재는 규율이 있었다. 태스크가 느려졌는지,
스캔이 예산을 넘는지는 그걸로 잡힌다.

**그런데 오입력과 키씹힘은 느려지지 않는다.** 이번에 잡은 셋 중 어느 것도 태스크
시간에 한 글자도 안 나타났다. 기준값이 잘못 움직이는 것은 산술 몇 줄이라 공짜다.

```
증상                                 성능 지표
키를 문 채로 있는데 저절로 떼진다      아무 변화 없음
기준값이 갇혀 키가 영영 눌린 채다      아무 변화 없음
손을 다 떼도 안 떨어진다               아무 변화 없음
```

---

## 값 주입 — 자리를 고르는 일이 절반이다

스캔 루프가 DMA 결과를 `snap[]` 으로 뜬 **직후**에 갈아 끼운다.

```c
for (uint32_t i = 0; i < KEYS_SEQ_LEN; i++)
{
  snap[i]                = adc0_buf[i];
  snap[KEYS_SEQ_LEN + i] = adc1_buf[i];
}

/* 주입 중인 셀만 갈아 끼운다 — 스텝당 분기 하나다 */
if (inject_mask[step]) keysInject(step, snap);
```

`keysFilter` 가 `(packed & 0xFFFF) >> KEYS_RAW_SHIFT` 로 12비트를 뽑으므로 값을
그만큼 왼쪽으로 밀어 넣는다. 그래야 **데드밴드와 누적을 실제와 같은 눈금으로 지난다.**

이 자리를 고르면 뒤가 전부 시험 범위가 된다:

```
데드밴드 필터 → 3탭 누적 → 드리프트·래치 → 스퀄치·데드존 → RT 상태기계
→ pressed[] → matrix → QMK(키맵·레이어·탭홀드) → SOCD·연타 → HID 리포트 → USB
```

못 지나는 것은 그 앞뿐이다 — MUX, ADC 설정, DMA 자체, 아날로그 잡음, 실제 자석.

### ★ 셀 단위 마스크로 한다 — 전체 덮기가 아니라

처음에는 "주입 켜면 전부 덮는다" 로 생각했다. **그러면 시험 중에 키보드가 통째로
죽는다.** CLI 의 탈출 조합(Ctrl+Esc)은 `pressed[]` 를 직접 읽는데, 전부 덮으면
그것도 안 먹는다. USB 를 뽑는 수밖에 없어진다.

마스크가 안 선 셀은 실물 값이 그대로 살아 있게 둔다. 한 키만 주입하고 나머지로
빠져나올 수 있다.

### ★ ADC 는 계속 돌린다

DMA 를 멈추고 값을 넣는 쪽이 간단해 보인다. 그런데 그러면 **스캔 시간이 달라져
시험의 뜻이 바뀐다.** 타이밍은 평소 그대로 두고 결과만 덮어야 "평소와 같은 조건"
에서 잰 것이 된다.

### ★ 리포트는 기본으로 막는다

주입한 키는 진짜 키와 구별이 안 되므로 그대로 호스트로 나간다. 시험을 걸어 놓고
손을 떼면 **그 키가 무한히 눌린 채 터미널에 쏟아진다.** 명령을 더 칠 수도 없다.

그래서 판정까지만 보는 것이 기본이고, 호스트까지 보내는 종단간 시험은
`keys inject live on` 으로 명시할 때만 한다.

### 값이 공짜인가

```
                 넣기 전        넣은 뒤
keys time track   +13.066 us    +12.59 ~ 13.28 us   (여러 번 재서 범위)
keysUpdate          27 us         26 us
```

스텝당 분기 하나(스캔당 8회)라 재도 안 보인다.

## 잡음 주입 — 균등 분포로는 시험이 안 된다

고정값 위에 잡음을 얹으면 드문 사건의 빈도를 잴 수 있다. 그런데 분포를 잘못 고르면
**아무리 오래 돌려도 0 이 나와서 "안 일어난다" 는 잘못된 결론**에 이른다.

```
균등 분포  p-p 밖으로 절대 안 나간다
           실측 p-p(40)로 두면 래치 문턱(93)에 영원히 안 닿는다
꼬리 있음  균등 셋을 더한다 — 종 모양이 되고 드문 큰 이탈이 난다
           표준편차를 균등과 맞추려 1/√3 배 (정수라 4/7 로 대신)
           최대 이탈이 균등의 1.7배까지 뻗는다 — 거기가 시험하려는 자리다
```

`xorshift32` 하나면 되고, 주입 중인 셀만 도므로 몇 셀이면 공짜다.

### ★ 실물 잡음은 백색이 아니다 — 외삽의 한계

이 저장소가 이미 실측해 둔 것이 있다. 누적을 3 → 6 → 12 로 늘려도 잡음이
**N^-0.2** 로만 준다 (백색이면 N^-0.5). 표본끼리 강하게 상관돼 있다는 뜻이다.

주입 잡음은 독립 난수라 백색이다. **꼬리 모양이 실물과 다를 수 있으므로 가속
외삽을 그대로 믿으면 안 된다.** 실물 장시간 측정이 여전히 필요하다.

## 잡은 것

### ① 눌린 키의 기준값이 따라 내려온다 — 저절로 떼진다

`keys inject` 로 재니 이렇게 나왔다. 입력지점 0.30mm, **주입값은 한 번도 안 바꿨다.**

```
깊이 116 → 104 → 92 → 83 → 71 → 59 → 47 → 35 → 26 → 14
     [눌림] ..................................... [눌림]  → 해제
약 18초.  3카운트/512ms = 5.9카운트/초
```

손가락은 그대로인데 키가 떨어진다.

**원인 — 설계 전제가 곡선을 넣으면서 깨져 있었다.** 하향 드리프트는 깊이로만 걸렀다.

```c
if (do_drift && d > KEYS_DRIFT_STEP && d < KEYS_DRIFT_BAND)   /* 밴드 = 150 */
```

주석에 근거가 적혀 있었다 — *"밴드는 노이즈(약 120)와 액추에이션(4000) 사이여야
한다."* 그 숫자들이 **곡선 도입 전** 것이다. 지금은 실측 스트로크 2525 로 환산하면

```
입력지점 0.10mm =  26      0.30mm =  83      0.50mm = 145   ← 전부 밴드 150 안
입력지점 0.75mm = 231      1.00mm = 330                     ← 밖
```

즉 **밴드가 입력 문턱보다 크다.** 게임용으로 흔한 얕은 설정이 정확히 그 구간이다.

**고친 방법 — 깊이가 아니라 판정 결과로 거른다.**

```c
if (do_drift && d > KEYS_DRIFT_STEP && d < KEYS_DRIFT_BAND
    && (pressed[step] & bit) == 0)          /* 이 한 줄 */
```

기준값은 "안 눌린 상태의 값" 이므로 눌려 있는 동안 움직일 이유가 애초에 없다.
**상수끼리 크기를 맞춰 둘 필요가 사라져 사용자가 문턱을 어디에 두든 안전하다.**

★ 밴드를 줄이는 쪽은 답이 아니다. 입력지점은 0.10mm(26카운트)까지 내려갈 수 있는데
  잡음 밴드는 그보다 넓어야 한다. **두 조건을 동시에 못 만족한다.**

### ② 상향 글리치 한 방에 기준값이 영구히 갇힌다 (미해결)

`v - base > KEYS_LATCH_JUMP(93)` 이면 기준값이 즉시 끌려 올라간다. 그 뒤
`d >= KEYS_DRIFT_BAND(150)` 이면 하향 보정이 **아예 안 돈다.**

**손으로는 만들 수 없는 조건이라 주입이 아니면 못 잡았다.**

```
1) 정상값 주입                  깊이 2 카운트,  latch 0
2) +100/표본 글리치 (2초)        latch 1 로 증가
3) 정상값으로 되돌림             깊이 276 카운트
4) 10초간 다섯 번 읽음           276, 276, 276, 276, 276  ← 1도 안 움직인다
```

잡음 주입으로 더 밀어 보니 기준값이 **7470 → 8071 로 +601 갇혔고**, 깊이 598 이
입력지점 334 를 넘어 그 키가 눌린 것으로 보고됐다. 주입을 꺼서 실물 ADC 로 돌아와도
그대로였다. **재보정만이 복구했다.**

**래치율은 잡음이 아니라 드리프트에 묶여 있다.**

| 잡음 p-p | 40 | 60 | 80 | 100 | 140 | 200 |
|---|---|---|---|---|---|---|
| 래치/30초 | 0 | 1 | 1 | 1 | **0** | **0** |

가운데가 평평한 이유 — 래치 뒤 기준값이 5.9카운트/초로 내려와야 다음이 가능하다.
상한이 **16초에 한 번**이라 잡음을 키워도 안 늘어난다.

★ **끝의 0 이 더 중요하다.** 잡음이 크면 기준값이 잡음 천장 **위로** 올라가 갇히고
  그 뒤로는 래치가 멎는다. **래치 0 이 안전하다는 뜻이 아니라 이미 굳었다는 뜻이다.**

아직 안 고쳤다. 문턱 셋(밴드 150 / 래치 93 / 드리프트 3)이 서로 묶여 있어, 실물
장시간 측정으로 실제 빈도를 알기 전에는 어디로 옮길지 근거가 없다.

★ 그리고 잡음이 아니어도 난다 — **기구 변형**(핫스왑 재장착, 플레이트 휨, 키캡
  측압)은 93 을 쉽게 넘고, 그쪽이 실제 원인일 가능성이 더 크다.

### ③ 해제지점 0 을 웹앱 경로가 허용했다 — 손을 다 떼도 안 떨어진다

전역 setter(`keysSetReleaseUm`)는 0 을 막고 있었다. **웹앱이 쓰는 키별 명령(0xC5)만
안 막혀 있었다.** 게다가 `press_um` 이 0 이면 순서 보정까지 건너뛰어져 그대로 남는다.

```
0xC5 로 press_um = 0, release_um = 0 을 쏘면
  → 입력지점 60 (하한으로 올라감), 해제지점 0

주입으로 눌렀다 떼니
  누름: 깊이 591  [눌림]
  뗌  : 깊이 12   [눌림]   ← 0.05mm 인데 안 떨어진다
```

판정에서 `d` 는 0 미만으로 안 내려간다. 그래서 절대 해제인 `d < t->release` 는
`t->release` 가 0 이면 `0 < 0` 이라 **영원히 거짓이다.**

**고친 방법 — 0 은 값이 아니라 "안 보냈다" 로 본다.**

```c
if (keysGet16(&p_buf[0]) > 0) k->press_um   = keysClampUm(keysGet16(&p_buf[0]));
if (keysGet16(&p_buf[2]) > 0) k->release_um = keysClampUm(keysGet16(&p_buf[2]));
```

같은 파일의 `sw_type` 이 이미 그 방식이다(유효할 때만 쓴다). 결을 따랐다.

★ **처음에 표를 만드는 쪽에서 `t->release == 0` 이면 1 로 올리게 고쳤는데 모자랐다.**
  `release = 1` 이면 `d < 1` 즉 깊이가 정확히 0 일 때만 떨어진다. 데드밴드 때문에
  실제로는 깊이가 12~14 에서 멎으므로 여전히 안 떨어졌다. **시험이 바로 잡아냈다** —
  고쳤다고 생각한 것이 안 고쳐졌다는 것을 그 자리에서 알았다.

### ④ 프로파일을 바꾸면 눌려 있던 키가 호스트에 영원히 남는다

**보는 자리를 못 찾아서 한동안 못 잡았다.** `qmk log` 는 부트 키보드(IF0) 섀도를
읽는데, NKRO 가 켜져 있으면 QMK 가 6KRO 를 아예 안 보내서 **IF0 이 죽어 있다.**
실측으로 `KBD sent 1` vs `EXK nkro sent 6440` — 화면만 보면 아무 일도 없어 보인다.

`qmk held` 를 만들었다. NKRO 칸의 마지막 내용을 그대로 찍는다 — **호스트가 지금
눌린 것으로 아는 키**다.

```
1) 프로파일 1 에서 X 를 누름        호스트: 0x1B (X)
2) 누른 채로 프로파일 2 로 전환      호스트: 0x1B (X)
3) 손을 뗀다                        호스트: 0x1B (X)   ← 여전히 눌린 채
```

**원인** — QMK 는 뗄 때 키코드를 (레이어, 행, 열)로 **다시 읽는다.** 누를 때 캐시해
두는 것은 레이어 번호뿐이다. 그런데 프로파일마다 키맵이 따로라 같은 자리가 새
프로파일에서는 다른 키코드다. 위 시험에서 프로파일 2 의 그 자리는 Z 였고, **해제는
Z 로 나갔다.** X 는 아무도 안 뗐다.

**고친 방법 — 바꾸기 전에 비운다.**

```c
void keysProfChanged_kb(uint8_t idx)
{
  if (idx == 0xFF)          /* 아직 옛 프로파일이다 */
  {
    clear_keyboard();       /* 해제가 옛 키맵으로 제대로 나간다 */
```

★ **바꾼 뒤에 비우면 이미 늦다.** 그때는 키코드가 벌써 새 것이다. 훅이 전·후로
  나뉘어 있는 것이 다행이었다.

★ 덤으로 SOCD·연타의 눌림 기억(`userLoad` 가 지운다)과도 앞뒤가 맞는다. 한쪽만
  지우면 "물리적으로 누르고 있는데 호스트에는 없는" 상태가 된다.

### ⑤ SOCD 를 끄면 억눌러 둔 키가 영영 안 살아난다

억제는 리포트를 **한 번 고치는 일**이다(`del_key`). 되살리는 것은 상대 키를 뗄
때뿐인데, SOCD 를 끄면서 눌림 기억을 지워 버리면 그 조건이 영영 거짓이 된다.

```
1) X 를 누름                   호스트: X
2) W 도 누름 (SOCD 억제)        호스트: W          (X 억눌림 — 여기까지 정상)
3) SOCD 를 끈다                 호스트: W
4) W 만 뗀다 (X 는 계속 누름)   호스트: 없음       ← X 가 안 살아난다
```

원래 주석은 반대 방향을 걱정하고 있었다 — *"끄는 순간 눌려 있던 키가 남으면
곤란하다."* 실제로 곤란한 것은 **남는 쪽이 아니라 사라지는 쪽**이었다.

**고친 방법 — 끌 때 지금 눌려 있는 것을 전부 다시 넣는다.**

```c
if (was_on && socd[pair].enable == 0)
{
  for (i = 0; i < 2; i++)
    if (socd_down[pair][i] && socd[pair].keycode[i] != KC_NO)
      add_key(socd[pair].keycode[i]);
  send_keyboard_report();
}
```

꺼진 뒤에는 두 키가 다 눌려 있는 것이 맞는 상태다. 이미 들어 있는 키에 `add_key`
를 해도 무해하다.

★ **프로파일 전환 경로는 ④ 의 `clear_keyboard()` 로 같이 맞았다.** 양쪽(호스트
  리포트와 눌림 기억)이 함께 비워지므로 어긋날 자리가 없다. **한쪽만 지우는 것이
  버그였다.**

### ⑥ 해제지점을 올리면 래피드 트리거가 조용히 죽는다

`rt_arm` 은 "이번 스트로크에서 RT 가 걸려 있다" 는 표시다. 그것을 푸는 조건이
이랬다 —

```c
/* 입력지점 아래로 완전히 돌아왔으면 RT 를 푼다. */
if (!rt_cont && d < (int32_t)t->release) rt_arm[step] &= ~bit;
```

**주석은 "입력지점", 코드는 해제지점이다.** RT 해제가 난 자리가 해제지점보다
얕으면 같은 스캔에 RT 가 풀리고, 그 뒤로는 절대 입력지점까지 눌러야만 다시 산다.

같은 깊이(281)에서 설정 하나로 갈린다:

```
입력지점 1.00mm, RT 재입력 0.10mm / 입력해제 0.20mm

  해제지점 0.50mm (기본)   ->  눌림    RT 재입력 정상
  해제지점 0.80mm (올림)   ->  떼짐    RT 가 죽었다
```

★ **기본값이 아슬아슬하게 살아 있었다.** `1.00 − 0.50 == 0.50` 이고 비교가 `<` 라
  간신히 통과한다. 해제지점을 조금만 올리면 넘어간다. 사용자 눈에는 "가끔 리셋이
  안 먹는다" 로만 보인다.

**고친 방법 — 원위치 판정에 사용자 설정을 안 쓴다.**

```c
if (!rt_cont && d < (int32_t)squelch_cnt[idx]) rt_arm[step] &= ~bit;
```

스퀄치 문턱은 실측 잡음 바닥에서 나온 상수(0.12mm)라 **입력지점·해제지점을 어디에
두든 뜻이 안 변한다.** 사용자 설정을 원위치 판정에 끌어들인 것이 이 버그의 뿌리였다.

★ **그냥 지우면 안 된다.** 데드존 가지(`d < dead`)가 이미 있지만 데드존 기본값이
  0 이라 실질적으로 안 걸린다. 그러면 `rt_arm` 이 영영 안 풀려, 쉬는 상태에서
  살짝만 눌러도 RT 가 절대 입력지점을 건너뛴다. **그 쪽을 시험 항목으로 따로 뒀다** —
  0.80mm 까지 눌러도 안 눌리는 것을 확인한다.

### ⑦ 설정 도구로 RT 를 켜면 그 자리에서 키가 떨어진다

`peak` 은 설정과 짝을 이루는 값이다. 설정이 바뀌면 그 전에 쌓인 `peak` 은 뜻이 없다.
전역 setter(`keysSetRtFlags`)는 그것을 다시 잡는데 **웹앱이 쓰는 키별 명령(0xC5)만
빠져 있었다.**

```
1) RT 끔.  2.00mm 로 깊게 누름      [눌림]   peak = 889 로 남는다
2) 1.05mm 까지 올림 (입력지점 위)   [눌림]
3) 웹앱 경로로 RT 를 켠다            떼짐    ← 손은 그대로인데 떨어진다
```

`peak - d = 889 - 369 = 520` 이 이미 RT 해제 문턱을 넘어 있어, 켜는 순간 판정이
"방금 520 카운트 올렸다" 로 보인다.

★ **같은 조작이 CLI 로는 멀쩡하고 웹앱으로는 키를 떨어뜨렸다.** 두 길의 동작이
  다른 것 자체가 버그의 증거였다 — 조사에서 그 비대칭을 먼저 발견하고, 그 다음에
  증상을 재현했다.

**고친 방법 — 두 길이 같은 헬퍼를 부른다.**

```c
static void keysRtReseed(void)   /* 지금 깊이로 다시 잡는다 */
```

★ **0 으로 미는 것이 아니다.** 원래 `keysSetRtFlags` 는 `peak = 0` 으로 밀었는데,
  떼진 상태의 키는 해제 국면이 최솟값 추적이라 **0 에 머문다.** 연속 RT 가 켜져
  있으면 `rt_arm` 과 무관하게 RT 가 살아 있으므로, 쉬는 자리에서 반응 행정만큼만
  눌러도 절대 입력지점을 건너뛴다. 지금 깊이로 다시 잡으면 그 구멍이 없다 —
  **고치면서 옛 경로의 구멍도 같이 막혔다.**

### ⑧ 한 키만 눌러도 연타가 걸린다

연타는 "기본 키 두 개 이상을 지연시간만큼 쥐고 있으면" 시작한다. 그 개수를
`process_record` 훅에서 **사건으로 세고 있었다** — 누름 +1, 놓음 −1.

그 앞에 게이트가 셋 있었다.

```c
if (ghost.enable == 0)          return;
if (socdIsUsed(keycode))        return;
if (!IS_BASIC_KEYCODE(keycode)) return;
```

**누름과 놓음 사이에 그중 하나라도 바뀌면 짝이 영영 깨진다.**

```
1) F13 + F14 를 쥔다                연타 돈다 (86 개/1.5초)
2) 쥔 채로 F13 을 SOCD 묶음에 넣는다
3) 둘 다 뗀다                       조용하다 (0 개) — 겉보기 정상
4) ★ 한 키만 누른다                 연타가 돈다 (98 개/2초)
```

3번에서 `socdIsUsed(F13)` 이 참이라 `−1` 이 건너뛰어졌다. `key_cnt` 가 1 남고
`running` 은 `key_cnt == 0` 에서만 꺼지므로 영영 안 꺼진다. 그 뒤로는 키 하나가
2 를 만든다.

★ 게이트를 하나씩 고치는 것으로는 안 끝난다. **탭홀드의 합성 릴리즈**(누른 적 없는
  놓음 사건)와 **프로파일 전환**(같은 자리가 다른 키코드가 된다)도 같은 짝을 깬다.

**고친 방법 — 리포트에서 센다.**

```c
static uint8_t ghostHeldCount(void)   /* 지금 리포트에 든 기본 키 수 */
```

**지금 호스트가 눌린 것으로 아는 것**이 곧 답이고, 거기엔 짝이라는 개념이 없다.
게이트 셋과 `ghostProcess` 훅이 통째로 사라졌다 — 고치면서 코드가 줄었다.

★ SOCD 와 다툴 일도 없다. `ghostBeat` 은 지금 리포트를 그대로 되돌려 놓을 뿐 키를
  지어내지 않는다 — SOCD 가 뺀 키는 애초에 리포트에 없다. 원래 게이트가 막으려던
  것이 실제로는 일어날 수 없는 일이었다.

### ★ 시험 키는 무해한 자리로 바꿔 둔다

연타는 리포트를 **실제로 호스트에 쏜다.** 평소 키코드 그대로 시험하면 화면에 글자가
쏟아진다. F13~F24 로 잠시 바꿔 두고 끝나면 되돌린다.

### ★ RT 시험은 구역 문턱을 넘겨야 한다

여기서 세 번 헛짚었다. RT 문턱은 깊이 구역(8칸)마다 다르고 **구역 한가운데** 값으로
굽는다. 그래서 얕은 쪽에서는 같은 mm 가 카운트로 덜 나온다 — 0.20mm 를 움직였는데
그 구역의 문턱(0.20mm 어치)에 못 미쳐 아무 일도 안 일어난다.

```
peak 344 에서 0.20mm 올림 = 87 카운트,  그 구역의 문턱 = 104 카운트  ->  안 난다
```

**시험에서는 폭을 넉넉히 잡는다.** 그리고 이 양자화 오차 자체가 실사용에서 얼마나
느껴지는지는 아직 안 쟀다.

### ★ 매트릭스와 호스트는 다른 것을 본다

이번에 배운 것이다. `keys show` 는 **장치가 보는 것**이고 `qmk held` 는 **호스트가
보는 것**이다. 둘이 갈리는 자리가 곧 버그다 — 손을 다 뗐는데 호스트에는 남아 있는
상태는 매트릭스만 봐서는 절대 안 보인다.

```
  단계    항목                                          결과
```

### ★ 아직 안 고친 것은 xfail 로 둔다

**늘 빨간 검사는 아무도 안 본다.** 알려진 문제는 "알려진 대로 재현됨" 이 통과이고,
**재현이 안 되면 그때 알려 준다** — 고쳐졌거나 조건이 바뀐 것이니 둘 다 봐야 한다.

곡선 대조 도구(`he_curve_check.py`)에서 같은 판단을 했다. 종료 코드를 가르는 것은
회귀 감지기 하나뿐이고 나머지는 참고 출력이다.

### ★ 초과 **횟수**로는 성능을 판정하지 않는다

처음에 "125us 초과 50회 미만" 으로 뒀더니 늘 빨간불이었다. 플래시 쓰기는 XIP 라
인터럽트를 막아야 하고 그동안 태스크가 멎는데, **시험 자체가 설정을 쓰므로 그
초과를 스스로 만들어 낸다.** 평균과 최대를 본다 — 평균이 늘면 진짜 회귀다.

### ★ 상태를 반드시 되돌린다. 그리고 **순서**가 있다

시험이 입력지점을 바꾸므로 끝나면 원래대로 놓는다. 안 그러면 사용자가 쓰던 설정이
조용히 바뀐 채 남아, 다음에 칠 때 감이 달라져도 원인을 못 짚는다.

**되돌리는 순서를 틀려서 실제로 사고를 냈다.**

```
틀린 순서    주입 끄기  →  설정 되돌리기
             그 사이 몇 초 동안 해제지점 0 인 채로 리포트가 살아난다
             스턱 키가 호스트로 새어 나갔다

맞는 순서    설정 되돌리기  →  주입 끄기
             주입 중에는 keysIsReportEnabled() 가 막아 준다
```

그래서 마지막에 **"눌린 키가 없다"** 를 확인하는 항목을 따로 뒀다. 아무도 안 치는데
리포트가 늘면 뭔가 남은 것이다.

### ★ 그런데 "리포트가 안 나간다" 로는 모자랐다

래치 시험은 **일부러 기준값을 갇히게 만든다.** 그것을 안 되돌려서 X 키가 **0.9mm
눌린 채로** 남았다. 그런데 위의 확인 항목은 통과했다 — 갇힌 양(295 카운트)이
입력지점(334)을 안 넘어 **리포트는 조용했기 때문이다.** 화면에만 눌린 것으로 보인다.

두 가지를 더했다.

- **래치 시험이 스스로 재보정한다.** 회복 수단이 재보정뿐인 것이 이 버그의 성질이다
- **기준값과 실제 값을 직접 견주는 항목**을 뒀다. `keys key` 의 기준값과 `keys dump`
  의 실제 값이 아무도 안 누를 때 잡음 폭 안에서 붙어 있어야 한다

★ **"증상이 안 보인다" 와 "정상이다" 는 다르다.** 리포트만 보면 둘을 못 가른다.

## 겪은 함정

### macOS 는 키보드 HID 를 root 로도 안 열어 준다

호스트에서 리포트를 직접 세어 유실을 재려 했다. `0xE00002E2 not permitted` 가 나고,
입력 모니터링 권한을 줘도 `0xE00002C1 privilege violation` 이 났다. **`sudo` 로도
똑같이 막혔다.**

권한 문제가 아니다 — **키보드 usage 를 여는 것이 곧 키로거**라 OS 가 그렇게 다룬다.
같은 조건에서 벤더 채널(`0xFF60`·`0xFF61`)은 그냥 열린다.

```
if 0  키보드      : 실패 — open failed
if 1  키보드      : 실패 — open failed
if 2  벤더 0xFF60 : 열림
if 3  벤더 0xFF61 : 열림 — 32B 수신
```

그래서 "호스트가 실제로 받았나" 는 **장치가 정해진 패턴을 스스로 쳐 넣고 받은 글자를
비교하는** 길로 간다. 권한이 필요 없고 실제 경로를 그대로 지난다.
(`tools/hid_probe.py` 가 이 판정을 다시 해 준다.)

### 오래 도는 CLI 명령은 기다려 줘야 한다

`keys noise 10000` 은 장치가 10초 동안 잰다. `dev.py` 가 기본 1.2초만 기다려서
출력이 잘린 채 돌아왔고, **아무것도 안 나온 것처럼 보여 명령이 실패한 줄 알았다.**
`-w` 를 붙였다.

## 아직 안 한 것

- **A2 의 실제 빈도** — 굽지 않고 아무도 안 치는 상태로 오래 둬야 한다. 굽는 순간
  카운터가 리셋되므로 검증 작업과 같이 못 한다
- **`ramp`** — 시간에 따라 값을 바꾸는 궤적. RT 상태기계(재입력이 몇 번 사는지)를
  시험하려면 필요하다
- **DMA 타임아웃 강제 실패** — 주입으로는 못 만든다. 별도 플래그가 필요하다
- **종단간 자가 타건** — 장치가 정해진 패턴을 치고 호스트가 받은 글자를 비교
