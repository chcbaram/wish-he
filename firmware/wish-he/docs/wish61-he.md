# wish61-he — 이어받기

61키 HE 보드(HPM5361). **벤더 IAP 부트로더는 그대로 두고 앱만 우리 것으로** 바꾼다.
브링업은 `hpm5300evk` 저장소를 작업장으로 써서 끝냈고(2026-08-28~29), 되는 것만
여기로 옮겼다. 리버싱 근거 전체는 그쪽에 있다.

    ~/hdd/git/hpm5300evk/firmware/hpm5361-fw/docs/              덤프·디스어셈블 (깃 제외)

## 지금 상태 — 다 된다

키 스캔 · HID · QMK/VIA · RGB 가 전부 동작하고, 시험도 통과했다.

| | wish60-he-7u | wish61-he |
|---|---|---|
| `he_test.py` | 25 통과 · 0 실패 | 25 통과 · 0 실패 |
| `via_test.py` | 정상 | 정상 |
| RGB | 정상 | 정상 (104 LED, 육안 확인) |
| 빌드 | FLASH 20.7% | FLASH 31.5% |

보정 뒤 전 키를 바닥까지 눌러 잰 값 (공칭 3.40mm 대비, `789d5e3` 이후)

    wish60   3.34~3.49   평균오차 0.02  최대 0.09 mm
    wish61   3.36~3.41   평균오차 0.01  최대 0.04 mm

## 빌드·굽기

```sh
tools/build.sh wish61-he    && python3 tools/flash.py      build/wish61-he/wish61-he-tag.bin
tools/build.sh wish60-he-7u && python3 tools/iap_update.py build/wish60-he-7u/wish60-he-7u-tag.bin
```

★ **플래셔가 보드마다 다르다.** `flash.py` = wish61(벤더 IAP), `iap_update.py` =
wish60. `WISH_PID` 로는 안 갈린다 — 그건 `dev.py` 의 CDC 포트만 고른다.

둘 다 앱이 돌고 있으면 알아서 부트로더에 넣고, 굽고, 앱으로 되돌린다. JTAG 이
필요 없다.

## 보드가 갈리는 곳 — 다섯 군데뿐

앱 소스는 한 벌이다. `HW_BOARD` 축으로 갈리는 것은 **부트로더 계약이 정하는 것**뿐.

| | wish60-he | wish61-he |
|---|---|---|
| ldscript | `HPM5361_IAP_APP.ld` (0x80020000, 384KB) | `HPM5361_WISH61_APP.ld` (슬롯+0x1000, 252KB) |
| 후처리 | `fw_tag.py` 매직 4B | `mkimage.py` 헤더 20B + CRC32 |
| 부트 플래그 | `0x1D000` 전용 페이지 | **App1 헤더 페이지 `0x20000`** |
| USB PID | `0x5304` | `0x5305` |
| 표시 LED | 있다 (PA23) | **없다** — PA23 이 RGB 데이터 선 |

핀과 상수는 보드 축이 아니라 **`keyboards/<모델>/config.h`** 에 있다.

## 하드웨어 (전부 실측)

```
아날로그  PB02~PB09,  ADC 채널 {12,8,0,13,9,10,11,1}
          ADC0 앞 4개 / ADC1 뒤 4개 (두 ADC 가 같은 채널을 같은 값으로 본다)
MUX 주소  PY00~PY02 (GPIOY). ★ PIOC 도 ALT3(SOC) 로 넘겨야 한다
RGB       PA13=SPI3.MOSI 키 LED 65,  PA23=SPI2.MOSI 언더글로우 39
LED 전원  PA09 언더글로우 / PA10 키 위 / PA11 키 아래  ★ 안 세우면 안 켜진다
플래시    App1 0x20000~0x60000,  App2(벤더 백업) 0x60000~0xA0000  ★ 건드리면 안 됨
          우리 몫 0xC0000~0x100000 (wish60 과 같은 자리)
```

### ~~3. 벤더 펌웨어 → 우리 펌웨어~~ ✔ 같이 끝났다

부트로더를 서술자(`IapSpec`)로 뽑고 굽는 쪽이 고른 보드에서 가져다 쓴다.

| | wish60-he | wish61-he |
|---|---|---|
| 부트로더 | `534B:4102` / `0xFF53` | `1CA6:300B` / `0xFFB0` |
| 전송 | 자체 (START·DATA·FLUSH·END, 4KB 페이지) | `08 02` + addr(LE32) + len(LE16) + 56B |
| 완료 | — | `08 03` ValiDate → `08 04` BootToApp |
| 모드 판정 | — | `01 02` 응답 바이트 16 (255=부트, 0=앱) |

`tools/flash.py` 의 **청크 재시도**도 같이 옮겼다. 그리고 wish61 은 **벤더 앱과
부트로더가 같은 VID/PID/usage page** 를 쓰므로, 채널이 보인다고 부트로더라 단정하면
안 된다 — `01 02` 로 물어봐야 한다.

같이 고친 것 — 어긋나면 굽기를 **막고**(경고만 하고 열어 뒀었다), 장치가 바뀌면
자동 선택이 따라가고, 옛 장치 정보를 버리고, 굽고 나면 방금 구운 보드로 돌아온다
(대상이 사라진 사이 VIA 가 선택을 옮긴다).

★ 순정 보드 개조는 **진입만 다르다** — 벤더 앱에는 우리 `0xFF60` 채널이 없으므로
  자기 채널에 `08 01`(AppToBoot). 그 뒤는 같은 길이다.

★ **wish61 은 아직 배포본이 없다.** `public/firmware/wish61-he/manifest.json` 이
  빈 목록이라 "파일에서 굽기" 만 열려 있다. 배포를 내려면 `tools/make_release.py`.

### ~~4. `keys cal` 안내 문구~~ ✔ 고쳤다 (2026-08-29, `742b558`)

"끝까지" 를 "평소 치는 힘으로" 로 바꾸고 "끝난 키" 라는 말을 걷어냈다. 보정할 때의
손힘이 곧 그 키의 mm 눈금이라, 세게 누르라고 하면 눈금이 10% 늘어난다 — 실제로
그렇게 안내했다가 평소 타건이 3.40 이 아니라 3.23mm 로 읽혔다.

**완료 문턱 자체는 못 좁힌다.** 키마다 센서 감도가 1.4배까지 차이 나서
(실측 2430~3417) 전역 문턱으로는 "감도가 낮은 키" 와 "덜 눌린 키" 를 가릴 수 없다.
올리면 감도 낮은 키가 영영 안 끝난다.

```c
#define KEYS_CAL_STROKE_MIN  (500 * KEYS_ACC_CNT)   /* = 1500 카운트, 실측의 48~69% */
```

**다만 그 문턱이 값을 자르지도 않는다.** 칸이 차는 것이 손을 멈추지 않고, 한 번
눌러 내리는 동작 안에서 `cal_min` 은 가장 깊은 지점을 잡는다. 같은 힘이면 보정은
**1% 안으로 재현된다** (실측). 그래서 여기서 지킬 것은 알고리즘이 아니라 문구였다.

### 5. 크로스토크 — 재 놓았다. 실사용에는 문제가 없다

한 키를 두드리면 다른 칸의 원시값이 조금씩 흔들린다. `J` 를 두드려 셋으로 갈랐다
(값은 원시 카운트, 주 키의 흔들림은 2350).

```
                       반응형    정적     RGB 끔
숫자열 8 / 7 / 6      83/74/59  20/14/11   0/0/0
미연결 s2/ch0            82       80       78
P · ' · = · Tab       36~10     32~7     36~7

주 키 제외 합계          788      388      327
```

**① RGB 가 바뀔 때 — 전체의 절반.** 숫자열 유령의 75~80% 다. 반응형 조명이 누른 키
주변을 밝히며 만드는 **전류 계단**이다. 숫자열이 유독 큰 이유는 **키 LED 체인의 머리**가
거기(백스페이스에서 왼쪽으로)라 전류 계단이 가장 크기 때문이다.

**② LED 가 켜져 있기만 해도 — 20%.** 정적인데도 20/14/11 이 남고 끄면 0 이다.
전송(DMA)이나 점등 전류의 몫이다. 작다.

**③ RGB 와 무관 — 327.** 대부분이 `s2/ch0` **80** 인데 이건 **미연결 칸**이고 눌린
`ch1=PB03` 과 **핀이 붙어 있다**(`ch0=PB02`). 떠 있는 고임피던스 입력이 옆 핀 전압을
용량성으로 줍는 것이고, `keys_present` 가 판정에서 건너뛰므로 해가 없다.
`P`·`'` 의 30 안팎은 아직 설명이 없다 — 조립을 마치고 다시 잴 것.

★ **실사용에는 문제가 없다.** 최악이 0.13mm 이고 입력지점은 1.00mm, 프리셋 최저도
  0.30mm 다. 다만 입력지점을 0.2mm 아래로 내리는 길을 열면 여기에 닿는다.

★ **위상 맞추기(전송과 스캔)는 할 이유가 없다.** 전송 자체의 몫이 20%, 절대값 20카운트
  (0.03mm)다. 구조를 바꾸는 비용에 비해 얻는 게 없다.

★ **필터·ADC 클럭으로는 안 줄어든다.** 반응형 조명의 전류 변화는 수백 ms 지속되는데
  변환 한 번은 0.4us 다 — 그 구간의 모든 변환이 똑같이 밀린다. wish60 에서 분주
  4→3 으로 올렸을 때 결합이 +8.5→+10.0 으로 측정 산포 안이었고, 샘플 조리개를
  5→16 으로 넓혀도 잡음이 그대로였다 (2026-08-17).

★ **남은 레버는 밝기와 효과 종류다.** ①이 전류 계단 크기에 달렸으니 밝기에 비례할
  것으로 보이지만 **아직 안 쟀다.** 재서 비례하면 `RGB_MATRIX_MAXIMUM_BRIGHTNESS`
  (지금 110)가 그대로 레버가 된다.

### 6. 벤더 펌웨어의 ADC 처리 — 참고한 것

`analysis-wish61-he/app.ll.dis` 에서 뽑았다.

**필터** (`0x800211bc`, 스캔 핫 경로) — 칸마다 32비트 누산기 하나.

```
acc = acc + raw − (acc >> 2)      시상수 4의 지수이동평균 (IIR)
out = acc >> 2                     16비트로 잘라 저장
```

64칸을 **2 ADC × 8 스텝 × 4 채널**로 도는 것까지 우리와 같다. 우리는 3탭 박스카
(`KEYS_ACC_CNT 3`)다. 계수는 **양쪽 다 상수** — 벤더에도 적응 필터는 없다.

**ADC 설정** (`0x8002e238`)

```
sh 0x315 → res = 21 (16비트),  conv_mode = 3 (preemption)
sw 4     → adc_clk_div = 4  (33.3MHz)
sh 0x101 → sel_sync_ahb = 1, adc_ahb_en = 1
```

| | 벤더 | 우리 |
|---|---|---|
| 해상도 | 16비트 | 12비트 |
| 변환 모드 | preemption | sequence + DMA |
| 분주 | 4 (33.3MHz) | 3 (44.4MHz) |
| 트리거 | GPTMR1→TRGM0 하드웨어 주기 | 소프트웨어 |

★ **RGB 때 추가 처리는 없다.** `TRGM0`(0xf033c)를 건드리는 곳이 **앱 전체에서 초기화
  한 곳뿐**이다. LED 를 쏘는 동안 트리거를 끄거나 표본을 버리지 않는다.

★ **16비트를 따라갈 이유가 없다.** 우리 잡음 바닥(p-p 42~47 카운트)이 이미 12비트
  양자화보다 훨씬 크다. 눈금만 잘게 나뉘고 변환이 14→21 클럭으로 길어져 스캔율만 잃는다.

## 겪은 것 — 같은 데 두 번 빠지지 말 것

★★ **캐시를 채우는 자리를 빠뜨리면 "재부팅해야 먹는" 버그가 된다.** `keysCalSave()`
  와 `keysCfgLoad()` 에 `keysThrRebuild()` 가 없어서, 보정을 저장해도 판정 임계값도
  깊이 표시도 옛 스트로크로 계속 돌았다 (`789d5e3` 에서 고침). 61키 실측 오차가
  0.16mm → 0.01mm 로 줄었다.

  진단 과정에서 두 번 놓쳤고, 놓친 방식이 더 값지다.

  - **진단 명령이 진단 대상을 고치는 경우가 있다.** 값 주입 시험이 통과해 가설을
    접었는데, 그 직전에 돌린 `keys base` 가 `keysCalibrate()` 안에서 재빌드를 부른다
  - **설명 안 되는 사실이 남으면 그게 답이다.** "재보정했는데 값이 안 변한다" 는
    이미 결정적이었는데 손힘 탓으로 돌렸고, 그 바람에 있지도 않은 "바닥이 무르다" 를
    만들어 냈다

★ **`tools/flash.py` 는 wish61 전용이다.** wish60 은 `tools/iap_update.py` 다.
  `WISH_PID` 는 **dev.py 의 CDC 포트만** 고르고 flash.py 의 HID 대상은 안 바꾼다.
  wish60 이미지를 flash.py 에 넘겨 wish61 을 부트로더에 처박은 적이 있다.

★★ **같은 사실을 두 곳에 적지 않는다.** 오늘 네 번 당했다.

  - `cellmap.h`(MUX 주소 공간) vs `layout.h`(스캔 루프 공간) — 그레이 코드만큼 어긋남
  - `led_chain()` vs 좌표 생성 — 같은 규칙을 두 곳에 적어 한쪽만 고침
  - VIA 정의의 PID 가 상수로 박혀 wish60 정의를 덮어쓸 뻔함
  - `he_test.py` 의 시험 셀 `(0,0)` — wish60 은 X, wish61 은 RCtrl

★★ **미연결 칸은 조용하지 않다.** ADC 샘플홀드에 직전 전하가 남아 앞 칸 값을
  스텝당 0.58배로 끌고 온다. 센서가 붙은 칸은 저임피던스라 그 잔류를 지우므로
  **번지는 것은 빈칸 바로 앞 키뿐**이다. 세틀링을 3000 nop 까지 올려도 안 변한다.

★ **개수가 딱 맞아떨어지는 것은 검증이 아니다.** 유령 입력이 빈자리를 채워
  "ch0 5개, 나머지 8개, 합 61" 이 성립해 버렸고 Fn 이 빠진 것을 못 봤다.

★ **매핑은 그 매핑을 쓸 도구 안에서 잰다.** `keys learn` 이 처음부터 있었는데
  브링업용 `adcscan` 측정을 변환해 넣으려다 하루를 썼다.

★ **시험 중에는 그 키보드를 아무도 만지면 안 된다.** 사용자 타이핑으로 두 번,
  내가 다른 스크립트를 동시에 띄워서 한 번 오염됐다. 지금은 `dev.lock()` 이 막고
  `he_test.py` 가 경고를 찍는다.

★ **호스트를 의심할 때를 안다.** 장치 지표(에지·리포트 수·유실·타임아웃·잡음)가
  전부 정상인데 화면만 이상하면 호스트다. 2026-08-29 의 "키 반복" 은
  **Karabiner-Elements** 였다 — 한글 IME 조합이 재발행에 무너진 것이다.
