# 7. 드디어 키보드

> 전체 목차는 [README.md](README.md) 를 본다.

6편의 눌림 판정을 HID 리포트로 내보낸다. 여기까지가 **"완전히 동작하는 평범한 키보드"**
목표 지점이다.

## 인터페이스 배치

부트 키보드를 IF0 에 넣었다. **일부 BIOS 가 첫 인터페이스만 본다.**

```
IF0  HID 부트 키보드   0x03/01/01   EP 0x82  mps 8   bInterval 1  = 125us = 8kHz
IF1  raw HID           0xFF60       EP 0x84/0x04     bInterval 4
IF2  CDC 제어         ┐ IAD
IF3  CDC 데이터       ┘
```

raw HID 가 IF0 → IF1 로 밀렸지만 **호스트 도구는 usage page 로 찾으므로** 고칠 것이
없었다. 상용 보드도 IF0 이 부트 키보드고 `bInterval=1` 이다.

> ★ **등록 순서가 곧 인터페이스 번호다.** CherryUSB 의 `usbd_add_interface()` 는 부른
> 순서대로 번호를 매긴다. 그런데 `cdcInit()` 은 링버퍼를 스택보다 먼저 만들려고
> `hw.c` 에서 `usbInit()` 보다 앞서 불린다. 거기서 인터페이스 등록까지 하면 CDC 가
> IF0 을 가져가 기술자와 어긋난다. 그래서 `cdcIfInit()`(버퍼) / `cdcIfRegister()`(등록)
> 로 갈랐다.

## 키맵

`tools/gen_keymap.py` 가 KLE 에서 생성한다. 키코드 공간을 이렇게 나눴다.

```
0x00        KC_NO       배정 안 됨 — 레이아웃 옵션 자리. VIA 가 채운다
0x01~0xDF   HID Usage   리포트의 키 배열로
0xE0~0xE7   모디파이어  리포트 [0] 바이트의 비트로
0xF0~       내부        FN 등. HID Usage 가 아니라 리포트에 실리지 않는다
```

`0xF0(FN)` 은 스플릿 우시프트 오른쪽 1u 자리(`1,6`)에 뒀다. 60% 는 F키·방향키를
레이어로 올려야 하는데 배치 어디에도 FN 이 없었다. 지금은 자리만 잡고, 레이어 동작은
11편에서 VIA 와 함께 붙인다.

`keys_present[]` 도 스캔에 반영했다. 없는 셀은 판정하지 않고, **캘리브레이션 중앙값
계산에도 넣지 않는다** — 자석이 없어 늘 높은 값이라 기준을 위로 끌어올린다.

## 지연 — 목표를 잘못 잡았다가 고쳤다

처음에는 **매 폴링마다 재무장**해서 초당 8000 리포트를 채우려 했다. 그런데 그러면
오히려 느려진다.

```
매번 재무장   키가 바뀜 -> 이미 실려 있는 옛 리포트가 먼저 나감 (최대 125us)
                        -> 완료 -> 재무장 -> 다음 폴링 (125us)     합쳐 최대 250us

바뀔 때만     키가 바뀜 -> 즉시 프라임 -> 다음 폴링                최대 125us
```

**지연이 절반이고, 같은 값을 되풀이해 보내느라 버스와 CPU 를 쓰지도 않는다.** 안 실려
있는 동안 하드웨어가 NAK 하는 것은 정상 동작이다.

그래서 구조는 이렇다.

```
스캔 (자유 구동)  ──▶  hidKbdSetReport() : 바뀌었을 때만 섀도 갱신 + 프라임
USB 완료 콜백(ISR) ──▶  그 사이 또 바뀌었으면 곧바로 잇는다
```

**"초당 리포트 수"는 성능 지표가 아니다.** 놀 때 0 이고 칠 때만 올라가는 게 맞다.
지연을 정하는 것은 폴링 주기(`bInterval=1` → 125us)이지 전송 횟수가 아니다.

## 8kHz 폴링은 확인됐다

그래도 "매 폴링마다 보내면 8000 이 나오는가"는 따로 재봤다. 5900/s 에서 멈췄고,
하나씩 배제했다.

| 확인 | 결과 |
|---|---|
| 호스트 폴링 | **8kHz 정상** — 완료 간격 최소 115us |
| 컴파일 최적화 | 무관 — `-O0` / `-Og` 모두 약 5900/s |
| 메인 루프 간섭 | 무관 — 메인 루프를 굶긴 채 재도 5917/s |
| ADC 인터럽트 | 무관 — 폴링으로 바꿔도 그대로 |

남은 것은 완료 → 재프라임 왕복이었고, **상용 펌웨어를 디스어셈으로 확인해 결론이
났다.**

> *(분석 인용은 옮기지 않는다)*

SDK 의 `usb_device_edpt_xfer()` 마지막 세 줄 그대로다. **상용도 dTD 를 하나만 걸므로
매 마이크로프레임마다 같은 왕복을 한다 — 상한이 같다.** 복원해서 재볼 필요가 없었다.

> 호스트에서 재려 했으나 macOS 가 키보드 HID 열기를 root 아니면 차단한다.
> `0xE00002E2 not permitted` → 권한 부여 후에도 `0xE00002C1 privilege violation`.

**실사용 지연에는 영향이 없다.** 리포트는 바뀔 때만 나가고 그때 즉시 프라임되어
다음 폴링(≤125us)에 실린다. 5900 은 매 폴링마다 억지로 보낼 때의 상한일 뿐이다.

## 겪은 함정

### ① ADC 완료를 인터럽트로 받고 있었다

하는 일이 플래그 하나 세우는 것뿐인데 스캔 루프가 어차피 스핀으로 기다리고 있었다.
8스텝 × ADC 2개 × 초당 15,000 스캔이면 **초당 24만 번**이다. 상태 레지스터를 직접
폴링하도록 바꿨다. (리포트 속도와는 무관했지만 그냥 없애는 게 맞다.)

### ② 측정 명령이 메인 루프를 굶겼다

`usb rate` 가 빈 루프로 3초를 기다렸더니 스캔도 리포트 갱신도 안 돌아 **"키를 눌러도
0"** 이 나왔다. RTOS 가 없어서 CLI 명령이 도는 동안 메인 루프가 멈춘다.
`cliLoopIdle()` 이 `moduleUpdate()` 를 부르는 통로라 대기 루프에서 그걸 부른다.

## 검증

```
cli# usb info
KBD Ready   : 1

cli# usb rate
KBD 리포트 : 8 개 / 3000 ms      <- 키를 눌렀다 뗀 횟수만큼
```

그리고 편집기에 실제로 타이핑된다. `2222u` 가 CLI 에 찍힌 것이 스캔 → 판정 → 키맵 →
HID 리포트 경로가 끝까지 동작한다는 증거였다.
