# 12. 스캔을 62us 에서 33us 로

> 전체 목차는 [README.md](README.md) 를 본다.

10편에서 QMK 를 얹은 뒤 스캔이 38us 에서 62us 로 느려졌다. 목표는 "스캔을 슈퍼루프에서
떼어내 25us 대로" 였는데, **재보니 구조가 문제가 아니었다.**

## 한 것

- `keys time` 을 단계별 분해 측정으로 바꿈
- `-O0` → `-O2`, 스캔 경로를 ILM 에 배치
- `-O2` 가 드러낸 잠복 버그 둘을 수정 (DMA 경합, `volatile` 누락)
- 우리 소스만 `-Wall -Werror`, `config.h` 강제 인클루드

```
  메인 루프 스캔    62 us  ->  33 us      (유효 30 kHz)
  라이브 트래킹    241/s  ->  620/s
  keyboard_task    8 us  ->   2 us (평균)
```

---

## 총량만 보면 손댈 데를 못 고른다

처음에는 구조 탓으로 봤다. 참고 보드는 스텝 안에서 생값을 누적만 하는데 우리는
`keysFilter` 8번에 `keysTrack` 까지 스텝 안에서 하니, 두 배 걸리는 게 당연해 보였다.

그래서 `keys time` 을 **단계를 쌓아 돌리고 차이로 몫을 뽑도록** 바꿨다.

```
cli# keys time
  mux+settle :   5.998 us   (+ 5.998)
    +adc 변환 :  29.730 us   (+23.732)   <- 순수 대기. CPU 는 놀고 있다
    +filter  :  43.645 us   (+13.915)
    +track   :  62.040 us   (+18.395)
```

후처리가 32.3us 다. 64키니까 **키당 505ns, 400MHz 에서 200 사이클**이다. 데드밴드
하나에 200 사이클은 말이 안 된다. 구조가 아니라 코드 생성이 문제였다.

## 원인 ① — `-O0`

이식 중 추적이 쉽게 하려고 둔 값이었다. 예전에 "최적화는 USB 폴링과 무관하다"고
확인하고 그대로 뒀는데, **폴링은 USB 하드웨어가 정하고 스캔은 코어가 정한다.**
같은 실험으로 두 가지를 결론 낸 것이 잘못이었다.

```
스캔 1회 (8 step x 8 ch)      -O0        -O2
  mux + 세틀링              5.998 us   1.262 us
  + ADC 변환 대기          23.732     19.528
  + 데드밴드 필터          13.915      2.619
  + 기준값 추적·판정       18.395      5.067
  ─────────────────────────────────────────────
  합계                     62.040     28.476
```

## 원인 ② — 명령어 캐시 축출

`-O2` 로도 문맥에 따라 값이 갈렸다.

```
                                  측정 루프   메인 루프
  keysUpdate() 반복만                29 us       —
  qmkUpdate() · usbUpdate() 와 섞임    —        63 us
```

사이에 낀 코드가 XIP 플래시 캐시에서 스캔 코드를 밀어내, **매 스캔이 플래시에서 다시
읽혔다.** 스캔 경로(`keysUpdate` · `keysTrack`)를 `ATTR_RAMFUNC` 로 ILM 에 올렸다.
128KB 중 1KB 도 안 쓰고 있던 자리다.

> 같은 코드가 문맥에 따라 두 배 느릴 수 있다는 것이 이 편의 가장 큰 수확이다.
> 성능을 잴 때는 **실제로 도는 자리에서** 재야 한다.

---

## `-O2` 가 드러낸 잠복 버그 둘

### ① "변환 끝"과 "버퍼에 앉음"은 다른 사건이다

`SEQ_CMPT` 는 마지막 채널의 **변환**이 끝났다는 뜻이지, 그 값이 DMA 버퍼에 앉았다는
뜻이 아니다. `-O0` 에서는 플래그를 보고 버퍼를 읽기까지 코드가 충분히 느려 가려져
있었는데, `-O2` 로 간격이 좁아지자 각 시퀀스의 **마지막 원소**만 직전 스텝 값을 읽었다.

```
             ch0  ch1  ch2  ch3   ch4  ch5  ch6  ch7      <- 시퀀스 위치 3 = 마지막
  노이즈 p-p   8    6    6   82     9    9    9   72
  s3           4    5    7   12     4    4    4  231
```

MUX 는 스텝마다 바뀌므로 **다른 키의 값**이 들어온다. 실제로 "엉뚱한 키가 연속으로
눌린다"로 나타났다.

`cycle_bit` 은 못 썼다 — SW 트리거가 시퀀스를 0번부터 재시작시켜 포인터가 감기지
않는다 (수백만 스캔 뒤 덤프해도 네 워드 모두 bit31 = 0). 마지막 칸을 0 으로 비워 두고
채워지는 것을 본다. DMA 워드에는 채널 번호가 실려 있어 절대 0 이 아니다.

나중에 `SEQ_CMPT` 폴링 자체를 걷어냈다. DMA 기록은 변환이 끝나야 일어나므로 뒤엣것이
앞엣것을 이미 포함한다.

### ② DMA 버퍼가 `volatile` 이 아니었다

`ATTR_PLACE_AT_NONCACHEABLE_BSS` 는 **하드웨어 캐시** 이야기라 컴파일러와 무관하다.
컴파일러 눈에는 아무도 쓰지 않는 배열이라 읽기를 합치거나 루프 밖으로 끌어낼 수 있다.
"채워질 때까지 기다리는" 회전은 `volatile` 없이는 애초에 성립하지 않는다.

## 경고를 오류로 — 그리고 거기서 또 하나

매직 스왑 버그([11편](11-via.md))는 컴파일러가 **이미 경고하고 있었다**
(`-Wint-conversion`, 기본 켜짐). QMK 와 SDK 가 쏟아내는 경고에 묻혔을 뿐이다.
무시되는 경고는 없는 것과 같으므로 범위를 우리 것으로 좁혀 오류로 올렸다.

켜자마자 진짜 버그가 하나 나왔다.

**`config.h` 가 아무 데서도 먼저 들어오지 않았다.** QMK 상류 빌드는
`-include config.h` 로 강제하는데 우리는 그걸 빼먹었다. `config.h` 는 `host.h` 를 타고
늦게 들어왔고, 그전에 `eeconfig.h` 가 처리된 번역 단위에서는

```c
#ifndef EECONFIG_USER_DATA_SIZE
#    define EECONFIG_USER_DATA_SIZE 0
```

가 0 으로 굳었다. **같은 매크로가 파일마다 0 이기도 512 이기도 했다.** `EECONFIG_SIZE`
와 사용자 영역 주소가 번역 단위마다 달랐다는 뜻이다.

`-Wextra` 는 넣지 않았다. `src/common` 은 다른 프로젝트와 공유하는 틀이라
`sign-compare` 만 여덟 군데 나오는데, 고치면 원본과 갈라진다. 잡으려던 종류는
`-Wall` 로 잡힌다.

## 남은 것

```
  mux + 세틀링          1.29 us
  ADC 변환 + DMA 도착  23.72        <- 하드웨어. 여기가 바닥이다
  데드밴드 필터         2.69
  기준값 추적·판정      4.77
  ─────────────────────────
                       32.5 us
```

23.7us 는 ADC 하드웨어 시간이다. `adc_clk_div` 와 `sample_cycle` 을 건드리면 줄지만
그 둘은 참고 보드와 같은 값으로 맞춰 둔 것이라 두기로 했다 — 잡음과 맞바꾸는 일이다.

남은 여지는 **겹치기**뿐이고, 그것은 [13편](13-rapid-trigger.md) ①에서 한다.
