# wish40-he — 브링업

42키 HE 보드(HPM5361**ICF1**, LQFP64). 우리가 설계한 보드라 **칩이 비어 있다** —
부트로더도 우리가 만든다. 순서는 ① 회로 시험 → ② 부트로더 → ③ 본 펌웨어 포팅.

★ 부트로더를 펌웨어보다 먼저 한다. 본 펌웨어에서 보드마다 갈리는 다섯 군데(링커 주소 ·
  이미지 형식 · 부트 플래그 · `reset boot` · 플래시 배치)가 전부 부트로더 계약이다.
  또 **조립하면 밑면 택트 스위치 둘과 JTAG · BOOT 헤더에 손이 안 닿는다** — USB 로 굽고
  USB 로 살리는 길이 조립 전에 있어야 한다.

★ USB 인터페이스는 wish60 · wish61 과 **똑같이** 맞춘다 (키보드 HID · VIA `0xFF60` ·
  CDC · 부트로더 진입 명령). 웹앱과 `iap_update.py` · `dev.py` 를 그대로 쓰기 위해서다.

★ USB ID — 앱 **`0483:5307`**, 부트로더 **`0483:5308`** (2026-10-26 결정)

  - 앱은 보드마다 달라야 한다. VIA HE 앱이 VID/PID 로 보드 정의를 찾는다
  - 부트로더도 따로 준다. wish60 과 같은 `534B:4102` 면 **앱이 깨져 부트로더에 머문
    보드를 웹앱이 wish60 인지 wish40 인지 못 가린다** — 엉뚱한 펌웨어를 권하게 된다.
    `534B` 는 wish60 에 원래 있던 벤더 부트로더의 것이라 빌려 쓸 이유도 없다
  - 프로토콜은 wish60 부트로더 그대로다 (usage page `0xFF53`, 64B, 0x80~0x83).
    `iap_update.py` 는 usage page 로만 찾으므로 그대로 되고, 웹앱은 wish40 용 IapSpec
    하나만 더하면 된다
  - `0x5306` 은 **qmk-link 가 쓴다** — 처음에 그걸로 정했다가 다른 저장소를 뒤져 찾았다.
    `0483` 아래 계열 번호: 5304 wish60 · 5305 wish61 · 5306 qmk-link · 5307/5308 wish40

## 핀 — 회로도 `SCH-WISH40-HE` (2026-10-26)

| 핀 | 용도 |
|---|---|
| PB08~PB13 | MAG0~MAG5 — MUX 출력 (100Ω 직렬, 핀에 커패시터 없음) |
| PY00~PY02 | MUX_A0~A2 — MUX 6개 공통 |
| PA31 | 표시 LED (1k 로 GND, HIGH 가 켬) |
| PA30 | BOOT_BTN (SW2, 누르면 HIGH, 10k 풀다운) |
| PA02 / PA03 | BOOT0 / BOOT1 스트랩 (10k 풀다운, BOOT0 은 H3 헤더로 올린다) |
| PA00 / PA01 | UART0 — H2 헤더 |
| PA04~PA08 | JTAG — H1 헤더 (TRST 포함, SRST 없음) |
| PA24 / PA25 | USB DP / DM |

RGB 는 없다. VDD_SOC 는 외부 LDO(1.2V) — 내장 DCDC 를 설정하면 안 된다 (1편).

이전의 설계 문서(핀 배정 단계)와 다른 곳: RGB(PA29) · LED 전원(PA10) · 부트 스트랩(PA09)
은 회로도에 **없다.** 회로도가 출처다.

## ① 회로 시험 — 됐다 (2026-10-26)

`bringup/wish40-he/` 의 단독 이미지(0x80000000, 부트 헤더 포함)를 JTAG 으로 굽고
`tools/bringup_wish40.py` 로 읽는다. QMK · USB 없이 클럭 · LED · MUX · ADC 16채널만 돈다.

```sh
cmake -S bringup/wish40-he -B build/bringup-wish40-he && cmake --build build/bringup-wish40-he
openocd -s tools/openocd -f hpm5361-fw.cfg -c "adapter speed 4000" -c init -c "reset halt" \
  -c "flash write_image erase build/bringup-wish40-he/wish40-he-bringup.elf" -c "reset run" -c exit
python3 tools/bringup_wish40.py            # 지금 값 + 채널 판정
python3 tools/bringup_wish40.py range      # clear 뒤 키를 눌러 보고
```

| 항목 | 결과 |
|---|---|
| JTAG | TAP `0x1000563d`, 내장 플래시 1MB 프로브 · 쓰기 · 검증 |
| ROM 부팅 | 부트 헤더 → `main` 까지 간다 (XIP 120MHz 옵션) |
| 클럭 | CPU 400,000,000 Hz, ADC 133.3MHz — 외부 LDO 전압에서 PLL 정상 |
| MUX 주소 | GND 칸이 회로도 그대로 — MAG0 은 주소 5·7, MAG2~4 는 6, MAG5 는 3. **A0~A2 세 비트가 다 산다** |
| 센서 42개 | 전부 VCC/2 근처 (16비트 32238~32813) — 자석 없는 상태 |
| ADC0 / ADC1 | 같은 패드를 둘 다 본다, 값 일치 |
| 잡음 | 5초 p-p 100~136 (16비트) ≈ 12비트 8 LSB. GND 칸 0 |

**센서가 자기장에 반응한다** — Esc 자리에 스위치 하나를 올려 눌렀다 (2026-10-26).

| | 안 눌림 | 바닥까지 | 차 |
|---|---|---|---|
| 주소 0 · ch11 (ADC0) | 32644 | 49277 | **+16633** (12비트 약 +1040, 약 +0.84V) |
| 주소 0 · ch11 (ADC1) | 32613 | 49275 | +16662 |

다른 센서 칸은 그대로였다. ch12 가 따라 오른 것은 떠 있는 패드가 직전 채널(ch11)을
물고 온 것이다 — 키와 무관하다.

★ **누르면 값이 오른다.** wish61 은 "누르면 준다" 였다. 데이터시트(TI SBASAI5E)와 맞는지 봤다.

  - 8.3.1절: 자속이 패키지 아래 → 위(마킹면)로 지나가면 B 가 양수다 — 마킹면에 S극이
    올 때다. 출력은 `VOUT = VQ + B × S` 라 B 가 양수면 오른다 (BA3 는 양극성)
  - 센서 42개는 **PCB 밑면**에 있다(케이스 `parts_flip.pkl`). 마킹면이 아래를 보고 자석은
    센서 뒷면(패드 쪽)에서 온다. 뒷면에 N극 = 마킹면에 S극과 같은 자속 방향이다
  - 그러므로 **자석 아래쪽이 N극이면 오르고, S극이면 내린다.** 이 스위치는 N극이 아래다.
    이상이 아니다

  크기도 규격 안이다. 바닥 2.48V − 휴지 1.64V = 0.84V, 15mV/mT 로 **약 56mT** —
  범위 ±80mT 의 70% 라 포화(바닥값 잘림)가 없다. 휴지값 1.64V 도 VQ 규격(1.61~1.69V) 안이다.

  휴지 자기장도 쟀다 (Esc, 같은 칸)

      스위치 없음      32576   1.640V    0mT (VQ)
      올림, 안 눌림    33980   1.711V   +4.7mT
      바닥까지         49277   2.481V   +56mT

  **0 을 지나지 않고 한 방향으로만 는다** — 바텀 실장 + 자석 N극 아래의 예측 그대로다.
  스위치 제원(16 → 72mT)보다 작은 것은 PCB 1.6mm 만큼 멀어서다.

  설계 문서(`hpm5300evk` 저장소 `hpm5361-fw/docs/hall-keyboard-design-spec.md`)가 바로 이
  구성(TMAG5253BA3 · 뒷면 실장 · N극 하향)을 전제로 했다. 그 문서의 미확정 1번 **"자석
  극성"이 닫혔다 — N극 하향이다** (wish60 과 같은 스위치, GEON Raw HE).

      GEON Raw HE @1.6mm    예측      실측
      바닥                  54.0mT    약 56mT    맞다 (4%)
      휴지(초기 자속)       14.4mT    약 4.7mT   1/3 이다

  ★ 휴지 쪽이 크게 어긋난다. 설계 문서도 미확정 3번("측정 PCB 두께 미명시")으로 그 근거를
    의심해 두었다. 휴지 자속이 작으면 **상단 구간 기울기가 작아** 얕은 작동점 · RT 의 SNR 이
    예측보다 나빠진다. 스위치 하나 한 번이라 확정은 아니다 — 키를 다 올리고 다시 잰다.

  ★ **스위치는 wish60-he 와 같은데 wish60 은 누르면 내려갔다** (06편, 휴지 40318 ≈ 2.03V
    → 바닥 26960 ≈ 1.36V). 같은 스위치라면 차이는 센서 쪽이다. 그런데 wish60 은 휴지가
    VCC/2 보다 높고 바닥이 낮다 — TMAG5253 이었다면 이동 중 0mT 를 지나야 나오는 모양이다.
    **센서가 다른 품목(출력 방향이나 VQ 가 다른)일 가능성이 크다.** 상용 보드라 품번을
    적어 두지 않았다 — 칩 마킹을 보기 전까지는 추정이다.

  ★ keys.c 는 "누르면 내려간다" 를 가정한다 (keys.c 보정 이상치 판정 "누르면 값이
    내려가므로" 등). 같은 펌웨어에서 wish60 · wish61 은 내리고 wish40 은 오른다.
    포팅할 때 방향을 보드 상수로 박기보다 **보정 때 키마다 재서 정하는** 쪽을 본다.

★ Esc = (주소 0, ch11) = U6 S0 = R0_C0 = U11. **부트로더 강제 진입 키로 쓴다** — 주소를 0 에
  두고 ch11 한 번 읽어 문턱(예: 40000)을 넘으면 남는다.

**아직 안 본 것** — 나머지 41칸. 스위치를 다 올리면 `range` 로 전부 움직이는지 보고,
그때 MAG2·3·4 와 ch2·3·4 의 짝도 갈린다 (GND 무늬가 같다).

### ★ ADC 채널 <-> 패드 — wish60 문서가 틀렸다

GND 무늬로 쟀다.

    MAG0 (PB08) = ch11      MAG5 (PB13) = ch5
    MAG1 (PB09) = ch1       MAG2~4 (PB10~PB12) = ch2 · ch3 · ch4 (순서는 키로 가른다)

나머지 열(0, 6~10, 12~15)은 떠 있다 — 값이 주소마다 흘러내린다(샘플 커패시터가 직전
채널을 물고 온다). 0 · 8 · 9 · 10 · 12 · 13 은 LQFP64 에 없는 PB02~PB07 이다.

**wish61-he config.h 의 벤더 표(PB08 = IN11, PB09 = IN1, PB04 = IN0 ...)와 전부 맞는다.**
00편의 "PB08~PB15 → ch0~ch7" 은 틀렸다. wish60 이 멀쩡히 도는 것은 드라이버가 패드가
아니라 채널 번호만 쓰기 때문이다 — 주석의 패드 이름만 틀렸던 것이다.

### ★ 시험 코드가 코어를 묶었다 — JTAG 이 안 붙을 때

첫 판은 원샷 ADC 를 `wait_dis=false`(변환 끝까지 버스를 잡는다)로 두고
`adc16_enable_oneshot_mode()` 를 빠뜨렸다. 첫 읽기가 영영 안 돌아왔고, 그 상태의 코어는
**디버그 정지조차 못 받는다** — `Unable to halt`, `init` 의 examine 부터 실패한다.

`reset halt` 는 examine 이 끝나야 쓸 수 있어 소용없다. **DMI 를 날로 써서 리셋과 정지
요청을 같이 건다** (dmcontrol = ndmreset | haltreq). 그러면 ROM 에서 멈추고 examine 이
통과한다. 그 뒤 `reset halt` 로 다시 붙잡고 굽는다. `bringup_wish40.py --rescue` 가 이
절차다.

    irscan hpm5361.cpu 0x11;  drscan hpm5361.cpu 2 0x2 32 <dmcontrol> 7 0x10
    0x00000001 -> 0x80000003 -> 0x80000001 -> arp_examine -> reset halt

부트로더도 같은 함정에 빠질 수 있다 — **버스를 무한히 잡는 접근은 쓰지 않는다.**

## ② 부트로더 — 됐다 (2026-10-26)

**설계와 까닭은 [19편](19-wish40-bootloader.md) 에 있다** — 플래시 배치, 부팅 판정, 끊겨도 사는
굽기 순서, 겪은 함정(VBUS · 타이머 · 이미지 만들기)까지. 여기에는 결과만 둔다.

- 소스 `boot/wish40-he/`, 새 보드용 이미지 `boot/wish40-he/bin/wish40-he-boot.bin`
  (VSCode `boot-wish40-flash`)
- USB `0483:5308`, 프로토콜과 앱 계약은 wish60 부트로더 그대로 — 앱 · `iap_update.py` · 웹앱이
  손대지 않고 쓴다
- 진입 경로 넷(앱 없음 · 플래그 · BOOT 버튼 · **Esc 를 누른 채 꽂기**)을 다 확인했다. 조립한
  뒤에도 USB 만으로 살린다
- ★ LQFP64 에는 VBUS 핀이 없다 — `usb_phy_using_internal_vbus()` 가 없으면 호스트에 안 보인다.
  본 펌웨어(board.c)에도 넣었다

## ③ 본 펌웨어 — 올라왔다 (2026-10-27)

`tools/build.sh wish40-he`. 보드 축은 wish60-he 와 같은 계약(링커 · fw_tag · 플래그 자리)이고,
키보드 축은 `keyboards/wish40-he/` 다.

| | |
|---|---|
| USB | `0483:5307` — 키보드 · NKRO · VIA `0xFF60` · 트래킹 `0xFF61` · CDC |
| 스캔 | 8 x 6 = 48칸, **한 바퀴 21us (46,020/s)** — 8kHz 예산의 16%. ADC 하나가 3채널이라 wish60 보다 빠르다 |
| 태스크 | keyboard_task 평균 2us · 최대 10us · 125us 초과 0, rgb_task 평균 1us |
| 배선 | `keys learn` 42/42 — 레이아웃과 한 칸도 안 어긋난다. MAG2~4 대응도 이것으로 확정 |
| 키맵 | 장치 저장값 3 레이어 x 42 = 126 대조 일치, 실제 타이핑 · 레이어(Tab 홀드) 확인 |
| 보정 | 42/42, 스트로크 2230~2637 (3개 합 눈금, 평균 2439 = 12비트 약 813) |
| 잡음 | 데드밴드 전 p-p 평균 17 · 최대 27 — 스트로크 대비 0.67%, 가만히 둘 때 표시 깊이 0.00mm |

공유 코드에서 바꾼 것 — **wish60 · wish61 바이너리는 바이트 단위로 그대로다** (`SOURCE_DATE_EPOCH`
로 빌드 시각을 고정해 기준과 대조).

- `HW_KEYS_CH_MAX` 를 키보드가 정한다 (기본 8)
- `HW_KEYS_PRESS_RISES` — 하드웨어 값을 복사하는 두 자리(`KEYS_RAW_IN`)에서 뒤집는다.
  keysFilter 에서 뒤집으면 `keys inject` 값까지 뒤집혀 시험 눈금이 바뀐다
- board.c — `usb_phy_using_internal_vbus()` (LQFP64), led.c — PA31 액티브 하이
- gen_keymap.py — 행렬 크기를 KLE 메타데이터(`rows` · `cols`)에서, 기본 키맵을 `keymap-default.json`
  에서 (기존 WISH40 키맵 3 레이어), 언더글로우 0개 허용
- he_test.py — 보드 표에 열 수를 넣었다 (키별 설정 번호가 `스텝 x 열 수 + 열`)

RGB 는 켜 둔 채다 (PA29, 회로도에서 연결 없음). 공유 코드를 RGB 유무로 가르지 않으려는 것이다.

### ★ he_test.py 를 돌리다 맥 화면이 꺼졌다 — 원인 모름

보정 전(스위치는 Esc 하나)에 돌렸다. 통과 6 · 실패 다수, 그러다 **호스트에 밝기 조절이 들어가
화면이 꺼져** 맥을 재부팅했다. 시험이 끝에 설정을 되돌리지 못해 해제지점 0.80mm · RT 켬이
남았다 — 기본값으로 되돌려 저장했다. 키맵은 멀쩡했다.

시험이 쓰는 키코드는 Z · X · F23 · F24 이고 F13~F15(macOS 밝기)는 일부러 피하고 있다. 키맵에도
밝기 키가 없다. 프로파일 2~4 가 비어 있을 가능성도 봤는데 via_port.c 가 네 벌을 다 채운다.

남은 가설 — RT 시험이 RT 를 **보드 전체에** 0.10mm 로 켜는데, 그때 보정 안 된 41칸이 잡음으로
눌림 · 뗌을 되풀이해 Ctrl · Cmd · Alt 가 섞인 입력이 나갔을 수 있다. **확인 전이다.** 리포트를
막은 채(`keys show` 같은 CLI 루프 안) RT 를 켜고 칸별로 저절로 눌리는지 재서 가른다. 그 전에는
wish40 에서 he_test.py 를 돌리지 않는다.

| 열 1 이 스캔 순서대로 부드럽게 오르내린다 (떠 있는 입력의 모양) | U7(MAG1) 납땜 | 고침 |
| 열 5 가 한 값에 고정, GND 칸도 같은 값 | U29(MAG5) 납땜 | 고침 |
| GND 칸이 엉뚱한 행으로 옮겨 가고 짝 행(주소 0·1, 2·3)의 값이 같다 | A0 가 GND 에 붙음 (U29 11번 옆 12번이 GND 인 S3) | 고침 |
| `keys learn` 에서 주소 4~7 의 키만 저절로 눌리고 `,` 가 안 잡힌다 | A2 접촉 불량으로 보인다 — **확인 전** | 남음 |

★ **납땜할 때는 USB 를 뺀다.** 붙인 채로 손보다가 x · z · Space 가 저절로 쳐졌다.

`tools/board_compare.py snap <이름>` 으로 보드를 떠 두고 `cmp A B` 로 칸별 비교한다. 첫 보드는
`A` 로 떠 두었다 (build/board/, 깃에 안 올린다). 같은 모델은 USB 시리얼까지 같아서 **한 장씩**
꽂는다.

## 채널 사이 번짐 — 샘플 시간과 센서 출력 커패시터 (2026-10-28)

`keys raw` 에서 키 하나를 누르면 **늘 정해진 다른 한 키가 15~19 같이 작아진다.** 첫 보드에서
열다섯 키를 하나씩 누른 채 칸마다 평균을 내 보니(`keys dump` 반복, 누르기 전과의 차) 모양이
하나였다.

    누른 키        같이 작아진 키      누른 키        같이 작아진 키
    X  (s2/c1)     V  (s2/c2) -18      D  (s6/c1)     G  (s6/c2) -17
    N  (s2/c3)     ,  (s2/c4) -18      J  (s6/c3)     L  (s6/c4) -17
    Z  (s3/c1)     C  (s3/c2) -16      S  (s7/c1)     F  (s7/c2) -19
    B  (s3/c3)     M  (s3/c4) -15      H  (s7/c3)     K  (s7/c4) -19
    A  (s6/c0)     D  (s6/c1) -14      K  (s7/c4)     ENT(s7/c5) -15
    c2 열의 키      없음

**같은 MUX 스텝에서 ADC 시퀀스의 바로 다음 채널로만 간다.** ADC0 이 c0→c1→c2, ADC1 이
c3→c4→c5 를 차례로 변환하는데, c2 는 ADC0 의 마지막이라 번질 곳이 없다. MUX 주소는 스텝 안에서
안 바뀌므로 세틀링과는 무관하다 — `keys settle` 을 16 → 64 로 올려도 그대로였다.

행이 이웃한 같은 열 키는 반대로 **+10~20 커진다** (X → Z +15, J → H +20). 물리적으로 바로 옆이라
누른 키 자석의 옆으로 퍼진 자기장이 닿는 것이다. 자석 옆쪽에서는 수직 성분이 축과 반대라
**떼는 쪽**으로 읽힌다 — 오입력 쪽이 아니다. 비율은 거리로 정해지고 센서 감도와는 무관하다
(감도가 오르면 자기 신호와 옆 영향이 같은 배율로 오른다).

### 샘플 시간을 쓸어 봤다

`keys sample <n>` 으로 굽지 않고 바꾼다. S 를 누른 채, 같은 값으로 손 뗀 기준과 비교했다.

    샘플(클럭)   F 로 번짐   스캔 1회   잡음 p-p (평균/최대)
      5          -19.3       21 us      18 / 25
      8          -15.0
     12          -11.0
     16           -4.3       27 us      18 / 24
     24           -2.5       31 us      17 / 21
     32           +2.0       36 us
     48           +4.2       44 us

**시간을 주면 빠진다** — 샘플 커패시터가 앞 채널 전압을 품고 다음 채널에 붙는 것이다. 16 이면
잡음 밑으로 들어가고 스캔은 +6us 다. 옆 자석의 +값(A +6, W +7, E +4)은 어느 값에서도 그대로였다
— 전기가 아니라는 확인이다. 잡음은 늘지 않았다.

**16 으로 넣었다** (config.h `HW_KEYS_SAMPLE_CYCLES`, wish40 만 — 다른 보드는 기본 5). 굽기 전후:

                      전 (5)              후 (16)
    keysUpdate       21us  45,800회/초    27us  36,800회/초
    keyboard_task    avg 2 · max 15us     avg 2 · max 6us
    125us 초과        0                    0

### 원인은 센서 출력의 820pF 로 보인다

회로는 센서 OUT 에 820pF (C40 …), MUX 를 지나 ADC 핀 앞에 100Ω 직렬, 핀에는 커패시터가 없다.
센서 데이터시트(SBASAI5E)는 OUT 부하를 **최대 1nF** 로 두고, DC 출력 저항이 1.27Ω, 잡음 규격은
**100pF** 부하에서 쟀다.

- **820pF 는 잡음을 걸러 주지 않는다.** 출력 저항 1.27Ω 과의 차단 주파수가 100MHz 대라 센서
  대역폭(15kHz) 훨씬 위다. 필터가 되려면 앞에 저항이 있어야 한다
- 하는 일은 저수지다 — 샘플 커패시터가 붙는 순간의 오차를 "샘플 C ÷ 820pF" 로 줄인다
- 대신 그 오차를 센서 증폭기가 820pF 를 통째로 다시 채우며 되돌려야 해서 **회복이 느리다**.
  한계 1nF 의 82% 다

샘플 C 를 약 12pF, 증폭기의 순간 출력 임피던스를 약 200Ω 으로 두면 실측과 맞는다 — 오차 약 1.5%
에서 시작해 160ns(= 200Ω x 820pF) 시간 상수로 빠진다. 5 → 0.73%(실측 0.73), 8 → 0.49%(0.57),
16 → 0.16%(0.16). **두 값은 측정에 맞춘 것이라 맞는다고 확인된 것은 아니다.**

**100Ω 은 거의 상관없다.** 커패시터 뒤에 있어 샘플 C 와의 시간 상수가 수 ns 다. 핀 보호와
링잉 억제 몫으로 그대로 둔다.

### 다음 판 — 센서 출력 커패시터를 100pF 로 (재 보고 정한다)

같은 모델로 샘플 5 에서의 번짐을 셈하면 820pF 0.73% · 220pF 약 0.4% · **100pF 약 0.04%** 다.
100pF 는 데이터시트가 특성을 잰 조건이고, 잡음을 걸러 주던 것이 아니니 줄여서 잃을 것이 없다.
그러면 샘플 시간을 늘릴 필요가 없어 스캔 6us 를 아낀다.

★ 예측은 증폭기를 200Ω 저항으로 본 것이다. 부하가 작아지면 대역폭·슬루에 묶이거나 흔들릴 수
  있다. **판을 뜨기 전에 두 번째 보드에서 잰다.**

시험 방법:

- ★ **바꿀 커패시터는 번지는 쪽 키의 것이다.** 다음 채널을 샘플할 때 앞 채널 전하가 그 채널 센서의
  노드로 쏟아지므로 그 노드의 커패시터가 결과를 정한다. S 를 누르면 F 가 번지니 F 센서의 것을 바꾼다
- 같은 스텝 줄에서 c1·c2·c4·c5 중 몇 키를 골라 820pF(기준) · 220pF · 100pF · 떼어 냄으로 나눈다
- 각각 앞 채널 키를 누른 채 샘플 5 와 16 에서 잰다. 바꾼 키의 `keys noise` 도 같이 본다
