# 18. 키를 누르고 글자가 나오기까지

성능 지표에 한 칸이 비어 있었다.

지금 재는 것은 전부 **"한 바퀴가 얼마나 걸리나"** 다 — 스캔 시간(`keys time`), 태스크
시간(`qmk info`), 루프 간격. 그런데 사용자가 느끼는 것은 **"키를 누른 순간부터 글자가
나올 때까지"** 이고, 그건 여러 단계가 이어 붙은 값이라 **어느 지표에도 안 나온다.**

재기 시작했더니 절반이 엉뚱한 데서 새고 있었다. 고치고 나니 **판정에서 도착까지가
260us 에서 97us** 가 됐다.

---

## 다섯 시점에 도장을 찍는다

```
T0   keysInject()            주입값이 파이프라인에 들어간 순간
T1   keysTrack()             pressed 비트가 뒤집힌 순간          ← "키로 인식했다"
T1a  qmkUpdate 진입
T1c  matrix_scan 진입
T1d  matrix_scan 반환
T1e  process_record_kb       키코드까지 풀린 순간
T1b  usbd_ep_start_write 직전  리포트를 엔드포인트에 얹은 순간
T2   USB IN 완료 콜백        호스트가 가져가고 ACK 한 순간       ← 측정의 끝
T3   usbd_hid_set_report     OS 가 LED 상태를 되돌려 준 순간
```

구간 —

| 눈금 | 무엇 |
|---|---|
| ① T0→T1 | 스캔 + 3탭 이동합이 문턱을 넘을 때까지 |
| 루프 대기 T1→T1a | 판정 뒤 스캔의 **남은 스텝** |
| ② T1c→T1d | 키변환 — 판정 비트를 매트릭스로 |
| ③ T1d→T1b | 키처리 — 키맵·레이어·SOCD·연타 + 리포트 만들기 |
| ④ T1b→T2 | 호스트가 가지러 올 때까지 (폴링) |
| ⑤ T2→T3 | OS 왕복 (락 키에서만) |

### ★ 왜 ACK 를 끝으로 잡나

USB 인터럽트 전송은 호스트가 ACK 를 보내야 **완료 인터럽트가 뜬다.** 그래서 `T2` 가
곧 "호스트가 실제로 받았다" 다. 장치가 알 수 있는 가장 늦은 자리이자, 가장 정직한
자리다.

### ★ 시작점이 둘이라는 것을 분명히 해 둔다

`T1`(판정) 은 **스캔이 키를 알아본 시점**이고, `T0`(주입) 은 **값이 바뀐 시점**이다.
둘의 차가 ① 이고 50us 쯤 된다. 어느 눈금으로 말하느냐에 따라 답이 두 배 가까이
달라지므로 **숫자를 적을 때 반드시 어느 쪽인지 같이 적는다.**

---

## 두드리기를 장치 안에 둔다

`keys lat run <n> [ms]` — 장치가 스스로 눌렀다 뗀다.

### ★ CLI 로 재면 CLI 자신이 측정 창에 들어간다

처음에는 `keys inject ... d 150` 을 CLI 로 한 번씩 쏘며 쟀다. 키처리가 **249us** 로
나왔다. 장치가 두드리게 하니 같은 자리가 **108us** 였다. 차이는 CLI 의 CDC 출력이
측정 창 안에 들어앉은 것이었다.

**재는 도구가 측정 대상 안에 있으면 안 된다.**

### ★ 간격을 매번 새로 뽑는다

고정 5ms 로 두드리고 있었는데, **5ms 는 125us 의 정확히 40배**다. 매번 같은 위상에서
누르게 되어 폴링 대기가 한 값에 묶인다.

평균의 0.5~1.5배 사이에서 us 단위로 뽑도록 바꾸니 —

```
고정 간격   가장 느릴 때 164us
무작위      가장 느릴 때 224us      <- 가끔 폴링을 한 번 통째로 건너뛴다
```

고정 간격으로만 쟀으면 **"그런 일 없다" 고 적을 뻔했다.**

## 표본을 하나씩 남긴다

`keys lat dump` 가 400개를 그대로 내놓는다 (`n filt wait conv act proc bus`).

★ **min/avg/max 로는 모양이 안 보인다.** 폴링 대기가 균등분포인지 어딘가 뭉치는지,
드물게 튀는 것이 있는지는 흩뿌려 봐야 안다. 표준편차도 여기서 나온다.

### 잰 것 — 400 표본, 간격 무작위

| 구간 | 최소 | 평균 | 흔들림(σ) | 절반 | 20중 19 | 최대 |
|---|---|---|---|---|---|---|
| ① 스캔 + 누적 | 34 | 51 | 16 | 53 | 67 | 85 |
| 루프 대기 | 20 | 21 | 0.4 | 21 | 22 | 22 |
| ② 키변환 | 2 | 2 | 0.3 | 2 | 3 | 3 |
| ③ 키코드까지 | 2 | 4 | 1.3 | 5 | 6 | 6 |
| ③ 훅 + 리포트 | 4 | 5 | 0.7 | 5 | 6 | 10 |
| ④ 폴링 → ACK | 6 | 65 | 35 | 61 | 122 | 131 |
| **= 판정 → ACK** | **38** | **97** | **35** | 93 | 154 | 163 |
| 주입 → ACK | 74 | 148 | 40 | 148 | 217 | 228 |

### ★ 폴링 대기는 우리가 느린 게 아니다 — 숫자가 그렇게 말한다

인터럽트 전송은 호스트가 물어봐야 나간다. 우리는 얹어 놓고 기다릴 뿐이고, 키가 언제
눌릴지는 폴링과 무관하므로 **대기는 0~125us 에 고르게 흩어진다.**

```
균등분포 0~125us 의 이론 흔들림   125 / √12 = 36.1 us
폴링 구간의 실측                            35~39 us
```

히스토그램도 종 모양이 아니라 **평평한 판**이다. 8kHz 가 USB 2.0 고속의 하한이라
**여기가 바닥값**이다.

---

## ★ 키처리가 108us 였다 — 명령어를 가져오는 시간이었다

400MHz 에서 108us 는 **43,000 사이클**이다. 키맵 한 번 찾고 리포트 32바이트 만드는
일에 그만큼 들 리가 없다.

### 가려낸 방법

같은 키를 **짧은 간격으로 이어 두드리면** 캐시에 남아 있다. 최소값을 보면 갈린다 —

```
간격 500ms   키코드까지 30us   훅+리포트 54us
간격   1ms   키코드까지 15us   훅+리포트 20us
```

키 처리 경로는 **드물게 돈다.** 스캔은 26us 마다 돌아 캐시에 눌러앉지만, 키를 누르는
것은 수십 ms 에 한 번이라 그때마다 캐시 밖이고 **매번 XIP QSPI 에서 수백 줄을 다시
읽는다.**

### ★ 처음에는 "캐시 아니다" 로 기각했다 — avg 만 봤기 때문이다

5ms 와 200ms 를 견주고 평균이 같길래 접었다. **5ms 면 이미 다 밀려나 있어서 둘 다
식은 값**이었다. 최소값을 보고서야 갈렸다.

**평균은 뭉갠다. 갈라지는 것은 최소값에서 먼저 보인다.**

---

## 오브젝트 단위로 ILM 에 올린다

ILM 은 코어에 붙어 있어 캐시도 XIP 도 안 탄다. 128KB 중 3KB 만 쓰고 있었다.

```
.text   *(EXCLUDE_FILE(*/qmk/*.obj */keyboards/*.obj */src/hw/*.obj) .text)
        *(EXCLUDE_FILE(...) .text*)

.fast   */qmk/*.obj(.text .text*)
        */keyboards/*.obj(.text .text*)
        */src/hw/*.obj(.text .text*)
```

### ★ 함수마다 `ATTR_RAMFUNC` 을 붙이지 않는다

상류 QMK 소스를 고치는 것이라 갱신할 때마다 다시 붙여야 하고, 어느 함수가 경로에
있는지도 늘 바뀐다. **오브젝트 단위로 옮기면 소스를 한 줄도 안 건드린다.**

### ★ `.text` 쪽에서 걸러야 한다

`ld` 는 스크립트 순서대로 **처음 맞는 출력 섹션**에 넣는다. `.text` 가 `.fast` 보다
앞에 있으므로 `EXCLUDE_FILE` 로 안 걸러 두면 `.text` 가 먼저 집어간다.

### ★ 부팅 코드는 넣으면 안 된다

`.fast` 를 복사하는 쪽이 `.fast` 안에 있으면 **자기를 복사하기 전에 실행된다.**
`src/bsp` 는 그대로 둔다.

### 결과

| | XIP | ILM |
|---|---|---|
| 키코드까지 | 56 us | **4 us** |
| 훅 + 리포트 | 68 us | **5 us** |
| 스캔 (실제 루프) | 31 us | **26 us** |
| **판정 → ACK** | **260 us** | **97 us** |

```
FLASH  159,604 -> 81,084 B     ILM  3,288 -> 86,608 B (66%)
이미지 159,176 -> 167,912 B     DLM  변화 없음
```

★ **스캔도 같이 빨라졌다.** QMK 코드가 스캔 코드를 캐시에서 밀어내고 있었다 —
12편에 적어 둔 "같은 코드가 문맥에 따라 두 배 느렸다" 가 여기서도 나온 것이다.

★ **ILM 이 66% 찼다.** 앞으로 코드가 늘면 넘칠 수 있으니 **빌드 로그의 ILM 줄을 봐야
한다.** 넘치면 링커가 잡아 주지만, 그때 무엇을 뺄지 정해 둔 것이 없다.

★ 덤으로 **USB 드라이버가 ILM 에 올라갔다** — 플래시를 쓰는 동안에도 인터럽트를 열어
둘 수 있는 전제 조건이 갖춰졌다 (C9). cherryusb·SDK 31KB 는 아직 플래시다.

## 겪은 함정

### 재는 도구가 세 번 거짓말했다

| 무엇 | 어떻게 드러났나 |
|---|---|
| `qmk reset` 이 새 카운터를 안 지웠다 | 값이 늘 `668,991us` 로 같았다 |
| `keysLatClear()` 가 기록 버퍼를 안 비웠다 | RGB 끔/켬 두 조건이 **소수점까지 똑같이** 나왔다 |
| 시험이 만든 타임아웃 카운터가 남았다 | 다음 실행이 "ADC 가 죽었다" 로 오판 (17편) |

★ **셋 다 원인이 같다 — 지우는 자리가 두 곳이었다.** 목록을 두 곳에 두면 새 항목이
한쪽에만 들어간다. 지우는 함수는 하나여야 하고, 다른 곳은 그것을 부르기만 해야 한다.

★ 하마터면 **"왕복이 루프를 669ms 멎게 한다"** 고 적을 뻔했다. 실제로는 굽고 부팅하며
생긴 값이 안 지워지고 있었을 뿐이다.

### 시험 키는 이름이 아니라 HID usage 로 따진다

17편에 "F13~F15 는 macOS 에서 화면 밝기·스크린샷이라 쓰지 말 것" 이라 적어 뒀는데,
**`Scroll Lock`(HID usage `0x47`)이 macOS 에서 F14 = 화면 밝기 낮추기**였다. 이름이
달라서 같은 키인 줄 모르고 여섯 번 눌러 화면이 어두워졌다.

**"무해한 키" 목록은 이름이 아니라 usage 번호로 적어 둔다.**

### LED 왕복(⑤)은 아직 못 믿는다

락 키를 누르면 OS 가 LED 상태를 되돌려 준다 — 그 시각이 **"OS 가 실제로 인식했다" 는
유일한 도장**이다. 장치는 버스에 실었다는 것까지만 알고, macOS 는 키보드 HID 를 안
열어 줘서 호스트 쪽에서 잴 수도 없다.

그런데 지금 숫자는 27ms~2.8s 로 못 쓴다. **뗌이 다음 눌림 상태를 덮어써 짝이 어긋난다.**
아이디어는 유효하니 상태기계를 고칠 때 다시 본다.

## RGB 를 켜면 느려지나 — 안 느려진다

| 조건 | 평균 | 흔들림 | 최대 | RGB 몫 (평균/최대) |
|---|---|---|---|---|
| RGB 끔 | 98.3 | 36.8 | 164 | 1 / 3 us |
| 솔리드 (한 색) | 99.3 | 36.5 | 164 | 1 / 4 us |
| 패턴 (깊이 파문) | 97.4 | 35.1 | 163 | **5 / 38 us** |

효과가 무거워져 RGB 가 쓰는 시간은 다섯 배가 됐는데 키 지연은 **1~2us 안에서 그대로**다
— 흔들림 폭 35us 에 묻히는 크기다.

★ **순서 때문이다.** 리포트는 매트릭스를 훑는 자리에서 이미 엔드포인트에 얹히고,
RGB 는 그 **뒤에** 돈다. 다음 스캔을 조금 늦출 수는 있어도 이번 키를 늦추지는 못한다.

## 남은 것

| | 값 | 성격 |
|---|---|---|
| ④ 폴링 → ACK | 65 us | **물리적 바닥** — 8kHz 의 절반. 못 줄인다 |
| ① 스캔 + 누적 | 51 us | 그중 **군지연 28us** 가 줄일 자리다 (아래) |
| 루프 대기 | 21 us | 판정 뒤 스캔의 남은 스텝. 구조를 바꿔야 하고 비싸다 |
| ③ 키처리 | 9 us | 이미 바닥 |

### ★ 군지연 28us — 가장 값진 자리

3탭 이동합을 **스캔 세 바퀴에 걸쳐** 더한다. 그래서 판정에 쓰는 값의 나이가
`군지연 1샘플(28us) + 스캔 반 바퀴(14us) = 42us` 다.

같은 표본 수를 **한 스텝 안에서 두 번** 재도록 바꾸면(시퀀스 4 → 8) 두 표본이 붙어
있어 **군지연이 0 이 된다.** 표본 처리량은 그대로고 잡음 이득도 그대로다.

★ 계단 주입은 최악을 잰다. 진짜 타건은 손가락이 연속으로 내려와 이동합이 계속 따라
가므로 ①의 실제 지연은 **42us** 쪽이다 (실측 51us 는 계단 입력 값).

## 도구

```
keys lat                     구간별 최소·평균·최대
keys lat run <n> [ms]        장치가 스스로 두드린다 (간격은 매번 새로 뽑는다)
keys lat dump                표본 하나씩 (n filt wait conv act proc bus)
keys lat clear
qmk info 의 `루프 한 바퀴`     루프가 통째로 멎은 최대 시간
```

★ `keys lat run` 은 `keys inject live on` 이 있어야 리포트가 나간다. 시험 셀은
`s0/ch0` 이고 **거기 키코드를 무해한 것으로 바꿔 두고 되돌려야 한다.**

★ 표본 400개가 차면 기록이 멈춘다. 순환시키면 "몇 번째 표본" 이라는 축이 흐려진다 —
지우고, 정한 횟수만큼 두드리고, 읽는다.
