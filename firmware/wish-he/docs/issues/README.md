# 이슈 분석

올라온 이슈를 하나씩 뜯어 둔다. 편(篇)은 **펌웨어가 어떻게 도는지**를 적고, 여기는
**한 사용자가 무엇을 봤고 어느 줄을 고쳐야 하는지**를 적는다.

변경 이력이 아니다. 신고가 들어오면 파일을 하나 열고, 고친 뒤에도 그 판단 과정을
그대로 남긴다.

## 목록

| # | 내용 | 신고 | 상태 | 자리 |
|---|---|---|---|---|
| [001](001-calibration-key-leak.md) | 보정 중에 키가 호스트로 입력된다 | 2026-08-30 | 분석 끝, 미수정 | 리포트 문지기, `keys.c` |
| [002](002-rapid-trigger-ghost-input.md) | 입력지점 위에서 1~3ms 짜리 유령 입력 | 2026-08-31 | 분석 끝, 결정 하나 남음 | `keysTrack()`, `keys.c` |

상태는 `분석 끝, 미수정` · `결정 대기` · `수정안 있음` · `고침 (<버전>)` ·
`재현 안 됨` · `의도된 동작` 중 하나로 적는다.

## 새로 더할 때

1. [TEMPLATE.md](TEMPLATE.md) 를 `<nnn>-<slug>.md` 로 복사한다. `<nnn>` 은 **GitHub
   이슈 번호**를 세 자리로 채운 것이다 — 파일과 이슈가 갈라질 수 없다. 이슈 없이
   시험에서 나온 것은 `900` 부터 센다.
2. **코드를 만지기 전에** 채운다. 검토를 받는 것은 분석이고 패치는 거기서 나온다.
3. 위 표에 줄을 더하고 상태를 최신으로 둔다. **색인은 여기 하나뿐이다** — 두 곳에
   두면 반드시 갈라진다.
4. 그림은 `images/<nnn>-<이름>.svg` 로 손으로 쓴다. 빌드 단계를 두지 않는다.
5. 고침이 끝나면 **왜 그랬는지는 그 코드를 가진 편**에 쓴다 (래피드 트리거 →
   [../13-rapid-trigger.md](../13-rapid-trigger.md), 보정·저장 →
   [../08-storage.md](../08-storage.md)). 이 파일은 신고 기록으로 남긴다. 두 곳,
   두 역할이다.

★ 파일과 폴더 이름만 영문으로 둔다. 도구와 링크가 걸리는 자리라 그렇고, 내용은
  다른 문서와 같이 한글로 쓴다.

## 다른 세션에서 이어받기

대화 맥락은 압축되면 사라진다. **이 폴더가 이슈 작업의 인계 지점이다.**

새 세션을 열었으면 순서는 이렇다.

1. 위 표에서 상태가 `고침` 이 아닌 줄을 고른다.
2. 그 파일의 **"다른 세션에서 집을 수 있는 것"** 절만 읽는다. 하드웨어가 있어야
   하는 일과 없어도 되는 일이 갈라져 있다.
3. 하나를 집었으면 그 자리에 `(진행 중 — <세션>)` 을 적어 두고 시작한다.
4. 끝나면 그 줄을 지우고, 알아낸 것을 같은 파일에 남긴다. **못 되는 길을 적어 두는
   것이 되는 길만큼 값지다.**

★ **두 세션이 같은 파일을 동시에 고치지 않게** 이슈 단위로 나눈다. 001 과 002 는
  건드리는 코드가 겹치지 않는다 (`keysIsReportEnabled()` vs `keysTrack()`) — 같이
  가도 된다. 한 이슈 안에서 A 와 B 처럼 갈라진 것은 **A 를 먼저 끝내고 B 를 잡는다.**

## 규칙

- **잰 것과 읽은 것을 갈라 적는다.** 문장마다 표시한다 — 장치로 잰 것인지, 코드에서
  읽은 것인지. 짐작은 짐작이라고 적는다.
- **시험에 안 들어간 재현 절차는 반드시 되돌아온다.** `tools/he_test.py` 에 같이
  넣는다. 아직 안 고친 것은 `xfail` 로 둬서 검사 전체가 늘 초록이게 한다.
- **코드는 파일과 줄로 인용한다** (`src/hw/driver/keys.c:2642`). 줄 번호는 움직이니
  어느 커밋에서 읽은 것인지도 같이 적는다.
- **보고자의 보드는 제조사·제품명을 쓰지 않는다.** "61키 HE 보드, 펌웨어 `<버전>`"
  까지만 적는다. 다른 문서와 같은 규칙이다.
- 오류 표기는 `[E_]` 로 한다.
