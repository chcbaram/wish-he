# 14. LED 전류 리미터

> 전체 목차는 [README.md](README.md) 를 본다.

83개를 흰색으로 켜면 USB 예산의 여러 배를 요구한다. 시험 중 실제로 USB 가 끊겼고,
그래서 효과를 얹기 전에 먼저 막았다.

## 한 것

- 프레임 전체를 합산해 상한을 넘으면 전 채널을 같은 비율로 줄인다
- 색 원본을 따로 들고, 비트패턴으로 펼치는 일을 `Refresh` 로 옮겼다
- 두 무리(키 LED · 언더글로우)에 우선순위를 줄 수 있게 했다
- 리미터가 걸린 횟수를 센다 — **평상시 0 이어야 한다**
- **USB 전류계로 모델을 실측했다.** 짐작했던 세 가지가 전부 틀렸다

```
cli# ws2812 info
limit        : 450 mA  (idle 269 mA)
ch full      : 위 11.51 mA / 언더 4.66 mA  (채널 255 일 때)
frame current: 449 mA   <- 제한됨
  키          :   0 mA
  언더글로우   : 180 mA
  제한 없었다면 : 520 mA
```

---

## ★ 짐작한 세 가지가 전부 틀렸다

모델은 이런 모양이다.

```
보드 전류 = 고정분 + Σ(무리별 채널 값의 합 × 무리별 채널 전류 / 255)
```

처음 채운 값은 전부 데이터시트와 개수 세기에서 나왔다. 전류계를 대 보니 **셋 다**
틀렸다.

| | 짐작 | 실측 |
|---|---|---|
| 고정분 | 83 mA (LED 칩 83 × 1mA) | **269 mA** |
| 무리 경계 | 63 (키가 63개니까) | **65** |
| 채널 전류 | 20 mA, 하나의 값 | **위 11.51 / 언더 4.66**, 둘 |

### 고정분 — 세는 대상이 틀렸다

LED 를 전부 끈 상태가 이미 269mA 다. 홀센서 64개는 멀티플렉서로 골라 읽을 뿐 모두
상시 켜져 있어 그것만 150mA 근처다.

숫자가 3배 틀린 것보다 **뜻이 틀린 게 문제였다.** 고정분을 LED 몫만으로 세면 상한도
"LED 몫의 상한"이 되어 USB 예산 500mA 와 이어지지 않는다. 실측값으로 두면 상한이 곧
**USB 가 끌어가는 전체 전류**가 되어 전류계로 그대로 검증된다.

### 경계 — 개수로 짐작했다

`63~82` 를 켰더니 **그중 둘이 위에서 켜졌다.** 63·64 만 빨강, 65~82 를 파랑으로
켜 보고서야 갈렸다.

```
  위쪽        0 ~ 64   (65개)
  언더글로우  65 ~ 82  (18개)
```

### 65 라는 수가 맞아떨어진다

```
  스위치 자리 63  +  스페이스바 스위치 좌우 2  =  65
```

배치([layout.h](../keyboards/wish60-he-7u/layout.h) `keys_geo[]`)의 1행이 16개인데
뒤 2개가 `x = 15.5, 16.5` 로 **판 밖**에 그려져 있다. 스플릿 백스페이스용 대체
자리다. 그리고 그 둘(`3,5`·`1,5`)이 **보정에서 빠진 3개 중 둘과 정확히 일치한다**
(나머지 `0,6` 은 미사용). 이 보드는 2u 백스페이스가 꽂혀 있어 스위치는 비었지만
LED 자리는 살아 있다.

7u 스페이스바는 길어서 하나로 고르게 못 비추므로 스위치 좌우로 하나씩 더 있다.
**"키가 63개니 LED 도 63개"로 넘어간 것이 짐작이었다** — 한 키에 LED 하나라는 전제가
깨지는 자리가 이 보드에 둘 있다. 비어 있는 스위치에도 LED 가 있고, 한 스위치에
LED 가 셋인 키도 있다.

### 채널 전류 — 값이 아니라 개수가 틀렸다

이게 셋 중 제일 컸다. 언더글로우만 켜고 재니 계산의 **절반**이 나왔다. 두 무리가
서로 다른 LED 였다.

```
  위쪽        11.51 mA / 채널
  언더글로우   4.66 mA / 채널      2.5 배 차이
```

하나의 기울기로 세면 언더글로우를 2.5배 과대평가한다. 그래서 언더글로우만 켰을 때
**예산의 3분의 1만 쓰면서 다 쓴 줄 알고 있었다** — 계기는 320mA 인데 리미터는
450mA 라고 믿고 밝기를 깎았다.

> 처음에는 이 값을 계산으로 빼내려 했다. 전체 측정에서 위쪽 몫을 빼면 될 것 같았지만
> **큰 수의 차라 못 쓴다** — 세 번의 간접 추정이 3.70 / 4.68 / 5.06 으로 흩어졌다.
> ±2mA 오차가 18개짜리 작은 무리에서 그대로 증폭된다. 직접 재야 했다.

### 재단은 전류로 한다

무리마다 채널당 전류가 다르면 "채널 값의 합"은 더 이상 공통 화폐가 아니다 —
언더글로우 1000 과 위쪽 1000 은 같은 무게가 아니다. 예산도 배분도 uA 로 셈한다.

4.66mA 를 정수 mA 로 반올림하면 7% 가 날아가므로 상수도 uA 로 둔다.

### 다섯 점이 ±4mA 안에 든다

```
                          합     실측    모델
  전체 v=12              2988    384     386
  전체 v=24              5976    504     504
  위쪽 65개 v=20         3900    445     445
  언더글로우 18개 v=160   8640    427     426
  63~82 v=38             2280    320     316   <- 두 무리가 섞인 경우
  언더글로우 흰255 (제한) —       450     449
```

마지막 줄 전의 `63~82` 가 처음의 이상 현상이었다. **위쪽 2개가 섞여 있었다는 것과
두 LED 의 전류가 다르다는 것이 둘 다 맞아야만** 설명된다.

## 펼치는 자리를 옮겼다

프레임버퍼는 비트패턴이라(0 → `0xE0`, 1 → `0xFC`) **되읽어 합산할 수 없다.**
리미터가 볼 원본이 필요해 `rgb_buf[83][3]` 을 두고, `ws2812SetColor()` 는 거기에만
쓰고, 펼치기는 `ws2812Refresh()` 에서 한다.

```
  전   SetColor()  83번 x 24바이트 펼치기
  후   Refresh()   합산 + 나눗셈 + 83번 x 24바이트 펼치기
```

총량은 같다. 새로 드는 것은 합산과 나눗셈뿐으로 **프레임당 2~3us** 다. 덤이 하나
있는데, QMK 의 `rgb_matrix_set_color()` 는 플러시 한 번당 같은 LED 를 여러 번 쓸 수
있다. 예전 구조라면 그때마다 24바이트를 펼쳤고, 지금은 플러시당 정확히 한 번이다.

### 배율은 Q16 이어야 한다

83개를 흰색으로 켜면 배율이 7% 근처까지 내려간다. 그 언저리에서 Q8 눈금(0.4%)은
큰 오차가 된다. 줄이는 쪽 오차라 안전은 하지만 **색이 틀어진다** — R·G·B 가 각각
다른 비율로 잘려 흰색이 흰색으로 안 나온다. Q16 이면 눈금이 0.0015% 라 사라진다.

## 두 무리

합산이라 한쪽을 끄면 그 몫이 자동으로 다른 쪽으로 넘어간다. 그건 공짜다.

```
  전부 흰색 255      위 18   언더글로우 18
  위쪽만 흰색 255    위 20
  언더글로우만 255           언더글로우 183   <- 위쪽을 끈 몫이 넘어온다
```

공짜가 아닌 건 반대 방향이다.

```
  shared      위쪽만 켬 20  ->  언더글로우도 켜면 18   어두워진다
  key-first   위쪽만 켬 20  ->  언더글로우도 켜면 20   그대로
```

각인을 비추는 건 기능이고 언더글로우는 장식인데, 장식을 켰다고 각인이 어두워지는 건
곤란하다. `key-first` 는 위쪽부터 예산을 채우고 **남은 것**을 언더글로우에 준다.
어느 쪽이든 합계는 같은 상한 안에 있다 — 순서만 정한다.

---

## ★ 전역 배율에는 고유한 결함이 있다

켜진 개수가 변하면 **이미 켜져 있던 LED 의 밝기까지 같이 변한다.** 반응형 입력
효과라면 한 키만 눌렀을 때 밝던 LED 가 열 키를 누르면 어두워진다. 타이핑하는 내내
전체가 숨쉬듯 출렁인다. 무지개처럼 합이 오르내리는 효과도 펌핑이 보인다.

기울기 제한으로 덜 튀게 할 수는 있지만 의존성 자체는 남고, 더 나쁘게는 **안전 반응이
느려진다.** 전류가 튀는데 배율이 천천히 내려가면 리미터를 둔 이유가 없어진다.

### 층을 나눈다

```
  밝기 상한    효과가 쓸 수 있는 최대값. 전부 켜도 예산에 들어가도록 미리 정한다
               -> 개수가 변해도 배율이 안 변하니 출렁임이 없다
  합산 리미터  그 아래 깔린 안전망. 평상시 걸리지 않아야 한다
               -> 걸린다면 효과 쪽이 예산을 넘긴 것이다
```

리미터의 일은 브라운아웃을 막는 것이지 보기 좋게 만드는 게 아니다. 보기 좋게 만드는
것은 밝기 상한의 일이고, QMK 에서는 `RGB_MATRIX_MAXIMUM_BRIGHTNESS` 가 그것이다.

**상한 450mA 에서 그 값은 18이다.**

```
  v=18   445 mA   통과
  v=19   445 mA   <- 리미터 걸림
```

그래서 걸린 횟수를 센다. `ws2812 info` 의 `limit hit` 가 0 이 아니면 밝기 상한이
예산보다 높다는 뜻이고, 그 상태로 두면 출렁임이 보인다.

## 성능은 문제가 아니었다

WS2812 는 1비트가 1.25us 라 83개를 한 번 밀어내는 데만 2ms 가 걸린다. 물리적 최대가
476fps 고 실제 효과는 60~100fps 로 돈다.

```
   60 fps   33us x  60 =  2.0 ms/s   ->  CPU 0.2 %
  476 fps   33us x 476 = 15.7 ms/s   ->  CPU 1.6 %   (물리적 최대)
```

최대 프레임률로 돌려도 1.6% 다. 전송 2ms 는 DMA 가 하니 CPU 와 무관하다. 프레임을
내보내는 그 한 바퀴만 스캔 주기가 28 → 60us 로 늘어나는데, 초당 35,000 번 중 60 번이라
0.17% 이고 8kHz 예산(125us) 안이다.

정작 큰 쪽은 QMK 다 — LED 마다 효과 함수와 `hsv_to_rgb()` 가 돈다. 거기에는 손잡이가
이미 있다.

```
  RGB_MATRIX_LED_PROCESS_LIMIT   한 번에 처리할 LED 수. 기본이 전체의 1/5
  RGB_MATRIX_LED_FLUSH_LIMIT     플러시 간격. 기본 16ms (약 60fps)
```

`PROCESS_LIMIT` 때문에 플러시 시점의 프레임은 서로 다른 애니메이션 단계의 LED 가 섞인
상태인데, 어차피 그게 실제로 선을 타고 나가는 값이라 합산 대상으로 맞다.

## 배치는 표가 아니라 규칙이다

체인 순서를 실측으로 확정했다.

```
  상단 0~64     ESC 에서 오른쪽으로, 행마다 방향이 바뀌는 지그재그
                16 / 14 / 13 / 13 / 9  =  65
  언더 65~82    오른쪽 아래에서 왼쪽으로, 판 외곽을 한 바퀴 (18개)
```

검증은 색을 갈라 켜서 했다 — `0`=ESC, `16`=백슬래시(2행 오른쪽 끝), `30`=CapsLock
(3행 왼쪽 끝), `62·63·64`=오른쪽 Alt·Win·Ctrl, `59·60·61`=스페이스바 셋.
2행 오른쪽 끝이 16이라는 것 하나로 **지그재그와 1행이 16개라는 것이 동시에** 걸린다.

> 흰색으로 켜면 옆 키캡까지 번져 두 개로 보인다. 인접한 자리를 가릴 때는 **색을
> 달리해야** 한다. 켜진 개수는 `ws2812 info` 의 전류로 검산된다 — 3개 × 채널 60 이면
> 8mA 여야 하고, 남은 게 있으면 값이 오른다.

이 보드는 **"한 키에 LED 하나"가 두 군데서 깨진다.**

```
  7u 스페이스바      스위치 좌우로 하나씩 더 — 길어서 하나로는 고르게 못 비춘다
  스플릿 백스페이스   스위치는 안 꽂혔는데 LED 자리는 살아 있다
```

그래서 표로 박지 않고 [`tools/gen_keymap.py`](../tools/gen_keymap.py) 가 배치에서
계산해 `layout.h` 에 `keys_led[]` 로 내보낸다. 배치를 고치면 매핑도 따라간다.
`keys led` 를 돌리면 누른 키의 LED 가 켜지므로 규칙 전체를 한 번에 검증할 수 있다.

언더글로우는 배치 파일에 없는 정보라 눈으로 셌다 — **아래 6, 왼쪽 3, 위 6, 오른쪽 3.**

> 둘레를 통째로 균등 분할하면 안 된다. 짧은 변(5u)과 긴 변(15u)에 같은 간격을 주면
> 아래가 7개, 옆이 2개가 되어 실제와 어긋난다. 변마다 개수를 주고 그 안에서 나눈다.
> 한 변 안에서의 간격까지는 실측이 아니므로, 효과가 어색하면 `ws2812 walk 65` 로
> 짚어 고친다.

## ★ 전류계를 물린 채로는 키보드를 쓰면 안 된다

측정을 끝내고 전류계를 물린 채로 타이핑했더니 **백스페이스가 가끔 안 먹혔다.** 다른
키보드로는 멀쩡했다. 한참을 펌웨어에서 찾았다.

```
  센싱    51 회 중 에지 안 남 0 회,  되올라온 지점 매번 0
  리포트  53 회 눌림 전부 (0,5)=0x002A 로 생성
  전송    변화 106 개 / 완료 106 개,  차이 0
```

세 층을 다 재고 나서야 장치 밖으로 눈을 돌렸다. **전류계를 빼니 바로 정상이 됐다.**

이 장치가 유난히 민감한 이유가 있다. 우리는 `bInterval = 1`, 즉 **125us 폴링(8kHz)**
을 요구한다. 보통 키보드는 1ms 나 8ms 라 중간에 뭘 끼워도 여유가 있지만 8kHz 에는
여유가 없다. 전류계를 물렸을 때 VBUS 가 4.822V 로 내려앉아 있던 것이 이미 그 경로에
손실이 있다는 표시였는데 읽어내지 못했다.

> **계측 도구가 대상을 바꾼다.** 13편에서 "계측 지점을 바꾸면서 비교하면 안 된다"를
> 배웠는데, 이번엔 계측 도구를 **끼운 채로** 다른 것을 판단했다. 전류를 잴 때는
> 물리고, 동작을 볼 때는 뺀다.

전류 측정값 자체는 영향받지 않는다 — 느리게 변하는 값이라 신호 무결성과 무관하다.
위의 실측값들은 그대로 유효하다.

## 재는 도구를 먼저 만들었어야 했다

측정에 쓴 것은 CLI 명령 셋이다. 전부 **재다가 필요해져서** 만들었다.

```
  ws2812 range <from> <to> <r> <g> <b>   구간을 덧칠한다
  ws2812 walk [ms]                       하나씩 켜며 번호를 찍는다
  ws2812 group                           두 무리를 다른 색으로
```

`range` 는 처음에 앞서 켠 것을 지우게 짰다. 그랬더니 정작 경계를 가리려고 **두 구간을
다른 색으로 같이 켜려는 순간** 못 쓰게 됐다. `set` 과 같이 덧칠하는 뜻이어야 한다.

## 배운 것

| 짐작 | 실제 |
|---|---|
| 고정분은 LED 칩 몫이다 | 269mA. 홀센서 64개가 상시 켜져 있다 |
| 키가 63개이니 LED 도 63개 | 65개. 7u 스페이스바 밑에만 3개가 들어간다 |
| LED 는 한 종류다 | 두 종류. 채널 전류가 2.5배 다르다 |
| 작은 무리 값은 빼서 구하면 된다 | 큰 수의 차라 3.70~5.06 으로 흩어진다. 직접 재야 한다 |
| 끄면 밝아지게 하는 옵션이 필요하다 | 합산이라 이미 공짜다. 필요한 건 반대 방향 |
| 리미터가 밝기를 관리한다 | 리미터는 안전망이다. 밝기는 상한이 관리한다 |
| 배율은 Q8 이면 충분하다 | 낮은 배율에서 색이 틀어진다 |
| RGB 를 켜면 스캔이 느려진다 | 최대 프레임률로도 CPU 1.6% |
| 백스페이스가 가끔 빠지는 건 펌웨어 탓 | 물려 둔 USB 전류계 탓. 8kHz 폴링은 여유가 없다 |

전부 **재기 전에 정한 값**이었다. 전류계 하나를 대는 데 든 시간보다 그 위에 쌓은
계산을 되돌리는 데 든 시간이 길었다.
