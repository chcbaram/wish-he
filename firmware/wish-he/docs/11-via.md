# 11. VIA 붙이기

> 전체 목차는 [README.md](README.md) 를 본다.

키맵·레이어·매크로는 10편에서 QMK 를 얹어 해결한다. 이 편은 그 위에 붙는 설정 채널
— **VIA 표준 명령과, HE 에만 있는 확장**이다.

지금까지 들어간 것은 확장 쪽 절반이다. QMK 없이도 되는 것부터 먼저 만들었다.

| | 상태 |
|---|---|
| 명령 ID 를 VIA 안전 대역으로 재배치 | 완료 |
| 물리 배치 읽기 (`0xC2`) | 완료 |
| 라이브 트래킹 (`0xC3`) | 완료 |
| VIA 표준 (`quantum/via.c` + `dynamic_keymap`) | 10편 뒤 |
| EEPROM 백엔드 (`0x0C4000`, 논리 16KB) | 10편 뒤 |
| 웹앱 포크 | 마지막 |

---

## 명령 ID 를 먼저 옮겼다

처음에 잡은 `0x01 INFO` / `0x02 BOOT` / `0x03 RESET` 이 **VIA 와 정면으로 겹쳤다.**

```
0x01  id_get_protocol_version
0x02  id_get_keyboard_value
0x03  id_set_keyboard_value
```

QMK 의 `via.c` 를 얹는 순간 한 채널을 두 주인이 쓰게 된다. 도구와 펌웨어를 같이
고쳐야 하는 종류의 변경이라 **쓰는 사람이 우리뿐일 때** 옮겼다.

```
0x0B   부트로더 점프      VIA id_bootloader_jump 와 같은 자리
0xC0   보드 정보          ┐
0xC1   리셋               │ VIA 가 쓰지 않는 대역
0xC2   물리 배치 읽기     │
0xC3   라이브 트래킹      ┘
0xC4   (장치 -> 호스트)   트래킹 프레임 태그
```

부트로더 점프를 VIA 자리에 맞춘 것은 덤이 있다 — **표준 VIA 도구로도 진입시킬 수
있다.** 우리 확장은 VIA 가 안 쓰는 `0xC0` 대에 모았다.

## 물리 배치는 장치가 준다

`keys_geo[]` 가 키마다 `{x, y, w, h, row, col}` 6바이트(1/4 키유닛)로 이미 펌웨어
안에 있다. 그걸 그대로 내보낸다.

```
OUT  [0]=0xC2  [1]=시작 인덱스
IN   [0]=0xC2  [1]=상태  [2]=시작 인덱스  [3]=개수  [4..]= 6바이트 x 개수
```

전체 개수를 응답에 싣지 않는다. **끝을 넘겨 물으면 개수 0 이 온다** — 호스트는 0 이
올 때까지 인덱스를 늘리면 되고, 프로토콜에 길이 필드가 하나 줄어든다.

이걸로 웹 도구는 **JSON 파일 없이 장치만 보고** 배치를 그린다. 펌웨어의 레이아웃이
바뀌면 도구가 따라간다.

## 라이브 트래킹

상용 디버깅 화면처럼 키마다 눌린 깊이(mm)와 원시값을 실시간으로 본다. 이게 필요한
이유는 화면이 예뻐서가 아니라 **13편(래피드 트리거)의 튜닝 도구**이기 때문이다.
0.1mm 단위 방향 반전을 CLI 로는 못 본다.

### 상용은 요청-응답, 우리는 장치가 민다

상용 펌웨어의 설정 채널을 뜯어보면 키값 읽기가 **페이지 방식 요청-응답**이다.

```
OUT  [0]=0xD2  [1]=페이지
IN   [0]=0xD2  [1]=상태  [2..]= uint16 x 16 (빅엔디안)
```

64키면 왕복 4번이다. 왕복 한 번은 OUT 폴링 + IN 폴링이라 주기의 2배가 든다.

```
상용   64B 리포트, bInterval 2 (250us), 16키/응답
       -> 스냅샷 = 4왕복 x 500us = 2ms  (이론 500장/s)

우리   32B 리포트, bInterval 1 (125us), 7키/프레임
       -> 켜두면 계속 나온다. 왕복 없음
       -> 스냅샷 = 10프레임 x 125us = 1.25ms  (이론 800장/s)
```

대역폭은 양쪽 다 256 KB/s 로 같다. **차이는 왕복을 없앤 것뿐이다.**

### 프레임

```
[0] 태그 0xC4   [1] 첫 키 인덱스   [2] 이 프레임 키 수   [3] 전체 키 수
[4..] 키당 4바이트   원시값(LE16) + 깊이(LE16, bit15 = 눌림)
```

깊이는 0.01mm 단위라 400 을 넘지 않는다. **상위 비트가 남아서 거기에 눌림 판정을
실었다** — 호스트가 임계값을 몰라도 상용 화면처럼 체크 표시를 그릴 수 있다.

첫 키 인덱스를 달고 다니므로 프레임이 몇 개 빠져도 나머지가 제자리에 들어간다.
순서 맞추기용 상태를 호스트가 들 필요가 없다.

### 깊이의 영점은 저장값이 아니라 살아 있는 기준값이다

```c
d = base[row][col] - raw[row][col];          /* 영점 = 러닝 최대값 */
depth_um = d * travel_um / stroke_cnt;       /* 기울기만 보정에서 */
```

보정 당시의 `cal_max` 를 영점으로 쓰면 몇 시간 뒤 안 눌러도 0 이 아니게 된다.
`base` 는 러닝 최대값이라 온도·자세 드리프트를 계속 따라간다. 보정에서 가져오는 것은
**"몇 카운트가 전 행정인가"(기울기)뿐이다.**

보정하지 않은 키도 값이 나와야 하므로 스위치 종류표에 **공칭 카운트**를 넣었다.
근거는 8편의 실측이다 — 61키 보정에서 평균 836 카운트가 4.0mm 였다.

```c
{ "generic 4.0mm", 400, 836 },   /* travel_um, stroke_cnt */
```

### EP 를 새로 만들지 않았다

바꾼 것은 `HID_INTERVAL_HS` 를 4 에서 1 로 내린 것 하나다. **MPS 32 는 유지한다 —
VIA 규약이라 늘리면 호환이 깨진다.**

명령 응답과 트래킹 프레임이 EP `0x84` 를 나눠 쓴다. 중재는 `is_tx_busy` 하나고,
겹치면 **트래킹 프레임을 버린다.** 최신값이 중요하지 빠짐없이 가는 게 중요한 게
아니다.

> ★ **표준 VIA 도구와는 트래킹 중에 공존이 안 된다.** VIA 는 "명령 보내고 다음 IN
> 리포트가 응답"이라고 가정하는데, 그 사이에 `0xC4` 프레임이 끼면 짝이 어긋난다.
> 우리 포크는 태그로 거르면 되지만, 표준 도구를 같이 쓰려면 **스트리밍 전용
> 인터페이스로 갈라야 한다.** 상용이 IN 전용 인터페이스를 따로 둔 이유로 보인다.
> 지금 가르지 않는 것은 CDC 인터페이스 번호가 또 밀려서 7편의 등록 순서 함정을
> 다시 밟기 때문이다. VIA 를 얹을 때 같이 한다.

## 실측 — 상한이 7편과 같은 자리였다

```
$ python3 tools/he_track.py --rate
키 64개, 프레임당 7키, 배치 63자리, 전 행정 4.00mm
스냅샷 1724장 / 3.0s = 574/s
```

이론값 800 에 못 미친다. 그런데 프레임 수로 환산하면 답이 나온다.

```
574 스냅샷/s x 10프레임 = 5740 프레임/s
7편에서 잰 연속 전송 상한          5900/s
```

**같은 천장이다.** 파이썬도 대역폭도 아니고, 7편에서 확인한 완료 → 재프라임 왕복이
정하는 값이다. 12편에서 dTD 체이닝으로 이 상한을 올리면 **키보드 리포트와 트래킹이
같이 빨라진다.**

## 화면

```
$ python3 tools/he_track.py

  0.35   ·      ·      ·      ·      ...
```

숫자를 오른쪽 정렬로 깔고 왼쪽부터 깊이만큼 반전시킨다. 막대와 mm 값이 한 칸에
겹쳐서 칸을 더 쓰지 않는다. 눌림 판정이 서면 초록이다.

`--raw` 를 주면 원시값을 같은 배치로 본다. 상용 디버깅 화면도 mm 와 원시값을 같이
보여주는데, 배선이나 자석 문제를 볼 때는 원시값이 필요하기 때문이다.
