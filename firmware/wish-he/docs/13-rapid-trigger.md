# 13. 래피드 트리거

> 전체 목차는 [README.md](README.md) 를 본다.

키가 눌리는 **지점**이 아니라 **방향이 바뀐 거리**로 판정한다. 그러려면 0.1mm 를
믿을 수 있어야 하고, 판정 주기가 고와야 한다.

## 한 것

- ① 처리를 변환 대기 안으로 숨김 — 33 → 28us
- ② 3개 이동합 — 잡음 1.31배 개선 (이론 1.73)
- ③ 드리프트 걸음 크기를 눈금에 맞춤 (분산은 **안 했다**)
- ④ 래피드 트리거 + 바닥 보호 + 데드존, 설정을 전부 키별로

---

## ① 처리를 변환 대기 안으로

변환은 스텝당 2.96us 인데 그동안 CPU 는 회전만 했고, 다 기다린 뒤에야 0.93us 를
처리했다. 스텝 N 을 트리거해 놓고 그 대기 시간에 스텝 N-1 을 처리하면 처리 시간이
통째로 숨는다.

```
  전    [설정][변환 대기 2.96us      ][처리 0.93us]  x 8
  후    [설정][변환 2.96us | N-1 처리 ]              x 8
```

DMA 버퍼는 다음 트리거가 덮어쓰므로 결과를 8워드 떠 놓는다. 그 복사가 숨기는 시간보다
훨씬 싸다. **ADC 설정도 잡음도 건드리지 않는다 — 순서만 바꾼다.**

---

## ② 3개 이동합 — 이론에 못 미쳤고, 그것도 기록한다

표본 3개를 더하면 신호는 3배, 잡음은 √3 배가 된다. 눈금이 `0~4095` 에서 `0~12285` 로
넓어지고 개선분이 하위 비트에 남는다.

**평균이 아니라 합이다.** `sum/3` 으로 나누면 눈금이 12비트로 돌아가면서 개선분이
양자화에 묻힌다. 합으로 두면 유효 분해능이 12비트에서 약 13.6비트가 된다.

**블록이 아니라 이동합이다.** 3개를 모아 한 번씩 판정하면 판정 주기가 1/3 로
떨어진다. 스캔이 35kHz 라 최근 3개의 합을 매 스캔 갱신해도 부담이 없다.

```
  블록    [1 2 3] 판정   [4 5 6] 판정
  이동합  [1 2 3] 판정 / [2 3 4] 판정 / [3 4 5] 판정 ...
```

### 실측은 1.31배였다

```
  누적 1개   p-p 평균 17,  눈금 0~4095    스트로크 836  대비 2.03 %
  누적 3개   p-p 평균 39,  눈금 0~12285   스트로크 2508 대비 1.55 %
                                          개선 1.31 배 (이론 1.73)
```

생값 비율 39/17 = 2.29 는 연속 스캔 사이 **상관계수 0.45** 를 뜻한다. 센서 상관시간
10.6us 에 스캔 간격 28us 면 0.07 이어야 한다.

> ★ 처음에는 잡음이 **나빠진 줄** 알았다. 데드밴드를 7 → 12 로 같이 바꿔 놓고 필터
> 통과 후 p-p 를 비교했기 때문이다. **계측 지점을 바꾸면서 비교하면 안 된다.**
> 데드밴드 이전 값을 따로 재고 나서야 실제로는 좋아진 게 드러났다.

### 잔여분은 우리 탓인가

보드가 참고 보드와 같으니 잡음 바닥도 같아야 한다. 그러면 차이는 **펌웨어가 만드는
것**일 수 있어서, 가장 유력한 용의자인 LED 전류를 흔들어 봤다.

```
  LED 꺼짐              p-p 평균 39
  LED 백색 3% (~156mA)  p-p 평균 39
  LED 백색 6% (~312mA)  p-p 평균 39
```

꿈쩍하지 않는다. 전원 결합이 아니다. 남는 설명은 홀 센서의 **1/f 플리커 잡음**이다 —
백색 성분은 28us 간격 평균으로 지워지지만 1/f 는 상관시간이 길어 3샘플(84us) 창으로
안 지워진다. **누적을 5, 7 로 늘려도 비례해서 좋아지지 않는다.**

> 곁가지로 하나 나왔다 — **LED 전류 상한이 펌웨어에 없다.** 83개를 25% 백색으로 켜면
> 1.25A 로 USB 예산의 두 배가 넘어 브라운아웃된다. 시험 중 실제로 USB 가 끊겼다.

---

## ③ 드리프트 — 없는 문제를 고치지 않는다

[05편](05-adc-scan.md)에 "512ms 마다 64키를 한꺼번에 처리해서 그 스캔만 무거워져 주기가
튄다"고 적어 두었다. 재보니 그 전제가 틀렸다.

```
  드리프트를 매 스캔 돌렸을 때  keysUpdate = 28 us   (평소와 같다)
```

64셀 몇 개 비교와 증감은 28us 안에서 보이지도 않는다. 계측값도 이를 뒷받침한다 —
60us 초과가 45초에 30회인데 드리프트는 같은 기간에 88회 돈다.

**진짜 문제는 걸음 크기였다.** 누적으로 눈금이 3배가 됐는데 걸음이 1카운트 그대로면
물리적으로 3배 느려진다. `KEYS_DRIFT_STEP = KEYS_ACC_CNT` 로 되돌렸다.

> ★ 최대치 하나로는 아무것도 못 정한다. `keyboard_task max 308us` 를 보고 한참
> 구조를 의심했는데, **초과 횟수**를 세니 바로 갈렸다 — 153만 번 중 3회, 전부 부팅과
> CLI 조작 순간이었다. 최대치는 "3번"과 "5000번"을 구분해 주지 않는다.

## ④ 래피드 트리거

```
  눌린 동안   peak = 가장 깊었던 지점
              RT: peak - d >= 입력 해제 거리  ->  해제. 단 바닥 보호 구간에서는 끈다
              아니면 절대 해제지점

  떼진 동안   peak = 가장 얕았던 지점
              RT: d - peak >= 재입력 거리    ->  입력
              아니면 절대 입력지점 (그리고 여기서 RT 를 건다)
```

### 절대 입력지점이 끼어들면 안 된다

처음에는 둘을 `or` 로 묶었다. 그랬더니 키를 바닥까지 눌렀다 떼면 같은 글자가 쏟아졌다.

```
  ffffffffffffffffffffffffjjjjjjkkkkkkddddddssssssccccc
```

RT 가 깊은 곳(예: 2187 카운트)에서 해제를 내면 키는 떼진 상태인데 깊이는 아직
입력지점(627)보다 훨씬 깊다. **바로 다음 스캔에 절대 입력이 걸려 즉시 재입력되고**,
해제 → 입력 → 해제 가 손가락이 올라오는 내내 반복된다. 바닥까지 누르면 `peak` 이
최대라 그 구간이 가장 길어진다.

RT 가 걸린 동안에는 RT 만 판정하고, 절대 입력지점은 RT 를 처음 거는 데만 쓴다.

> 이 증상을 처음에 "0.30mm 가 예민해서"로 보고 값을 낮춰 가며 경계를 찾으라고 했다.
> 틀렸다 — 로직 버그라 값을 얼마로 두든 반복이 났다.

### 바닥 보호와 데드존은 다른 물건이다

```
  데드존      쉬는 위치(위) 근처. 진동·공차로 인한 우발적 입력을 막는다
  바닥 보호   바닥(아래) 근처. RT 해제를 끈다
```

바닥까지 눌러 붙잡으면 기준점이 바닥에 고정되는데, 손가락은 누르는 동안에도
0.1~0.3mm 씩 미세하게 풀린다. 그 이완만으로 해제가 나가 키가 툭툭 끊긴다. 일반
모드에서는 해제지점이 절대값이라 바닥에서 멀어 안 생긴다 — **RT 특유의 문제다.**

잡음 때문이 아니다. 0.1mm 는 63 카운트로 잡음 σ(약 7)의 9배다.

### 연속 RT

보통 RT 는 입력지점 아래에서만 살아 있고 키가 그 위로 올라오면 풀린다. 연속 RT 는
전 구간에서 살려 둔다. 그 토글이 존재한다는 것 자체가 **RT 가 걸렸다/풀렸다 하는
상태를 갖는다**는 뜻이고, 위의 `or` 버그가 왜 틀렸는지도 그것으로 설명된다.

---

## 설정을 전부 키별로

```
  keys_key_cfg_t   8 B -> 24 B      레코드 544 B -> 1568 B
    입력지점 · 해제지점 · RT 재입력 · RT 입력 해제 · 바닥 보호 · 데드존 · rt_flags
```

**키별이 기본이고 전역은 "모두 선택"이다.** 둘을 따로 두면 어느 쪽이 이기는지가 계속
문제가 된다. 판정은 언제나 키별 값을 보고, 전역 설정은 64키에 뿌린다.

설정은 0.01mm 인데 판정은 카운트다. 환산에 키별 스트로크가 필요해 나눗셈이 드는데
35kHz × 64셀 루프 안에서는 못 한다. `keys_thr_t` 표를 두고 설정·보정이 바뀔 때만
다시 만든다.

> ★ 이걸 넣기 전까지 판정은 전역 상수를 썼다. VIA 입력지점 슬라이더가 EEPROM 만
> 바꾸고 판정에는 닿지 않고 있었다.

`KEYS_CFG_VERSION` 을 4 로 올리며 자리를 넉넉히 잡았다. 올릴 때마다 사용자 보정값이
버려지는데 이 편에서만 두 번 그랬다(누적으로 눈금 3배, RT 항목 추가).

### 전 행정 4.0mm 가 틀렸다

이 보드에 꽂힌 것은 **3.4mm** 스위치다. 카운트 기준 판정은 영향이 없지만 mm 표시가
전부 18% 어긋나 있었다 — "입력지점 1.00mm" 가 실제로는 0.85mm 였다.

참고 보드 디버그 화면에서 키를 끝까지 눌렀을 때 **3.385mm** 로 찍힌 것이 처음부터
증거였는데 읽어내지 못했다. 4.0mm 스위치를 3.385mm 까지 눌렀다고 읽는 대신, 3.4mm
스위치를 끝까지 눌렀다고 읽었어야 했다. **그 잘못된 전제 위에 분석을 두 번 쌓았다.**

## 배운 것

이 편에서 잘못 짚었다가 바로잡은 것들이 공통점을 갖는다 — 전부 **재보기 전에 짐작으로
움직인 것**이다.

| 짐작 | 실제 |
|---|---|
| 스캔이 느린 건 구조 탓 | `-O0` 과 캐시 축출 |
| 누적을 넣었더니 잡음이 나빠졌다 | 계측 지점(데드밴드)을 같이 바꿨다 |
| `max 308us` 는 구조 문제 | 153만 번 중 3회, 부팅 순간 |
| 드리프트가 주기를 흔든다 | 매 스캔 돌려도 28us |
| RT 반복은 값이 예민해서 | `or` 로 묶은 로직 버그 |
| 전 행정 4.0mm | 3.4mm |
| 드롭다운이 안 넓어지는 건 flex 탓 | 컴포넌트가 `width` prop 을 본다 |

## 뒤에 고친 것 — 이동량은 위치가 아니다

거리 환산을 곡선으로 바꾸면서 이 편의 전제 하나가 무너졌다 ([15편](15-distance-curve.md)).

절대 위치(입력·해제·데드존·바닥)는 곡선을 태우면 그만이다. 그런데 **RT 의 두 값은
이동량**이라, 곡선에서는 같은 mm 라도 어디서 움직였느냐에 따라 카운트가 딴판이다.
카운트 하나로 잡아 두었던 것이 한 지점에서만 맞았다.

```
RT 0.50mm 설정, 실제 되돌림 거리      고친 뒤
   깊이 1.31mm      0.95mm             0.50mm
   깊이 2.27mm      0.50mm  ← 여기만    0.50mm
   깊이 3.31mm      0.24mm             0.50mm
```

**깊이 눌린 상태일수록 두 배로 예민해진다.** 타이핑에서 손가락이 머무는 곳이 거기라,
RT 를 켜면 설정한 숫자보다 훨씬 떨었다.

매 표본마다 역변환을 할 수는 없다 (35kHz × 64셀). 정규화 값 u 의 상위 3비트로 여덟
구역을 잡고 구역마다 문턱을 `keysThrRebuild` 에서 구워 둔다. 뜨거운 루프가 하는 일은
곱셈 하나와 시프트 하나라 **RT 를 켜도 스캔은 28us 그대로다.** 키당 32바이트다.

★ **구역을 정하는 자리는 지금 깊이가 아니라 기준점(peak)이다.** 되돌림은 거기서
시작하는 이동이라 문턱도 그 자리의 기울기로 재야 맞다.

★ **바닥 구역은 뒤에서 재야 한다.** 그냥 더하면 행정을 넘어가 잘리는데, 그러면 문턱이
커지기는커녕 **작아져서**(481 → 160) 바닥에서 재입력이 제일 쉽게 걸린다 — 고치려던
것과 정반대다. `keys rt` 가 구역 여덟 개를 다 찍게 해 둔 덕에 눈으로 바로 보였다.
대표값 하나만 찍었으면 못 찾았다.

## 남은 것

      **재단이 끝났으므로 이제 숫자 하나를 찾는 일이 됐다** — 예전에는 깊이마다
      다르게 동작해 튜닝 자체가 성립하지 않았다
