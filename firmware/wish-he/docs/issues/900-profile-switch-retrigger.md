# 900 — 프로파일 전환 키가 1번 프로파일을 건너뛴다

| | |
|---|---|
| 이슈 | 없음 — 채팅으로 들어온 제보 (2026-10-05) |
| 신고 | 2026-10-05, 채팅 제보 |
| 신고된 환경 | 60키 HE 보드, 펌웨어 `V260918R1` |
| 분석한 소스 | `2d50830` (`V260918R1`) |
| 상태 | 분석 끝, 미수정 — **장치 재현 전** |
| 자리 | `keysProfApply()` · `keysThrRebuild()`, `src/hw/driver/keys.c` |

> 모르는 말이 나오면 [README 의 "자주 나오는 말"](README.md#자주-나오는-말) 을 본다.

## 세 줄 요약

- **증상** — 프로파일 셋을 Fn+Enter 로 돌리는데, 3번에서 누르면 1번이 아니라 2번으로
  간다. 2번과 3번만 오간다.
- **원인** — 전환을 일으킨 키가 **새 프로파일의 문턱으로 다시 판정된다.** 새 해제지점이
  지금 깊이보다 깊으면 "뗐다" 가 되고, 손가락이 계속 내려가 "다시 눌렀다" 가 된다.
  새 프로파일의 같은 자리에 있는 키코드(`PF2`)가 그대로 실행된다.
- **고칠 자리** — 전환 순간 눌려 있던 키는 **물리적으로 다 뗄 때까지** 새 문턱으로
  판정하지 않는다.

## 증상

보고자의 말 그대로 (채팅).

- "프로필 3개를 쓰는데 usb 케이블을 뺐다 꽂으면 1번 프로필이 안넘어 가집니다"
- "2번프로필이랑 3번 프로필만 왔다가지더라구요 3번에서 맵핑된 단축키를 누르면
  2번 프로필로 가집니다"
- "1번 프로필은 rgb를 끈 상태입니다 그리고 via를 꺼도 마찬가지로 작동이 안되구요"
- "프로필 확인을 led로 확인하는데"
- 전환은 **Fn + Enter** 로 한다.

VIA 드롭다운으로 바꾸면 1번으로 간다.

## 보고자 설정 (백업 파일에서 읽음)

보고자가 웹앱 백업 파일(`WISH60-HE-20261006.json`)을 보내 왔다. 저장소에는 안 넣는다 —
필요한 값만 옮긴다.

| 프로파일 | 입력지점 | 해제지점 | RT 재입력 / 해제 | `rtFlags` | L1 idx23 (Fn+Enter) | 조명 |
|---|---|---|---|---|---|---|
| P1 | **2.00mm** | **1.50mm** | 0.50 / 0.50 | 2 (RT 끔) | `PF2` | 끔 (`effect 0`) |
| P2 | 1.00mm | 0.95mm | 0.50 / 0.50 | 2 (RT 끔) | `PF3` | 효과 1, 색상 128 |
| P3 | **1.00mm** | 0.50mm | 0.50 / 0.25 | 3 (RT 켬) | `PF1` | 효과 1, 색상 154 |
| P4 | 1.00mm | 0.95mm | 0.50 / 0.50 | 2 | — | P3 과 같음 |

- 63키 모두 프로파일 안에서 같은 값이다 (키별로 다르게 둔 것이 없다).
- Fn 은 L0 idx14 의 `MO(1)` (`0x5221`), Enter 는 L0 idx23 (`0x28`).
- **키맵과 조명 칸은 의도대로 들어 있다.** 3번의 그 자리는 분명히 `PF1` 이고, 1번 조명
  칸도 꺼진 값 그대로다. 저장된 값이 틀린 것이 아니다.

## 무슨 일이 일어나는가

모두 **코드에서 읽은 것**이다. 장치 재현은 아직 안 했다.

1. P3 에서 Fn 을 쥐고 Enter 를 누른다. Enter 가 P3 입력지점 **1.00mm** 를 지나는
   스캔에서 눌림이 되고, QMK 가 L1 idx23 = `PF1` 을 처리한다.

   ```c
   /* keyboards/wish60-he-7u/via/via_port.c:457 */
   case KC_PROF_1: ...
     if (keysProfSelect((uint8_t)(keycode - KC_PROF_1))) keysProfTouch();
   ```

2. `keysProfApply()` 가 프로파일을 바꾸고 문턱 표를 새로 만든다. **눌림 상태는 그대로
   두고 표만 바꾼다.**

   ```c
   /* src/hw/driver/keys.c:4161 */
   keysProfChanged_kb(0xFF);   /* clear_keyboard() — 호스트 쪽만 비운다 */
   set_st.active = idx;
   keysThrRebuild();           /* P1 문턱: 입력 2.00 / 해제 1.50 */
   keysProfChanged_kb(idx);
   ```

3. 다음 스캔에서 Enter 는 1.0mm 근처다. P1 해제지점 1.50mm 보다 얕으므로 **떼짐**이 된다.
4. 손가락은 계속 내려간다. 2.00mm 를 지나면 **다시 눌림**이 된다. Fn 은 아직 쥐고 있으므로
   L1 idx23 을 읽는데, 지금은 P1 키맵이라 `PF2` 다 → P2 로 간다.
5. 조명 다시 켜기는 메인 루프로 미뤄져 있다(`rgb_reload_req`). P1 에 머무는 시간이 사람
   손가락 한 번 내려가는 시간이라 꺼진 P1 이 눈에 안 띈다. 보고자에게는 "3 → 2" 로 보인다.

### 왜 P3 → P1 에서만 나나

전환은 Enter 가 **옛 프로파일의 입력지점**을 지나는 순간 일어난다. 그 깊이가 **새
프로파일의 해제지점보다 얕으면** 다시 입력된다.

| 전환 | 바뀌는 깊이 (옛 입력지점) | 새 해제지점 | 결과 |
|---|---|---|---|
| P1 → P2 | 2.00 | 0.95 | 눌린 채 유지 |
| P2 → P3 | 1.00 | 0.50 | 눌린 채 유지 |
| P3 → P1 | 1.00 | **1.50** | **떼짐 → 다시 눌림 → `PF2`** |

조건은 **새 해제지점 ≥ 옛 입력지점**이다. 이 사용자 설정에서는 P3 → P1 하나가 그렇다.

### "다시 꽂으면" 은 원인이 아니다 (추정)

재부팅이 바꾸는 것을 다 따라가 봤다. 프로파일 번호, 조명 칸, 키맵, EEPROM 플러시 모두
일관된다. 그 사이 P1 이나 P3 의 입력지점을 바꿨다고 보는 것이 가장 자연스럽다.
**보고자에게 확인하지는 않았다.**

## 왜 지금까지 안 드러났나

- A5(프로파일 전환 중 눌린 키가 굳는다) 를 고칠 때 **호스트 쪽**만 봤다. `clear_keyboard()`
  가 리포트를 비우지만, 판정 쪽의 눌림 상태와 새 문턱의 관계는 안 봤다.
- `he_test.py` 의 전환 시험은 프로파일마다 문턱이 **같은** 상태에서 돈다. 문턱이 다른
  두 프로파일 사이에서 같은 키로 전환하는 경우가 없다.
- 전환 키를 Fn 레이어에 두고, **프로파일마다 다른 자리 키코드**로 순환시키는 쓰임을
  생각하지 않았다. `PF>` 하나로 돌리면 같은 일이 나도 다음 프로파일로 한 번 더 갈
  뿐이라 눈에 덜 띈다.

## 고칠 자리

**전환 순간 눌려 있던 키는 물리적으로 다 뗄 때까지 판정에서 뺀다.**

- `keysProfApply()` 에서 그 순간 `pressed` 인 키를 마스크로 잡아 둔다.
- 판정은 그 키를 계속 "눌림" 으로 두되, **새 문턱으로 다시 판정하지 않는다.**
- 쉬는 자리(스퀄치 위)까지 올라오면 마스크를 풀고 정상 판정으로 돌아간다.
- 전환 키뿐 아니라 그때 누르고 있던 **다른 키도** 같은 이유로 다시 입력될 수 있으므로
  전부 덮는다.

RT 상태도 같이 본다. `keysProfApply()` 는 `keysRtReseed()` 를 안 부른다 — RT 를 켠
프로파일로 들어갈 때 `peak` 가 옛 값인 채로 남는지 확인해야 한다 (코드에서 읽음, 안 잼).

### 생각했다가 접은 길

| 대안 | 왜 안 되나 |
|---|---|
| 전환 뒤 그 키를 "떼짐" 으로 강제 | 손가락이 계속 내려가면 새 입력지점에서 바로 다시 눌린다 — 지금 버그와 같다 |
| 프로파일 키를 뗄 때 실행 | 뗄 때는 이미 새 키맵을 보고 있어 "뗀 키" 가 어긋난다 (`via_port.c` 의 "누를 때 바꾼다" 주석) |
| 전환 뒤 일정 시간 입력 무시 | 시간은 손 빠르기에 달렸다. 길면 게임 중 입력을 먹고, 짧으면 안 막힌다 |
| QMK 쪽에서 직전 프로파일 키코드를 무시 | 판정이 이미 두 번 눌렸다고 하는 것을 위에서 가리는 셈이다. 다른 키의 재입력은 그대로 남는다 |

## 사용자에게 준 임시 조치

펌웨어를 안 고치고 피하는 법 (코드로 따진 것, 장치로 안 잼).

- **P1 에서 Enter 의 해제지점만 1.0mm 보다 얕게** (예: 0.50mm). 입력지점 2.00mm 는 둬도 된다.
- 또는 Enter 의 입력·해제지점을 세 프로파일 모두 같게.
- **Fn 은 안 바꿔도 된다.** Fn 이 새 문턱에서 떼짐이 돼도 레이어가 잠깐 꺼질 뿐이고,
  Enter 가 다시 눌리지 않으면 호스트로 나가는 키가 없다.

## 시험

`tools/he_test.py` 에 넣을 재현 절차.

1. 전 값 기록: 지금 프로파일, P1·P3 의 전역 입력/해제지점, 전환 자리 키맵.
2. P1 = 입력 2.00 / 해제 1.50, P3 = 입력 1.00 / 해제 0.50.
   P1 L1 Enter = `PF2`, P3 L1 Enter = `PF1`. P3 으로 간다.
3. `keys inject` 로 Fn 을 바닥에, Enter 를 0 → 1.05mm → 바닥 순으로 민다.
4. `prof` 를 읽는다. **지금 펌웨어는 2, 고친 뒤는 1** 이어야 한다 → 고치기 전에는 `xfail`.
5. 같은 절차를 다른 일반 키로 한 번 더 — 전환 순간 눌려 있던 키가 호스트로 두 번 안
   나가는지 (`host` 무리의 리포트 세기 재사용).
6. **되돌린다.** 설정을 먼저 되돌리고 주입을 나중에 끈다.

## 같이 찾은 것 — 이 증상의 원인은 아니다

분석 중 코드에서 읽은 결함 셋. 이번 제보와는 관계없지만 실재한다 (모두 장치로 안 잼).

1. **웹앱이 키로 바꾼 프로파일을 모른다.** `via-he/src/components/menus/profile-select.tsx`
   는 연결할 때와 자기 드롭다운에서 바꿀 때만 프로파일을 읽는다. 키로 바꾸면 배지와
   키맵 화면이 옛 프로파일 그대로이고, 그 상태에서 키를 고치면 **장치의 실제 프로파일**
   키맵에 써진다. 드롭다운에서 앱이 믿는 번호를 고르면 `if (i === prof.active) return;`
   로 아무것도 안 해서 바로잡을 수도 없다.
2. **조명과 프로파일 번호의 저장 시점이 다르다.** 조명은 EEPROM 으로 200ms 뒤
   (`EE_FLUSH_MS`), 번호는 설정 핑퐁으로 1초 뒤(`KEYS_CFG_SAVE_QUIET_MS`)에 남는다.
   그 사이에 전원이 끊기면 "번호는 옛것, 조명은 새것" 으로 부팅하고, 다음 전환 때
   `profRgbStore(옛 번호)` 가 새 조명을 옛 칸에 덮는다.
3. **`keymapProfileOffset()` 이 예약(`prof_req`)을 안 본다.** HID 로 전환한 직후, 메인
   루프가 돌기 전에 키맵 읽기·쓰기가 오면 옛 블록으로 간다. 백업·복원이 `heProfSet`
   바로 뒤에 키맵을 다룬다. 가능성은 낮다.
