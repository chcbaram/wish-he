# 16. 설정 채널이 한 칸씩 밀리던 것

펌웨어를 굽고 나면 웹앱이 장치를 다시 잡다가 **경고 개수가 끝없이 올라갔다.** 497 개,
2153 개, 멈추지 않고. 한참 두면 결국 붙기는 하는데 그때까지 화면이 비어 있고, 브라우저를
새로고침하면 곧바로 멀쩡해졌다.

원인이 넷이었다. 셋은 **밀림을 만드는** 쪽이었고 하나는 **밀림이 영영 안 풀리는** 쪽이었다.
앞의 셋만 고쳤을 때 개수가 줄기만 하고 없어지지 않은 이유가 그것이다.

---

## 1. 왜 한 번 밀리면 영영 밀리나

설정 채널(`0xFF60`)은 **명령 하나에 응답 하나**로 짝을 이룬다. 웹앱은 이렇게 읽었다.

```ts
await hid.write(command);
const buffer = await hid.readP();   // ← 다음에 오는 리포트를 그냥 집어 온다
```

`readP()` 는 **짝을 보지 않는다.** 그저 다음 리포트를 준다. 그러면 이렇게 된다.

```
① 응답 하나가 늦게 온다 (또는 명령 하나가 버려진다)
② 다음 명령이 그 늦은 답을 자기 답으로 읽는다     ← 여기서 한 칸 밀린다
③ 그 다음도 앞 명령의 답, 그 다음도, 그 다음도 ...
```

②에서 웹앱은 "응답이 틀렸다" 를 알아챈다 — 응답에 명령 바이트가 되비쳐 오니까. 그런데
**알아채고도 밀린 채로 넘어갔다.** 경고만 하나 찍고 다음 명령으로 간다. 그래서 어긋남이
풀리지 않는다.

**경고 개수가 늘기만 한다는 것은 곧 줄이 밀렸다는 뜻이다.** 하나씩 실패하는 것과는
모양이 다르다 — 그건 개수가 띄엄띄엄 는다.

결국 재시도를 다 쓰고 장치 목록을 통째로 비우면 그제야 줄이 다시 섰다. 그게
"한참 두면 붙는다" 의 정체이고, 새로고침이 듣던 이유다.

### 고침 — 짝이 맞을 때까지 건너뛴다

되비친 명령 바이트가 **이미 태그 노릇을 한다.** 검사에만 쓰던 것을 짝 맞추기에 쓰면 된다.

```ts
let buffer = await readP();                 /* 첫 판은 하염없이 기다린다 */
while (!matches(buffer) && skipped < 4) {
  const next = await readWithin(300);       /* 밀린 것을 버리고 다시 읽는다 */
  if (next === undefined) break;            /* 더 안 온다 — 진짜 [E_] 다 */
  buffer = next;
}
```

**밀린 응답 하나를 버리는 것으로 줄이 다시 선다.** 어긋난 상태에서는 앞 명령의 답이 이미
와 있어 곧바로 돌아오므로 기다림이 짧아도 된다.

★ **첫 판에는 시간 제한을 걸지 않는다.** 지우기처럼 느린 명령이 있어서, 여기에 제한을
걸면 멀쩡한 명령을 실패로 만든다. 건너뛰기는 어긋났을 때만 돈다.

★ **`Promise.race` 로 감싸면 안 된다.** `readP()` 는 영영 기다리므로, 경주에서 진 쪽의
대기가 대기열에 그대로 남아 **다음 응답을 대신 삼킨다.** 어긋남을 고치려다 어긋남을 하나
더 만드는 셈이다. 시간이 다 되면 **자기 대기를 직접 걷어내는** 읽기를 따로 뒀다.

### 일련번호를 넣는 길은 막혀 있다

더 튼튼하게 하려면 명령마다 일련번호를 붙이는 것이 정석이다. **그런데 자리가 없다.**
`DYNAMIC_KEYMAP_SET_BUFFER` 는 명령 1 + 오프셋 2 + 길이 1 + 데이터 28 로 32바이트를 이미
꽉 쓴다. 되비친 명령 바이트를 태그로 쓰는 것이 얻을 수 있는 최선이고, 그러면 **장치를
안 건드려도 된다.**

## 2. 장치가 밀림을 만들던 두 자리

### (가) 미뤄 둔 명령을 버리고 있었다

설정 채널은 받는 즉시 답하는 것과, 메인 루프로 넘겨 처리하는 것이 있다. 넘기는 쪽이
이랬다.

```c
else if (raw_recv != NULL && raw_pending == false)   /* ← 이미 차 있으면 그냥 버린다 */
{
  memcpy(raw_pending_buf, rx_report, HID_EP_MPS);
  raw_pending = true;
}
usbd_ep_start_read(busid, HID_OUT_EP, rx_report, HID_EP_MPS);   /* 곧바로 다시 받는다 */
```

앞 명령을 아직 처리하지 못했는데 다음 명령이 오면 **소리 없이 버렸다.** 그런데 호스트는
버려진 줄 모르고 답을 기다린다 — 그 답은 영영 안 오고, 그 뒤 모든 응답이 한 칸씩 밀린다.

**고침은 흐름제어다.** 다 처리하기 전에는 **다시 받지 않는다.**

```c
else if (raw_recv != NULL)
{
  memcpy(raw_pending_buf, rx_report, HID_EP_MPS);
  raw_pending = true;
  return;                    /* ★ 여기서 재무장하지 않는다 */
}
...
/* 처리한 뒤에야 다음 명령을 받는다 */
usbd_ep_start_read(HID_BUSID, HID_OUT_EP, rx_report, HID_EP_MPS);
```

그러면 컨트롤러가 NAK 을 내고 호스트가 알아서 다시 보낸다. **USB 가 원래 그러라고 만든
장치다.** 버릴 이유가 없다.

### (나) 묵은 응답을 뒤늦게 보냈다

보내기가 끝나기를 기다리는 표시(`tx_pending`)가 어떤 사정으로 안 풀리면, 한참 뒤 엉뚱한
때에 그 답이 나갔다. 호스트는 그것을 **다음 명령의 답**으로 읽는다.

정상이면 1ms 안에 나간다. 20ms 를 넘긴 것은 묵은 것으로 보고 **보내지 않고 버린다.**

```c
#define HID_TX_PENDING_MAX_MS   20      /* 정상은 1ms 안에 나간다 */

static bool hidTxPendingTake(void)
{
  if (tx_pending == false) return false;
  tx_pending = false;
  return (millis() - tx_pending_ms) <= HID_TX_PENDING_MAX_MS;
}
```

★ 여기서 **버리는 것이 맞다.** 늦게라도 보내면 줄이 밀린다 — 안 보내면 호스트가 그 명령
하나만 실패로 처리하고 지나간다. 실패 하나와 영구 어긋남은 값이 다르다.

---

## 3. 장치를 놓치면 아무도 다시 안 보던 것

웹앱은 USB 연결·해제 **이벤트에만** 반응했다. 그 이벤트가 온 순간에 장치를 못 잡으면 —
재열거 직후라 아직 안 떴거나, 재시도를 다 쓰고 목록을 비웠거나 — **그 뒤로 아무도 다시
안 본다.** 이벤트는 이미 지나갔기 때문이다.

굽고 나면 정확히 그렇게 됐다. 화면이 "키보드를 연결하면" 에서 굳고 새로고침해야 돌아왔다.

**장치가 하나도 없으면 3초마다 다시 훑게 했다.** 붙어 있을 때는 아무것도 하지 않는다.

★ 1초로 하지 않는다. 장치를 잡는 절차가 자체 재시도를 돌리므로, 그보다 촘촘히 부르면
재시도와 겹쳐 오히려 실패를 재촉한다.

---

## 4. 왜 하필 이때 터졌나

버리는 코드는 이틀 전 QMK 를 얹을 때부터 있었다. 그런데 **명령이 처리보다 빨리 와야**
터진다. 그 조건이 나중에 갖춰졌다.

```
QMK 얹음        버리는 경로가 생긴다 (버그는 이때부터)
인터페이스 6벌  USB 인터럽트가 바빠져 메인 루프가 비우는 창이 넓어진다
키맵 4벌        설정 도구가 GET_BUFFER 를 4배로 연달아 던진다      ← 결정타
굽고 재조회     그 폭풍을 굽을 때마다 일으킨다                      ← 방아쇠
```

**버그가 언제 들어왔는지와 언제 보이는지는 다르다.** 안 보이던 기간은 고쳐져 있던 것이
아니라 조건이 안 맞았던 것뿐이다.

---

## 남는 것

- 설정 채널만 고쳤다. **키코드가 나가는 길은 다른 인터페이스**(별도 IN 엔드포인트)라
  이 이야기와 무관하다 — 흐름제어를 걸어도 키 입력은 영향을 받지 않는다
- 건너뛰기 한도는 4 칸, 기다림은 300ms 다. 밀림은 실제로 한 칸이었다. 넉넉히 잡되
  무한정 삼키지는 않게 했다
- 웹앱 콘솔에 `밀린 응답 N개 버리고 다시 맞춤` 이 찍힌다. **이 경고가 보이면 장치 쪽에서
  아직 밀림을 만들고 있다는 뜻이다** — 되맞추니까 사용자에게는 안 보일 뿐이다. 다음에
  이 자리를 볼 때 그 숫자부터 확인할 것
