# 남의 부트로더 위에 내 키보드 펌웨어 얹기

기성 홀이펙트 키보드 보드를 열어, 벤더 부트로더는 그대로 둔 채 그 위에서 도는
**내 펌웨어**를 만든다. 최종 목표는 8kHz 스캔과 래피드 트리거지만, 먼저
**완전히 동작하는 평범한 키보드**를 만든다.

- 보드: HPM5361 (RISC-V, 400MHz), 아날로그 MUX + ADC 로 64키, WS2812 83개
- 배선: **없다.** UART 헤더도 디버그 LED 도 없는 보드라 USB 하나로 굽고 디버깅한다
- 자리: 플래시 `0x80020000` 부터 384KB. 부트로더와 EEPROM 은 건드리지 않는다

```
ROM → 부트 헤더 → 부트로더(0x80003000) → 매직 확인 → 본 펌웨어(0x80020004)
```

## 다음에 할 것

> 대화 맥락은 압축되면 사라진다. **여기가 이어서 할 일의 유일한 목록**이다.

### 지금 차례

- [ ] **RT 실사용 튜닝** — 이제 재단은 끝났으니 감으로 값을 정할 차례다.
      `keys learn` 이 눌림 에지마다 한 줄을 찍으므로 한 키를 한 번 눌러 몇 줄이
      나오는지로 잰다

- [ ] **WS2812 인코딩을 나눠 굽기** — 움직이는 효과에만 남은 문제다.

      더티 플래그(R33)로 정지 효과와 RGB 끔은 초과가 0 이 됐다. 색이 매 프레임 진짜로
      바뀌는 효과(가로흐름 등)는 거를 것이 없어 그대로 473회/10초다.

      **전송은 이미 비동기다** — `ws2812Refresh()` 는 앞 프레임이 나가는 중이면 그냥
      건너뛴다. 시간을 먹는 것은 색 83개를 비트 패턴 1992바이트로 펼치는 **인코딩**
      이라 DMA 로 넘길 수가 없다.

      가르면 된다 — 색을 249바이트 그림자에 한 번 복사해 두고(찢김 방지) 루프마다
      4분의 1씩 채운 뒤 다 차면 DMA 를 건다. 200us 봉우리 하나가 50us 넷이 된다.

      ★ **지금도 해는 없다.** 스캔은 ADC 가 모는 별도 경로라 28us 그대로고, USB 폴링
      1ms 에 200us 면 여유가 크다. 효과가 무거워지거나 LED 가 늘면 그때 가른다

- [x] ~~**WS2812 더티 플래그**~~ — 끝. R33.

      상류 QMK 에 있는 것을 이식하며 흘렸다 (`rgb_matrix_drivers.c` 의 `ws2812_dirty`).
      rgb_matrix 는 효과가 정지든 아니든, 심지어 **꺼져 있어도** 매 프레임 flush 를
      부른다. 그래서 색이 하나도 안 바뀐 프레임도 1992바이트를 다시 펼쳐서 쐈다.

      ```
                        R32       R33
      단색 (정지)      초과 353    초과 0     RGB 평균 22 -> 7us, 최대 206 -> 52
      RGB 끔           초과 353    초과 1     평균 0us
      가로흐름         초과 473    초과 473   색이 진짜 바뀐다 — 거를 것이 없다
      ```

      ★ 값 비교 없이 표시하면 있으나 마나다. rgb_matrix 가 매 프레임 83개를 전부 다시
      칠하므로 "썼다" 가 아니라 "달라졌다" 를 봐야 한다.

      ★ 색만 보면 놓치는 것이 있다 — 전류 상한이 바뀌면 같은 색이라도 리미터 배율이
      달라져 프레임이 달라진다. `ws2812SetLimit()` 이 `ws2812Touch()` 로 알린다.

      ★ 표시는 DMA 를 실제로 건 뒤에 지운다. 앞 프레임이 나가는 중이라 되돌아가는
      길이 있는데, 미리 지우면 그 프레임이 영영 안 나간다.

- [x] ~~**래피드 트리거를 깊이 구역마다 재단**~~ — 끝. R25.

      절대 위치(입력·해제·데드존·바닥)는 곡선으로 정확해졌는데, RT 의 두 값은
      **위치가 아니라 이동량**이라 직선으로 남아 있었다. 곡선에서는 같은 이동량이라도
      어디서 움직였느냐에 따라 카운트가 달라서, 설정한 숫자가 한 지점에서만 맞았다.

      ```
      RT 0.50mm 설정, 실제 되돌림 거리      고친 뒤
         깊이 1.31mm      0.95mm             0.50mm
         깊이 2.27mm      0.50mm  ← 여기만    0.50mm
         깊이 3.31mm      0.24mm             0.50mm
      ```

      정규화 값 u 의 상위 3비트로 8구역을 잡고, 구역마다 문턱을 `keysThrRebuild`
      에서 구워 둔다. 뜨거운 루프가 하는 일은 곱셈 하나와 시프트 하나다 —
      **RT 를 켜도 스캔은 28us 그대로다.** 키당 32바이트, 전체 2KB.

      ★ 구역을 정하는 자리는 지금 깊이가 아니라 **기준점(peak)** 이다. 되돌림은
      거기서 시작하는 이동이라 문턱도 그 자리의 기울기로 재야 한다.

      ★ 바닥 구역은 뒤에서 재야 한다. 그냥 더하면 행정을 넘어가 잘리는데, 그러면
      문턱이 커지기는커녕 **작아져서**(481 -> 160) 바닥에서 재입력이 제일 쉽게
      걸린다 — 고치려던 것과 정반대다. `keys rt` 가 구역 여덟 개를 다 찍으므로
      단조 증가인지 눈으로 확인할 수 있다

- [x] ~~**거리 환산을 곡선(LUT)으로**~~ — 끝. R22 부터 들어가 있다.

      스위치 표에 33칸 LUT(Q15), `keysGetDepthUm` 은 이진 탐색 + 보간,
      `keysThrRebuild` 는 반대 방향으로 문턱을 만든다. 왕복 오차 1um.

      ★ **실측으로 확인했다.** 이게 제일 중요하다 —

      ```
      심 1·2·3mm 를 버니어로 재서 넣었을 때    눈금이 1mm 씩 따라왔다
                                              (직선이면 0.6~0.7mm 씩이어야 한다)

      곡선을 끄고(일반형 3.5mm) 실제 2.00mm    1.25mm 로 읽혔다
        곡선 모델의 예측 1.23mm                 0.02mm 차이
        실제가 직선이었다면 2.06mm              0.81mm 어긋난다
      ```

      두 번째가 결정적이다. "곡선이 맞다" 가 아니라 **"직선이 틀린 양까지 예측대로"**
      라서, 모델이 곡선의 모양을 맞게 알고 있다는 뜻이다.

      덤으로 알아낸 것 — **키캡이 판에 닿기까지 여유가 0.4mm 쯤 있다.** 심을 끼워
      재면 그만큼 덜 막히므로, 한 장짜리 절대 측정은 이 여유를 빼고 봐야 한다.

      ★ **화면이 펌웨어보다 먼저**인 이유를 지켰다. 펌웨어를 먼저 바꿨으면 모든 키의
      감각이 한꺼번에 달라졌을 텐데 그게 맞는지 볼 방법이 없었다. 두 값을 나란히
      놓고 보는 화면이 있었기에 심 시험이 곧바로 판정이 됐다

      ★ **참고 보드는 끝까지 직선이다.** 두 군데를 다 확인했다 —

      - 펌웨어(디스어셈블): 부동소수 명령이 94개뿐이고 제일 큰 뭉치는 RGB 색상환용
        `atan2` 였다. 환산은 `(sample - base) * (32768/span) >> 15` 한 줄이고
        span 은 숫자 둘(보정 max·min)이다. 상수 영역에 거리용 표가 없다
      - 웹 도구(`index.js`): 입력지점·RT·데드존 다섯 값이 전부 `x * 1000 / 전행정`
        하나로 오간다. `curve`·`LUT`·`interp`·`flux` 라는 낱말조차 없다

      "웹이 곡선을 갖고 있고 변환해서 보내는 것 아닌가" 를 의심해서 본 것인데
      아니었다. **그들 화면이 1.25mm 라고 할 때 실제로는 2.00mm 눌려 있다.**
      분해능도 전 행정을 254칸으로 쓰니 그 오차가 눈에 안 띄었을 것이다

- [x] ~~**나눗셈 걷어내기**~~ — 끝. 곡선 경로에 나눗셈이 하나도 없다.

      RGB 의 HE 효과가 매 프레임 65키의 깊이를 물어서 이 함수가 뜨거운 자리였다.
      RGB 태스크 평균 21us(직선) → 34us(64비트 나눗셈) → 26us(역수 표). 스캔 한
      바퀴는 28us 로 처음부터 끝까지 변화 없다 — 판정은 카운트 비교라 곡선이 안 탄다.

      역수 표는 **참고 보드에서 가져온 수**다. 저쪽도 부팅 때 32768/i(i=1..255)를
      채워 두고 스캔 경로에서는 곱셈+시프트만 한다. 우리는 곡선 칸 간격의 역수를
      부팅 때, 키별 스트로크의 역수를 `keysThrRebuild` 에서 만든다.
      **상수로 박지 않는다** — 곡선을 고칠 때 짝이 어긋난다

      ★ 그런데 **제일 큰 답은 "그 자리에 거리가 필요 없다"** 였다 (R23).

      RGB 효과는 "반쯤 눌렸다" 만 알면 되는데 곡선을 태워 mm 로 바꾼 뒤 다시 행정으로
      나눠 0~255 로 되돌리고 있었다. `keysGetLevel8()` 로 센서 비율을 그대로 준다 —
      탐색도 나눗셈도 없다.

      ```
                       R18(직선)  R22(곡선)  R23(지금)
      스캔 한 바퀴        28 us      28 us     28 us
      RGB 태스크 평균     21 us      26 us     25 us
      RGB 태스크 최대     78 us     238 us    118 us
      125us 초과         590회     1177회      0회
      ```

      **초과가 0 이다 — 곡선을 넣기 전보다도 좋다.** 평균이 아니라 꼬리가 문제였고,
      이진 탐색의 예측 안 되는 분기가 프레임을 가끔 길게 끌고 있었다

- [x] ~~**얕은 입력지점의 하한**~~ — 곡선을 넣으면 같은 mm 가 카운트로 2.7배 작아진다.

      ★ **노이즈가 나빠진 게 아니라 이름표가 정직해졌다.** 예전 "0.30mm" 는 실제로
      0.72mm 였고 문턱이 222카운트였다. 같은 물리 지점의 여유는 하나도 안 변했다 —
      0.72mm 는 지금도 222 다. 바뀐 것은 적은 숫자를 그대로 받게 됐다는 점이고,
      행정의 맨 위는 자석이 멀어 원래 신호가 약하다. 직선이 그걸 가려 주고 있었다.

      ```
      0.10mm ->  26 카운트  0.7x    잡음 p-p 40 보다 낮다
      0.30mm ->  82         2.1x
      0.50mm -> 144         3.6x
      ```

      참고 보드도 같은 벽에서 막는 것으로 답했다 (웹 도구가 전 행정의 1/10 밑으로
      못 내리게 한다). **그 숫자를 그대로 가져오면 안 된다** — 저쪽은 254칸, 우리는
      2514칸이라 같은 1/10 이 우리에게는 0.80mm 가 되어 쓸 만한 구간을 통째로 막는다.
      우리 잡음으로 다시 잡아 60카운트(≈0.22mm)로 뒀다. 설정값은 안 건드리고
      문턱만 올린다 — 조용히 고쳐 쓰면 화면과 실제가 어긋난다

- [ ] **커스텀 스위치 프로파일** — 스위치 갈래에 `CUSTOM` 자리만 잡아 뒀다.
      먼저 정할 것: 사용자가 **무엇을 입력하나.** 두 점 자속(데이터시트를 보고
      직접)인지, 심을 끼워 재게 할 것인지. 앞쪽이 훨씬 쉽고 대부분 그걸로 족하다

- [ ] **태스크 최대 1685us 가 어디서 나는지** — 디버그 화면에서 드러났다.
      평균 3us 인데 최대 1685us, 125us 초과가 0.13%.

      실험으로 재현한 것은 여기까지다 (`tools/dev.py`) —

      | 상황 | 스캔 최대 | 태스크 최대 |
      |---|---:|---:|
      | 가만히 둠 | 40~71 us | 141~152 us |
      | HID 명령 계속 | 167 us | 311 us |
      | 프로파일 전환(플래시 저장) | 383 us | 289 us |

      **셋 다 1685us 가 아니다.** 부팅 직후나 USB 열거 때 한 번 나는 값일 가능성이

### 규칙 (지키기)

- **키보드 그림에 무엇을 칠할지는 그 화면이 정한다** — `heSlice.overlayKeys`.
  화면에 들어갈 때 자기 것을 넣지 않으면 앞 화면의 표시가 그대로 남는다.
  `null` = "보여줄 것 없으니 선택을 보여라", `[]` = "칠할 것이 없다"
- **i18n 키는 세 벌(en·ko·ja)을 함께 채운다** — 이 앱은 영어 문장을 그대로 키로
  쓰는데, `en.json` 에 없으면 영어에서 키 문자열이 그대로 나온다. 실제로 툴팁
  4개가 그렇게 나가고 있었다. 낱말이 이미 다른 뜻으로 쓰이면(`Flash` → "플래시")
  문장을 늘리지 말고 `he.fw.flash` 처럼 이름 공간을 준다
- **키캡 각인 스타일은 화면이 정한다** — 키 하나하나의 데이터가 정하면 같은 화면
  안에서 들쭉날쭉해진다. HE 탭은 값이 하나도 없어도 `keyLabels` 를 늘 넘겨
  `compact` 를 켠다. 값은 그 자리에 들어왔다 나갔다 할 뿐이다
- **HID 명령을 더하면 옛 펌웨어를 생각한다** — 모르는 하위 명령이 오면 옛 펌웨어는
  엉뚱한 응답을 주고, VIA 는 에코가 어긋난 것을 오류로 잡는다. 폴링 안에서 쌓이면
  **진짜 오류를 못 본다.** 도구는 한 번 실패하면 그만 물어야 한다
- **플래시를 쓰면 인터럽트가 6ms 꺼진다** — XIP 라 어쩔 수 없다. 그동안 USB 전송
  완료 인터럽트를 놓치면 `is_tx_busy` 가 굳고, 그 뒤 응답이 **조용히 버려진다.**
  못 보낸 응답은 들고 있다가 자리가 나면 보내고, 50ms 가 지나면 놓친 것으로 보고
  되살린다 (`hid_if.c`). 느린 것이 플래시만은 아니다 — 조명을 다시 켜는 일도
  ISR 에서 하면 USB 가 멈춘다
- **HID 왕복은 한 줄로 세운다** — 요청 하나에 응답 하나다. 라이브 트래킹·보정
  폴링·전 키 읽기·슬라이더 쓰기가 동시에 나가면 응답이 엇갈린다. 부르는 쪽마다
  조심하게 하면 반드시 하나를 놓치므로 `send` 자체를 직렬화한다 (`he-api.ts` 가 앱
  전체 몫으로 들고 있다). **VIA 자신이 부르는 길**(키맵·매크로)도 `heLock` 으로 같은
  줄에 세운다 — 이걸 빠뜨려 응답이 엇갈렸다. 폴링 한 회차가 여러 왕복이면 `setInterval` 도 쓰지 않는다 — 주기
  안에 못 끝내면 회차가 겹친다. 끝난 뒤에 다시 건다
- **버튼 폭은 고정 숫자로 맞추지 않는다** — 번역마다 길이가 달라 반드시 어긋난다.
  `min-width` 로 바닥을 주되 가장 긴 번역이 넘지 않는 낱말을 고른다

### 규칙 (지키기) — 이어서

- **장치에 직접 붙어 본다** — `tools/dev.py` (CLI 는 CDC, 설정 채널은 HID).
  "굳는다", "값이 0 이다" 같은 증상은 원인을 안 알려준다. 웹 도구를 통해서만 보면
  펌웨어인지 앱인지 못 가른다 — 짐작으로 고치다 두 번 빗나갔다. 직접 붙으면 한 번에
  갈린다 (`dev.py burst` 가 응답 소실을, `dev.py stat` 이 페이지 어긋남을 잡았다)
- **HID 한 프레임은 32바이트다** (`HID_EP_MPS`). 앞 4바이트를 빼면 LE32 를 일곱 개.
  값이 더 많으면 **페이지로 나눈다.** 한 번에 담으려다 `tx_report[32]` 를 28바이트
  넘겨 썼다 — ISR 안에서 남의 메모리를 밟는 짓이고, 컴파일러는 상수 첨자만 잡아 준다
- **문자열은 숫자 뒤에 이어 붙이지 않는다** — 숫자가 늘면 자리가 밀려 도구가 엉뚱한
  바이트를 읽는다. 고정 자리나 별도 페이지에 둔다

### 확인만 하면 되는 것

- [ ] `keyboard_task` 최대 302us 가 나는 순간 특정 (153만 번 중 3회, 부팅·CLI 조작 때)
- [ ] 8kHz 리포트 실측 — 폴링 주기와 스캔 주기가 실제로 분리됐는지
- [ ] **`bInterval = 1` 을 유지할지** — 125us 폴링은 링크에 여유를 안 준다. USB
      전류계를 끼웠더니 키 입력이 간헐로 빠졌고 빼니 정상이었다
      ([14편](14-led-limiter.md)). 보통 키보드(1ms)라면 견뎠을 조건이다

번호는 순서가 아니라 편 번호다. 9편을 5편보다 먼저 했다 — **JTAG 배선 없이 굽게 되면서**
이후 시행착오 비용이 크게 줄었고, 스캔처럼 반복이 많은 작업 전에 해둘 값어치가 있었다.

VIA 는 키맵을 장치에 저장해야 하므로 **8편(EEPROM)이 먼저**다. 앱 뒤쪽
`0x80080000` 부터가 그 자리다 ([00-hardware.md](00-hardware.md) 2절).

**VIA 프로토콜을 직접 구현하지 않는다.** QMK 의 `quantum/via.c` 와
`dynamic_keymap.c` 가 이미 그 일을 한다. 우리가 만들 것은 `port/` 쪽 —
`matrix_scan()` 이 `keysGetRow()` 를 읽게 하고, EEPROM 백엔드를 8편의 플래시 계층에
연결하고, HID 리포트 송신을 우리 CherryUSB 로 돌리는 어댑터다. 그래서 **10편(QMK)이
11편(VIA)보다 먼저** 온다.

**GUI 는 따로 만들지 않는다.** 11편에서 VIA 웹앱을 포크해 HE 기능을 얹는 것이 목표이고,
래피드 트리거 튜닝 화면도 거기에 붙인다. 그전까지 필요한 관측은 CLI 로 충분하다
(`keys bar` / `keys watch`).

레이아웃은 이미 펌웨어 안에 바이너리로 들어 있다 — `keys_geo[]` 가 키마다
`{x, y, w, h, row, col}` 6바이트(1/4 키유닛)다. raw HID 로 이걸 내보내면
**웹 도구가 JSON 파일 없이 장치만 보고** 배치를 그릴 수 있다.

## 1. 개발 환경

### 1.1 툴체인 — xPack RISC-V GCC

이 프로젝트는 **hpm_sdk 에 의존하지 않는다.** 필요한 SoC 헤더·드라이버·링커
스크립트는 `src/bsp/` 아래로 들여왔다. 그래서 준비할 것은 컴파일러뿐이다.

```sh
# https://github.com/xpack-dev-tools/riscv-none-elf-gcc-xpack/releases
tar xf xpack-riscv-none-elf-gcc-13.4.0-1-darwin-arm64.tar -C ~/hdd/tools/
export HPM_RISCV_TOOLCHAIN_DIR="$HOME/hdd/tools/xpack-riscv-none-elf-gcc-13.4.0-1"
```

`HPM_RISCV_TOOLCHAIN_DIR` 은 **디렉토리든 `gcc` 실행 파일 경로든** 받는다. 안 잡히면
`PATH` 에서 찾고, 그래도 없으면 CMake 가 `RISCV Toolchain not found` 로 멈춘다.
HPMicro 공식 툴체인(`riscv32-unknown-elf-`)도 그대로 쓸 수 있다 —
`tools/hpmicro-riscv-gcc.cmake` 가 두 접두어를 모두 안다.

### 1.2 OpenOCD — HPMicro 빌드여야 한다

플래시 기록에는 **`hpm_xpi` 드라이버가 들어간 HPMicro 배포판**이 필요하다.
homebrew 의 OpenOCD 에는 그 드라이버가 없어 읽기·디버깅까지만 된다.

```sh
tar xf openocd-macos-arm64.tar -C ~/hdd/tools/hpmicro/
~/hdd/tools/hpmicro/openocd/bin/openocd --version   # 0.12.0+dev
```

cfg 는 `HPM_SDK_BASE` 를 요구하지 않도록 `tools/openocd/` 아래로 복사해두었다.
`-s tools/openocd` 로 검색 경로만 넣어주면 `[find ...]` 가 풀린다.

### 1.3 파이썬

pip 패키지는 쓰지 않는다. 업데이터는 **libhidapi 를 ctypes 로 직접** 부른다.

```sh
brew install hidapi          # tools/iap_update.py — 펌웨어 굽기
pip3 install pyserial        # CLI 접속 (선택)
```

### 1.4 프로브

| 용도 | 프로브 |
|---|---|
| **플래시 기록 · 디버깅** | FT2232 계열 (HPM5300EVK 온보드 디버거 등) |
| 메모리 읽기만 | J-Link — 단, 정품이어야 한다 |

> 클론 J-Link 은 SEGGER DLL 이 연결 자체를 거부한다(`0xFFFFFEFA`). 그리고
> **클론에 SEGGER 펌웨어 업데이트를 수락하면 안 된다** — 벽돌이 된다.
> OpenOCD 는 그런 검사가 없어 클론에서도 읽기는 된다.

### 3.2 JTAG — 앱이 죽었을 때

## 4. 디버그

### 4.1 CLI (USB CDC)

**macOS 에서는 반드시 `/dev/cu.*`** — `/dev/tty.*` 는 캐리어를 기다려 블록된다.

```sh
python3 - <<'PY'
import serial, time
p = serial.Serial("/dev/cu.usbmodem00011", 115200, timeout=0.3)
p.dtr = True; p.rts = True
time.sleep(0.3); p.reset_input_buffer()
p.write(b"help\r\n"); time.sleep(1)
print(p.read(8192).decode())
PY
```

명령: `help` · `reset info|boot|reset` ·
`ws2812 info|all|set|off|limit|prio|group|test|rainbow` ·
`keys layout|show|learn|key|base|map|watch|noise|dump|time|info` · `log` · `usb`

### 4.2 RAM 링버퍼 (JTAG)

USB 가 올라오기 전이나 죽은 뒤에도 로그를 읽는다. `.noinit` 이라 리셋해도 남는다.
주소는 빌드마다 바뀌므로 ELF 에서 뽑는다.

```sh
A=$(riscv-none-elf-objdump -t build/wish60-he.elf | grep -w log_ram | awk '{print "0x"$1}')
openocd ... -c "dump_image log.bin $A 0x810" -c "exit"

python3 -c "
import struct; d=open('log.bin','rb').read()
m,i,w,s=struct.unpack('<IIII',d[:16])
print((d[16+i:16+s]+d[16:16+i]).decode('utf-8','replace') if w
      else d[16:16+i].decode('utf-8','replace'))"
```

헤더는 `magic('RLOG') / index / wrapped / size` 4 워드다.

## 5. USB 구성

| 항목 | 값 |
|---|---|
| VID / PID | `0x0483` / `0x5304` |
| 제품 문자열 | `WISH60-HE` |
| 속도 | High Speed (480 Mb/s) |
| 클래스 | `0xEF / 0x02 / 0x01` (Misc / Common / **IAD**) |

| IF | 클래스 | 엔드포인트 | 용도 |
|---|---|---|---|
| 0 | HID (`0xFF60`) | `0x84` IN / `0x04` OUT, 32 B | 설정 · **부트로더 점프** |
| 1 | CDC 제어 | `0x83` INT | ┐ IAD 로 묶인다 |
| 2 | CDC 데이터 | `0x81` IN / `0x01` OUT | ┘ |

7편에서 부트 키보드가 들어오면 그것이 IF0 을 가져가고 나머지가 한 칸씩 밀린다 —
일부 BIOS 가 첫 인터페이스만 보기 때문이다. 호스트 도구는 인터페이스 번호가 아니라
**usage page 로 찾으므로** 밀려도 고칠 것이 없다.

PID 는 자체 키보드 저장소들과 같은 체계다. 이미 쓰는 값 — `0x5201`~`0x5207`,
`0x5210`, `0x5230`, `0x5301`~`0x5303`.

**윈도우 드라이버는 필요 없다.** Win10/11 은 IAD 복합 장치를 `usbccgp` 로 잡고 CDC
기능에 `usbser.sys` 를 자동 바인딩한다. HID 는 애초에 클래스 드라이버가 처리한다.
(Win7/8.1 은 CDC 자동 바인딩이 없어 INF 가 필요하다.)

## 6. 복구

앱이 매직을 갖고 있으면 부트로더는 계속 그리로 점프한다. 앱이 초기화 중 멈추면
자동 복구가 안 걸리므로 아래 중 하나를 쓴다.

| 경로 | 방법 | 조건 |
|---|---|---|
| **부트로더 핀** | 핀을 잡고 전원 인가 → 업데이트 모드 | **언제나** |
| **HID 점프 / `reset boot`** | `iap_update.py` 가 알아서 한다 | 앱이 살아 있을 때 |
| **JTAG** | `0x20000` 섹터를 소거 | 프로브를 붙일 수 있을 때 |
| **전체 복원** | 보드 원본 플래시 이미지(1MB)를 `0x80000000` 에 | |

> **부트로더 핀은 실전에서 검증됐다.** 부팅 초반에 리셋 루프로 빠지는 펌웨어를 구워
> USB 열거가 아예 안 되는 상태가 됐을 때, JTAG 없이 이 핀만으로 되굽었다.

### 부팅 경로에 플래시 작업을 넣을 때

한 번 여기서 브릭을 만들었다. "부팅이 N회 연속 실패하면 스스로 부트로더로 간다"는
안전망을 넣었는데, 그 판단이 **초기화 아주 이른 시점에서 플래시 소거·기록**을 한다는
게 문제였다. CLI 의 `reset boot` 는 완전히 초기화된 뒤라 검증됐지만 그 이른 경로는
아니었고, 기록이 실패하자 조용히 리턴해 **그대로 리셋 루프에 남았다.**

교훈은 둘이다.

- 부팅 경로의 플래시 작업은 **실패했을 때 어디로 가는지까지** 설계해야 한다
- 안전망이 덮는 범위를 정직하게 따져야 한다. 그 카운터는 `.noinit`(RAM)에 있어
  전원을 빼면 사라지므로 **따뜻한 리셋 루프만** 잡았다. 정작 위험한 "부팅 중 멈춤"은
  못 잡으면서 위험만 추가한 셈이다. 그 경우는 부트로더 핀이 이미 덮고 있었다

부트로더의 업데이트 명령은 기록 주소를 `0x80020000` 으로 하드코딩하므로
**USB 로는 부트로더 자신을 덮어쓸 수 없다.**
