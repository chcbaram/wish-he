# WISH HE 펌웨어 — 만드는 과정

홀이펙트 키보드 펌웨어를 처음부터 만든다. 보드의 IAP 부트로더는 그대로 두고
`0x80020000` 부터를 앱 자리로 쓴다. 최종 목표는 8kHz 스캔과 래피드 트리거지만, 먼저
**완전히 동작하는 평범한 키보드**를 만든다.

- 보드: HPM5361 (RISC-V, 400MHz), 아날로그 MUX + ADC 로 64키, WS2812 83개
- 배선: **없다.** UART 헤더도 디버그 LED 도 없는 보드라 USB 하나로 굽고 디버깅한다
- 자리: 플래시 `0x80020000` 부터 384KB. 부트로더와 EEPROM 은 건드리지 않는다

```
ROM → 부트 헤더 → 부트로더(0x80003000) → 매직 확인 → 본 펌웨어(0x80020004)
```

지연도 같이 본다 — `keys lat run 200 8` 뒤 `keys lat` 에서 **판정→ACK 평균 97us** 근처다.

**지금 배포본은 `V260822R1`** (2026-08-22). 버전은 `src/hw/hw_def.h` 하나가 출처이고,
`tools/make_release.py` 가 거기서 읽어 웹앱에 바로 쓴다.

**바로 이어서 할 것** — 남은 큰 것 셋이다.

  · **A2 의 실제 빈도** — 잡음만으로 기준값 래치가 얼마나 나는가. **굽지 않고
    아무도 안 치는 상태로 오래 둬야** 나온다. `dev.py stat clear` 로 창을 잡고
    몇 시간 두었다가 `keys info` 의 `latch` 를 본다. 굽는 순간 카운터가 리셋되므로
    **다른 작업과 같이 못 한다** — 자리를 비울 때 걸어 두는 것이 맞다
  · **C9 플래시 쓰기가 루프를 30ms 멎게 한다** — 설정 저장 30.4ms, 프로파일 전환
    33.2ms. 소거는 1ms 뿐이라 **나머지는 쓰기다**(설정 6340B). 페이지(256B)로 쪼개
    부르면 30ms 한 창이 1ms 창 여럿이 된다. ★ USB 드라이버가 ILM 에 올라가 있어
    **쓰는 동안 인터럽트를 열어 두는 길도 열렸다**(cherryusb·SDK 31KB 는 아직 플래시)
  · **군지연 28us** — 3탭 이동합을 스캔 세 바퀴에 걸쳐 더해서 붙는 값이다. 같은 표본
    수를 **한 스텝 안에서 두 번** 재면(시퀀스 4→8) 0 이 된다. 지금 남은 지연 중
    유일하게 줄일 수 있는 자리다 (18편)

**손으로 해야 할 확인 둘** (자동 시험이 못 한다).

  · **B8 리모트 웨이크업** — 맥을 재우고 키를 눌러 깨어나는지 본다. 깬 뒤
    `ioreg -c IOUSBHostDevice -w0 -l | grep kPortStatRemoteWakeCount` 가 늘었으면
    우리가 깨운 것이다. 이어서 `dev.py cli "qmk held"` 로 눌린 키가 없는지 본다
  · **B10 재열거** — "전원은 유지된 채 버스 리셋만" 이 필요한데 macOS 에서 그것만
    일으킬 수단이 없다. 뽑았다 꽂으면 장치가 리부팅되어 시험이 안 된다

**도구는 이제 갖춰져 있다.**

```
keys inject <st> <ch> d <um>     깊이로 주입 — 실제 키를 안 누르고 시험한다
keys inject noise <pp> [tail]    잡음을 얹는다 (꼬리 분포라야 드문 사건이 난다)
keys inject fail on|off          DMA 대기를 일부러 실패 (.noinit — 리셋을 넘는다)
keys inject live on|off          호스트로 내보낼지 (기본 끔)
keys cfg press|release <um>      입력·해제지점 (웹앱 없이)
qmk held                         호스트가 눌린 것으로 아는 키 — 매트릭스와 다른 것
qmk proto [0|1]                  HID 프로토콜 (0 = BIOS 가 쓰는 부트, 시험용)
dev.py cli -w <초> "<명령>"       오래 도는 명령을 기다린다
dev.py stat clear                진단 카운터를 0 으로 (깨끗한 창)
he_test.py [무리...]             누적 검증 26항목, 표로 나온다
qmk info 의 `루프 한 바퀴`       루프가 통째로 멎은 최대 시간 — task_us 에는 안 남는다
keys lat                         눌림→ACK 구간별 최소·평균·최대
keys lat run <n> [ms]            장치가 스스로 두드린다 (간격은 매번 새로 뽑는다)
keys lat dump                    표본 400개를 그대로 — 평균으로는 모양이 안 보인다
```

★ **시험 키는 F23/F24 를 쓴다.** F13~F15 는 macOS 에서 화면 밝기·스크린샷이다 —
  연타 시험이 그걸 수십 번 쏘아 화면이 캄캄해진 적이 있다.

★ **ILM 이 66% 찼다** (128KB 중 87KB). QMK·보드훅·hw 드라이버가 통째로 올라가 있다.
  코드가 늘면 넘칠 수 있으니 **빌드 로그의 ILM 줄을 본다.** 넘쳤을 때 무엇을 뺄지는
  아직 안 정해 뒀다 (18편).

★ **`.ld` 를 만졌으면 `build/*.elf` 를 지우고 다시 빌드한다.** 링커 스크립트만 고치면
  재링크가 안 걸린다.

★ **시험이 바꾼 것은 시험이 되돌린다.** 설정뿐 아니라 **기준값·누적 카운터·리포트
  상태**도 바꾼다. 하루에 네 번 빠뜨렸다 (17편에 표로 있다).

- [ ] **상향 글리치 한 방에 기준값이 영구히 래치된다 — 실측 확인** (A2)

      ```

      2) +100/표본 글리치 (2초)        latch 1 로 증가
      3) 정상값으로 되돌림             깊이 276 카운트

      ```

      276 카운트는 약 0.86mm 다. **입력지점을 0.75mm 이하로 쓰면 그 키는 영원히
      눌린 채**가 된다. 회복은 재보정(`keys base`)이나 재부팅뿐이다.

      **종단간까지 재현했다 — 잡음 주입으로.**

      ```
      잡음 주입(꼬리 분포) -> 래치 -> 기준값이 7470 에서 8071 로 +601 갇힘
        -> 깊이 598 > 입력지점 334  ->  그 키가 눌린 것으로 보고됨
        -> 주입을 꺼서 실물 ADC 로 돌아와도 그대로  ->  재보정만이 복구
      ```

      **래치율은 잡음이 아니라 드리프트에 묶여 있다.** 잡음 폭을 올려 가며 30초씩
      쟀더니 이렇게 나왔다 (한 셀, 표본당 p-p):

      | p-p | 40 | 60 | 80 | 100 | 140 | 200 |
      |---|---|---|---|---|---|---|
      | 래치/30초 | 0 | 1 | 1 | 1 | **0** | **0** |

      가운데가 평평한 이유 — 래치 뒤 기준값이 5.9카운트/초로 내려와야 다음 래치가
      가능하다. 상한이 **16초에 한 번**이라 잡음을 키워도 안 늘어난다.

      ★ **끝의 0 이 더 중요하다.** 잡음이 크면 기준값이 초반에 잡음 천장 **위로**
        올라가 갇히고, 그 뒤로는 아무 표본도 그걸 못 넘어 래치가 **멎는다.**
        래치가 0 인 것이 안전하다는 뜻이 아니라 **이미 굳었다는 뜻이다.**

      ★ 실측 잡음은 누적 눈금 **p-p 평균 44 / 최대 51** 이다 (`keys noise 3000`).
        p-p 40 을 주입해도(누적으로 실제의 1.6배) 30초에 0 회였다 — 잡음만으로는
        문턱(93)에 잘 안 닿는다는 뜻이다.

      ★ **다만 주입 잡음은 백색이고 실물은 아니다.** 문서의 닫힌 항목이 누적을
        늘려도 **N^-0.2** 로만 준다고 실측해 뒀다 (백색이면 N^-0.5). 표본끼리 강하게
        상관돼 있어 꼬리 모양이 다를 수 있다 — 가속 외삽의 한계다.

      **그래서 남은 것은 실물 장시간 측정이다.** `dev.py stat clear` 로 창을 잡고
      아무도 안 치는 상태로 오래 두면 잡음만의 래치율이 나온다.

      ★ 그리고 잡음이 아니어도 난다 — **기구 변형**(핫스왑 재장착, 플레이트 휨,
        키캡 측압)은 93 을 쉽게 넘고, 그쪽이 실제 원인일 가능성이 더 크다.

      ### 왜 데이터시트만으로는 우리 보드의 곡선이 안 나오는가

      **세기는 모양을 안 정한다.** 정규화하면 `Br/2` 가 약분되어 사라지고 `f(z)` 만
      남는다 — 순전히 기하다. 그래서 셈이 이렇게 된다.

      ```
      모양을 정하는 데 필요한 것   R, L, z0        3개
      데이터시트가 주는 것         두 점의 비       1개   ← 절대값은 정규화로 날아간다
      ```

      **나머지 둘은 찍은 값이다.** 그게 이번 어긋남의 전부다.

      그리고 z0 가 제일 크다. 유효 갭에는 **PCB 두께 + 패키지 안 홀 소자 깊이 +
      공기 간격**이 전부 들어가는데, 우리 PCB 가 1.6mm 다.

      | 유효 갭이 이만큼 다르면 | 곡선 차 | 거리로 |
      |---|---|---|
      | 0.2 mm | 164 카운트 | 18.7 µm |
      | 0.4 mm | 324 카운트 | 37.3 µm |
      | **1.6 mm (PCB 한 장)** | **1243 카운트** | **136.7 µm** |

      **잡음 바닥이 100µm 다.** 제조사가 어느 면에서 쟀는지 모르는 채로는 여기를
      맞출 수가 없다. 스위치 기하 논쟁(27µm)보다 훨씬 큰 항이다.

      ★ **자석을 직접 재봤는데 오히려 안 맞았다.** 지름 2.8 / 높이 3.4 (실측)로
        데이터시트 두 점을 풀면 **Br 3.19 T** 가 필요하다 — NdFeB 상한 1.45T 의
        두 배가 넘는다. 현실적인 Br 로 바닥 720Gs 를 맞추면 3.4mm 떨어진 곳이
        105~115Gs 여야 하는데 데이터시트는 160Gs 다. 두 자속을 잰 지점의 간격이
        전 행정의 72~77% 여야 앞뒤가 맞는다.

        즉 **물리적으로 제일 정직한 값이 결과는 제일 나쁘다.** 이 모델은 물리
        모델이 아니라 맞추기 모델이고, z0 와 Br 이 오차를 흡수하고 있었다.
        `keys.c` 가 z0 를 "유효 갭" 이라 부른 것이 정확했다.

      ### 역산도 해봤다 — 되지만 한 점으로는 모자란다

      자석 기하를 재고 나면 미지수가 z0 하나다. 15편의 실측 한 점(실제 2.00mm 를
      눌러 1.25mm 로 읽힘)에서 풀면 **z0 = 4.12mm** 가 나온다. PCB 두께를 따로
      알 필요가 없다 — 통째로 흡수된다. 그런데 민감하다.

      | 읽힌 값 | 역산된 z0 | 곡선이 움직이는 양 |
      |---|---|---|
      | 1.20 mm | 3.68 mm | 492 카운트 |
      | 1.25 mm | 4.12 mm | (기준) |
      | 1.30 mm | 4.61 mm | 487 카운트 |

      **0.05mm 흔들리면 곡선이 1.5% 움직인다.** 가리려던 차이(3.8%)의 절반이다.
      제대로 하려면 여러 점을 재서 최소자승으로 맞춰야 하고, 그건 결국 실측 표
      기능 그 자체다. 그래서 그때 한꺼번에 한다.

        버퍼를 CPU 가 쓰고, 매 루프 색이 바뀌는 효과는 한 프레임도 못 낸다. 그 위험을
        10us 를 넷으로 쪼개자고 질 이유가 없다.

      `ws2812 enc` 로 언제든 다시 갈라 잴 수 있다

- [x] ~~태스크 최대 1685us 가 어디서 나는지~~ — **플래시 쓰기다.** 유도해서 재현했다.

      | 유도한 것 | task_max | scan_max |
      |---|---:|---:|
      | 가만히 12초 | 141 | 203 |
      | HID 연타 8초 | 133 | 90 |
      | **프로파일 전환 x4** | **778** | **1084** |
      | 설정 쓰기 x6 (저장) | 447 | 590 |
      | 부팅 직후 | 503 | 731 |

      앞서 못 잡은 이유는 셋을 각각 **한 번씩만** 해 봤기 때문이다. 플래시를 여러 번
      연달아 굽게 하니 바로 나왔다. 1685us 는 그 꼬리다.

      ★ **고칠 것이 아니다.** XIP 라 플래시를 지우는 동안 인터럽트를 막아야 하고,
        그동안은 스캔도 리포트도 멈춘다. 대신 —

        - 타이핑 중에는 안 일어난다. 저장은 조용해진 뒤에 한 번(`keysCfgTouch`),
          프로파일 전환·보정 저장은 사용자가 시킬 때뿐이다
        - USB 쪽 피해는 이미 막아 뒀다 — 놓친 전송 완료를 `tx_pending` 으로 들고
          있다가 자리가 나면 보낸다 (`hid_if.c`, 11편)
        - 한 번에 한 섹터만 굽는다 (`eeprom.c`). 네 섹터를 한꺼번에 지우면 그 창이
          네 배가 된다

      ★ `scan_max` 가 `task_max` 보다 크다. 스캔은 ADC 가 모는 별도 경로지만
        `keysUpdate()` 자체는 메인 루프라 같이 막힌다. 최대값을 볼 때 이 둘을
        따로 읽을 이유가 없다

- [ ] **RT 실사용 튜닝** (사용자 필요) — 재단은 끝났으니 감이 아니라 숫자로 정할 수
      있다. `keys learn` 이 눌림 에지마다 한 줄을 찍으므로, 한 키를 평소 속도로 열 번
      눌러 열 줄이 나오는 최소값이 **내 손의 하한**이다. 그 위는 취향이다

### 규칙 (지키기)

- **키보드 그림에 무엇을 칠할지는 그 화면이 정한다** — `heSlice.overlayKeys`.
  화면에 들어갈 때 자기 것을 넣지 않으면 앞 화면의 표시가 그대로 남는다.
  `null` = "보여줄 것 없으니 선택을 보여라", `[]` = "칠할 것이 없다"
- **i18n 키는 세 벌(en·ko·ja)을 함께 채운다** — 이 앱은 영어 문장을 그대로 키로
  쓰는데, `en.json` 에 없으면 영어에서 키 문자열이 그대로 나온다. 실제로 툴팁
  4개가 그렇게 나가고 있었다. 낱말이 이미 다른 뜻으로 쓰이면(`Flash` → "플래시")
  문장을 늘리지 말고 `he.fw.flash` 처럼 이름 공간을 준다
- **키캡 각인 스타일은 화면이 정한다** — 키 하나하나의 데이터가 정하면 같은 화면
  안에서 들쭉날쭉해진다. HE 탭은 값이 하나도 없어도 `keyLabels` 를 늘 넘겨
  `compact` 를 켠다. 값은 그 자리에 들어왔다 나갔다 할 뿐이다
- **HID 명령을 더하면 옛 펌웨어를 생각한다** — 모르는 하위 명령이 오면 옛 펌웨어는
  엉뚱한 응답을 주고, VIA 는 에코가 어긋난 것을 오류로 잡는다. 폴링 안에서 쌓이면
  **진짜 오류를 못 본다.** 도구는 한 번 실패하면 그만 물어야 한다
- **플래시를 쓰면 인터럽트가 6ms 꺼진다** — XIP 라 어쩔 수 없다. 그동안 USB 전송
  완료 인터럽트를 놓치면 `is_tx_busy` 가 굳고, 그 뒤 응답이 **조용히 버려진다.**
  못 보낸 응답은 들고 있다가 자리가 나면 보내고, 50ms 가 지나면 놓친 것으로 보고
  되살린다 (`hid_if.c`). 느린 것이 플래시만은 아니다 — 조명을 다시 켜는 일도
  ISR 에서 하면 USB 가 멈춘다
- **HID 왕복은 한 줄로 세운다** — 요청 하나에 응답 하나다. 라이브 트래킹·보정
  폴링·전 키 읽기·슬라이더 쓰기가 동시에 나가면 응답이 엇갈린다. 부르는 쪽마다
  조심하게 하면 반드시 하나를 놓치므로 `send` 자체를 직렬화한다 (`he-api.ts` 가 앱
  전체 몫으로 들고 있다). **VIA 자신이 부르는 길**(키맵·매크로)도 `heLock` 으로 같은
  줄에 세운다 — 이걸 빠뜨려 응답이 엇갈렸다. 폴링 한 회차가 여러 왕복이면 `setInterval` 도 쓰지 않는다 — 주기
  안에 못 끝내면 회차가 겹친다. 끝난 뒤에 다시 건다
- **버튼 폭은 고정 숫자로 맞추지 않는다** — 번역마다 길이가 달라 반드시 어긋난다.
  `min-width` 로 바닥을 주되 가장 긴 번역이 넘지 않는 낱말을 고른다
- **수명이 다르면 기록을 나누고, 버전도 따로 준다** — 보정(이 개체를 잰 값)·설정(취향)·
  스위치 정의(데이터시트 값)는 잃어도 되는 정도가 전부 다르다. 버전을 하나로 묶어 두면
  한쪽을 고칠 때 나머지까지 버린다. `keysBlobValid` 가 버전을 인자로 받는 이유다
  ([11편](11-via.md))
- **번호로 가리키는 것을 목록 뒤에 이어 붙이지 않는다** — 커스텀 스위치를 내장 표 뒤에
  붙였으면, 나중에 내장이 한 줄 늘 때 구조체가 안 바뀌어 **버전도 안 올라가고 기록도
  유효한 채로** 모든 키가 옆 것을 가리킨다. 비트로 갈라 두면(`sw_type & 0x80`) 그럴
  일이 없다
- **저장 자리는 손으로 더하지 않고 구조체로 선언한다** — `+0`, `+p*8` 로 잡았다가
  탭홀드와 0번 프로파일 조명이 **같은 바이트**에 앉았다. 총량만 보는
  `_Static_assert` 는 그걸 못 잡는다. 구조체로 선언하면 자리는 컴파일러가 잡고
  겹칠 수가 없다 (`via_port.c` 의 `ee_user_t`). 이미 쓰는 보드가 있으면 **자리를
  옮기는 쪽이 무엇을 잃는지**부터 본다 — 여기서는 불리언 하나를 잃는 쪽을 골랐다
  ([11편](11-via.md))

### 규칙 (지키기) — 이어서

- **장치에 직접 붙어 본다** — `tools/dev.py` (CLI 는 CDC, 설정 채널은 HID).
  "굳는다", "값이 0 이다" 같은 증상은 원인을 안 알려준다. 웹 도구를 통해서만 보면
  펌웨어인지 앱인지 못 가른다 — 짐작으로 고치다 두 번 빗나갔다. 직접 붙으면 한 번에
  갈린다 (`dev.py burst` 가 응답 소실을, `dev.py stat` 이 페이지 어긋남을 잡았다)
- **HID 한 프레임은 32바이트다** (`HID_EP_MPS`). 앞 4바이트를 빼면 LE32 를 일곱 개.
  값이 더 많으면 **페이지로 나눈다.** 한 번에 담으려다 `tx_report[32]` 를 28바이트
  넘겨 썼다 — ISR 안에서 남의 메모리를 밟는 짓이고, 컴파일러는 상수 첨자만 잡아 준다
- **문자열은 숫자 뒤에 이어 붙이지 않는다** — 숫자가 늘면 자리가 밀려 도구가 엉뚱한
  바이트를 읽는다. 고정 자리나 별도 페이지에 둔다

번호는 순서가 아니라 편 번호다. 9편을 5편보다 먼저 했다 — **JTAG 배선 없이 굽게 되면서**
이후 시행착오 비용이 크게 줄었고, 스캔처럼 반복이 많은 작업 전에 해둘 값어치가 있었다.

VIA 는 키맵을 장치에 저장해야 하므로 **8편(EEPROM)이 먼저**다. 앱 뒤쪽
`0x80080000` 부터가 그 자리다 ([00-hardware.md](00-hardware.md) 2절).

**VIA 프로토콜을 직접 구현하지 않는다.** QMK 의 `quantum/via.c` 와
`dynamic_keymap.c` 가 이미 그 일을 한다. 우리가 만들 것은 `port/` 쪽 —
`matrix_scan()` 이 `keysGetRow()` 를 읽게 하고, EEPROM 백엔드를 8편의 플래시 계층에
연결하고, HID 리포트 송신을 우리 CherryUSB 로 돌리는 어댑터다. 그래서 **10편(QMK)이
11편(VIA)보다 먼저** 온다.

**GUI 는 따로 만들지 않는다.** 11편에서 VIA 웹앱을 포크해 HE 기능을 얹는 것이 목표이고,
래피드 트리거 튜닝 화면도 거기에 붙인다. 그전까지 필요한 관측은 CLI 로 충분하다
(`keys bar` / `keys watch`).

레이아웃은 이미 펌웨어 안에 바이너리로 들어 있다 — `keys_geo[]` 가 키마다
`{x, y, w, h, row, col}` 6바이트(1/4 키유닛)다. raw HID 로 이걸 내보내면
**웹 도구가 JSON 파일 없이 장치만 보고** 배치를 그릴 수 있다.

- 부트로더를 보존한 채 **콜드 부팅으로 앱이 400MHz 로 뜬다**
- 배선 없는 콘솔 — USB CDC + CLI, 그리고 죽은 뒤에도 읽히는 RAM 링버퍼
- 펌웨어에서 **스스로 부트로더로 돌아간다** — CLI `reset boot`, 또는 HID 명령
- LED 83개를 **CPU 개입 없이** — SPI + DMA 로 2112바이트 한 방
- 64키 전체를 **38us 에 훑는다** — 8kHz(125us) 예산의 30%
- 설정·보정이 전원을 꺼도 남는다 — 저장 **2~3ms**, 키별 스트로크 편차 16% 실측
- 기준값이 스스로 따라간다 — 누른 채 부팅해도, 온도가 변해도 (전 셀 잔차 ±1)
- **키보드로 동작한다** — 63키 매핑, HID 부트 키보드, 8kHz 폴링(125us) 확인
- **JTAG 없이 USB 로만, 사람 손 없이 굽는다** — HID 명령으로 부트로더에 넣고 87KB 0.9초
- 복구 경로가 셋 (JTAG · 업데이트 모드 · 강제 스트랩), 그리고
  **USB 로는 부트로더 자신을 덮어쓸 수 없다** — 벽돌이 되지 않는다

## 1. 개발 환경

### 1.1 툴체인 — xPack RISC-V GCC

이 프로젝트는 **hpm_sdk 에 의존하지 않는다.** 필요한 SoC 헤더·드라이버·링커
스크립트는 `src/bsp/` 아래로 들여왔다. 그래서 준비할 것은 컴파일러뿐이다.

```sh
# https://github.com/xpack-dev-tools/riscv-none-elf-gcc-xpack/releases
tar xf xpack-riscv-none-elf-gcc-13.4.0-1-darwin-arm64.tar -C ~/hdd/tools/
export HPM_RISCV_TOOLCHAIN_DIR="$HOME/hdd/tools/xpack-riscv-none-elf-gcc-13.4.0-1"
```

`HPM_RISCV_TOOLCHAIN_DIR` 은 **디렉토리든 `gcc` 실행 파일 경로든** 받는다. 안 잡히면
`PATH` 에서 찾고, 그래도 없으면 CMake 가 `RISCV Toolchain not found` 로 멈춘다.
HPMicro 공식 툴체인(`riscv32-unknown-elf-`)도 그대로 쓸 수 있다 —
`tools/hpmicro-riscv-gcc.cmake` 가 두 접두어를 모두 안다.

### 1.2 OpenOCD — HPMicro 빌드여야 한다

플래시 기록에는 **`hpm_xpi` 드라이버가 들어간 HPMicro 배포판**이 필요하다.
homebrew 의 OpenOCD 에는 그 드라이버가 없어 읽기·디버깅까지만 된다.

```sh
tar xf openocd-macos-arm64.tar -C ~/hdd/tools/hpmicro/
~/hdd/tools/hpmicro/openocd/bin/openocd --version   # 0.12.0+dev
```

cfg 는 `HPM_SDK_BASE` 를 요구하지 않도록 `tools/openocd/` 아래로 복사해두었다.
`-s tools/openocd` 로 검색 경로만 넣어주면 `[find ...]` 가 풀린다.

### 1.3 파이썬

pip 패키지는 쓰지 않는다. 업데이터는 **libhidapi 를 ctypes 로 직접** 부른다.

```sh
brew install hidapi          # tools/iap_update.py — 펌웨어 굽기
pip3 install pyserial        # CLI 접속 (선택)
```

### 1.4 프로브

| 용도 | 프로브 |
|---|---|
| **플래시 기록 · 디버깅** | FT2232 계열 (HPM5300EVK 온보드 디버거 등) |
| 메모리 읽기만 | J-Link — 단, 정품이어야 한다 |

> 클론 J-Link 은 SEGGER DLL 이 연결 자체를 거부한다(`0xFFFFFEFA`). 그리고
> **클론에 SEGGER 펌웨어 업데이트를 수락하면 안 된다** — 벽돌이 된다.
> OpenOCD 는 그런 검사가 없어 클론에서도 읽기는 된다.

## 2. 빌드

```sh
export HPM_RISCV_TOOLCHAIN_DIR="$HOME/hdd/tools/xpack-riscv-none-elf-gcc-13.4.0-1"
cmake -B build -DCMAKE_BUILD_TYPE=Release .

```

키보드 모델은 `keyboards/` 아래에 있고 `-DHW_KEYBOARD=<모델>` 로 고른다 (기본
`wish60-he-7u`). 레이아웃을 고쳤으면 먼저 생성물을 다시 만든다.

```sh
python3 tools/gen_keymap.py            # layout-kle.json -> layout-via.json + layout.h
```

산출물 `build/wish60-he.bin` 은 `0x80020000` 부터의 이미지다. 선두 4바이트가
`48 50 4D 0A`(`"HPM\n"`) 여야 부트로더가 인식한다.

```sh
xxd -l 8 build/wish60-he.bin
# 00000000: 4850 4d0a 9711 0680    HPM.....
```

## 3. 기록

### 3.1 USB — 평소에는 이걸 쓴다

```sh
python3 tools/iap_update.py build/wish60-he.bin
```

이 한 줄이 전부다. 앱이 돌고 있으면 **HID 로 부트로더 진입을 요청**하고, 열거를
기다린 뒤 기록한다. 87KB 에 약 0.9초. VSCode 에서는 `flash-usb` 태스크.

→ [09-iap-updater.md](09-iap-updater.md)

### 3.2 JTAG — 앱이 죽었을 때

```sh
openocd -s tools/openocd -f hpm5361-fw.cfg \
  -c "adapter speed 4000" -c "init" -c "reset halt" -c "flash probe 0" \
  -c "flash write_image erase build/wish60-he.bin 0x80020000 bin" \
  -c "verify_image build/wish60-he.bin 0x80020000 bin" \
  -c "reset run" -c "exit"
```

`0x80020000` 부터만 쓰므로 부트로더와 EEPROM 은 건드리지 않는다.

> `init` 다음에 `reset halt` 를 넣는다. 앱이 돌던 상태에서 바로 `halt` 하면
> 플래시 로더 실행이 실패하는 경우가 있다.

## 4. 디버그

### 4.1 CLI (USB CDC)

**macOS 에서는 반드시 `/dev/cu.*`** — `/dev/tty.*` 는 캐리어를 기다려 블록된다.

```sh
python3 - <<'PY'
import serial, time
p = serial.Serial("/dev/cu.usbmodem00011", 115200, timeout=0.3)
p.dtr = True; p.rts = True
time.sleep(0.3); p.reset_input_buffer()
p.write(b"help\r\n"); time.sleep(1)
print(p.read(8192).decode())
PY
```

명령: `help` · `reset info|boot|reset` ·
`ws2812 info|all|set|off|limit|prio|group|test|rainbow` ·
`keys layout|show|learn|key|base|map|watch|noise|dump|time|info` · `log` · `usb`

### 4.2 RAM 링버퍼 (JTAG)

USB 가 올라오기 전이나 죽은 뒤에도 로그를 읽는다. `.noinit` 이라 리셋해도 남는다.
주소는 빌드마다 바뀌므로 ELF 에서 뽑는다.

```sh
A=$(riscv-none-elf-objdump -t build/wish60-he.elf | grep -w log_ram | awk '{print "0x"$1}')
openocd ... -c "dump_image log.bin $A 0x810" -c "exit"

python3 -c "
import struct; d=open('log.bin','rb').read()
m,i,w,s=struct.unpack('<IIII',d[:16])
print((d[16+i:16+s]+d[16:16+i]).decode('utf-8','replace') if w
      else d[16:16+i].decode('utf-8','replace'))"
```

헤더는 `magic('RLOG') / index / wrapped / size` 4 워드다.

## 5. USB 구성

| 항목 | 값 |
|---|---|
| VID / PID | `0x0483` / `0x5304` |
| 제품 문자열 | `WISH60-HE` |
| 속도 | High Speed (480 Mb/s) |
| 클래스 | `0xEF / 0x02 / 0x01` (Misc / Common / **IAD**) |

| IF | 클래스 | 엔드포인트 | 용도 |
|---|---|---|---|
| 0 | HID (`0xFF60`) | `0x84` IN / `0x04` OUT, 32 B | 설정 · **부트로더 점프** |
| 1 | CDC 제어 | `0x83` INT | ┐ IAD 로 묶인다 |
| 2 | CDC 데이터 | `0x81` IN / `0x01` OUT | ┘ |

7편에서 부트 키보드가 들어오면 그것이 IF0 을 가져가고 나머지가 한 칸씩 밀린다 —
일부 BIOS 가 첫 인터페이스만 보기 때문이다. 호스트 도구는 인터페이스 번호가 아니라
**usage page 로 찾으므로** 밀려도 고칠 것이 없다.

PID 는 자체 키보드 저장소들과 같은 체계다. 이미 쓰는 값 — `0x5201`~`0x5207`,
`0x5210`, `0x5230`, `0x5301`~`0x5303`.

**윈도우 드라이버는 필요 없다.** Win10/11 은 IAD 복합 장치를 `usbccgp` 로 잡고 CDC
기능에 `usbser.sys` 를 자동 바인딩한다. HID 는 애초에 클래스 드라이버가 처리한다.
(Win7/8.1 은 CDC 자동 바인딩이 없어 INF 가 필요하다.)

## 6. 복구

앱이 매직을 갖고 있으면 부트로더는 계속 그리로 점프한다. 앱이 초기화 중 멈추면
자동 복구가 안 걸리므로 아래 중 하나를 쓴다.

| 경로 | 방법 | 조건 |
|---|---|---|
| **부트로더 핀** | 핀을 잡고 전원 인가 → 업데이트 모드 | **언제나** |
| **HID 점프 / `reset boot`** | `iap_update.py` 가 알아서 한다 | 앱이 살아 있을 때 |
| **JTAG** | `0x20000` 섹터를 소거 | 프로브를 붙일 수 있을 때 |
| **전체 복원** | 보드 원본 플래시 이미지(1MB)를 `0x80000000` 에 | |

> **부트로더 핀은 실전에서 검증됐다.** 부팅 초반에 리셋 루프로 빠지는 펌웨어를 구워
> USB 열거가 아예 안 되는 상태가 됐을 때, JTAG 없이 이 핀만으로 되굽었다.

### 부팅 경로에 플래시 작업을 넣을 때

한 번 여기서 브릭을 만들었다. "부팅이 N회 연속 실패하면 스스로 부트로더로 간다"는
안전망을 넣었는데, 그 판단이 **초기화 아주 이른 시점에서 플래시 소거·기록**을 한다는
게 문제였다. CLI 의 `reset boot` 는 완전히 초기화된 뒤라 검증됐지만 그 이른 경로는
아니었고, 기록이 실패하자 조용히 리턴해 **그대로 리셋 루프에 남았다.**

교훈은 둘이다.

- 부팅 경로의 플래시 작업은 **실패했을 때 어디로 가는지까지** 설계해야 한다
- 안전망이 덮는 범위를 정직하게 따져야 한다. 그 카운터는 `.noinit`(RAM)에 있어
  전원을 빼면 사라지므로 **따뜻한 리셋 루프만** 잡았다. 정작 위험한 "부팅 중 멈춤"은
  못 잡으면서 위험만 추가한 셈이다. 그 경우는 부트로더 핀이 이미 덮고 있었다

부트로더의 업데이트 명령은 기록 주소를 `0x80020000` 으로 하드코딩하므로
**USB 로는 부트로더 자신을 덮어쓸 수 없다.**
