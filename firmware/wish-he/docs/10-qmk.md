# 10. QMK 를 matrix 아래에 얹기

> 전체 목차는 [README.md](README.md) 를 본다.

7편에서 키보드가 동작했지만 레이어도 매크로도 없었다. 그걸 직접 만드는 대신 QMK 를
얹는다. **다만 QMK 에게 키 판정을 맡기지는 않는다.**

## 어디를 QMK 에 맡기나

```
ADC 스캔 (자유 구동)  ──▶  깊이 판정 · 래피드 트리거(13편)  ──▶  matrix_row_t
                            ★ keys.c. QMK 아래다
                                        │
                                        ▼
                            QMK  matrix_scan() → 키맵 · 레이어 · 매크로 · VIA
                            ★ 이벤트 구동. 키가 바뀔 때만 비싸다
```

직접 만들면 시간이 다 들어가는 곳은 스캔이 아니라 그 위다 — 레이어, 탭홀드, 매크로,
키 오버라이드, 그리고 **VIA 프로토콜**. VIA 웹앱 호환은 결국 `via.c` 동작을 그대로
따라가야 하는데, 그럴 거면 `via.c` 를 쓰는 게 맞다.

반대로 아래쪽을 맡기지 않는 이유가 셋 있다.

**디바운스를 쓰지 않는다.** QMK 의 matrix 계층은 접점 스위치를 전제한다. 채터링을
걸러내려고 변화를 몇 ms 붙잡아 두는데, 홀이펙트는 접점이 없어 바운스가 없다. 그러니
디바운스는 걸러낼 것 없이 **지연만 더한다**(기본 5ms). 잡음은 6편의 데드밴드 필터와
눌림/해제 임계값 분리(히스테리시스)가 이미 처리하고, 둘 다 지연이 0 이다.

**래피드 트리거는 스캔 주기에서 돌아야 한다.** 0.1mm 단위 방향 반전을 보는 일이라
QMK 루프 주기에 묶이면 안 된다.

**QMK 는 변화가 있을 때만 비싸다.** `action_exec` 은 키가 바뀔 때만 돈다. 사람이
치는 속도로는 초당 수백 번이고 8kHz 폴링과 무관하다.

## 붙이는 면적

`quantum` 트리는 통째로 들어와 있지만 **CMake 에 적은 것만 컴파일한다.** 우리가 쓴
것은 `port/` 계층뿐이다.

| 파일 | 하는 일 |
|---|---|
| `port/matrix.c` | `keysGetRow()` 를 그대로 받는다. 디바운스 없음 |
| `port/driver_usb.c` | `host_keyboard_send()` → `hidKbdSetReportRaw()` |
| `port/via_hid.c` | raw HID 채널 ↔ `raw_hid_receive/send` |
| `port/platforms/eeprom.c` | RAM 섬도 + 지연 플러시 |
| `port/platforms/{timer,wait,bootloader,suspend}.c` | 거의 그대로 |

`matrix_scan()` 은 비트마스크를 복사만 한다. **비트 순서가 같아서** 변환이 없다 —
6편에서 `keysGetRow()` 를 QMK `matrix_row_t` 와 맞춰 만들어 둔 것이 여기서 값을 한다.

```c
for (uint8_t r = 0; r < MATRIX_ROWS; r++)
{
  curr[r]  = live ? keysGetRow(r) : 0;
  changed |= (matrix_row_t)(curr[r] ^ matrix[r]);
}
```

`live` 는 `keysIsReportEnabled()` 다. `keys` 명령이 도는 동안 0 을 주면 **QMK 가
스스로 "다 뗐다"고 보고 빈 리포트를 내보낸다** — 눌린 채 남는 키가 없다. 7편에서
ap.c 가 직접 하던 일을 여기로 옮겼다.

## 키맵도 KLE 에서 생성한다

`tools/gen_keymap.py` 가 `layout_qmk.h`(LAYOUT 매크로)와 `keymap.c` 를 같이 만든다.

**QMK 의 기본 키코드(0x0000~0x00FF)는 HID Usage ID 와 값이 같다.** 그래서 7편에서
만든 표를 그대로 쓸 수 있고, 예외는 우리가 내부용으로 잡았던 `0xF0(FN)` 하나뿐이라
`MO(1)` 로 바꾼다. FN 레이어에는 숫자열을 F키로, `IJKL` 을 방향키로 얹었다.

## EEPROM — RAM 섬도 + 지연 플러시

QMK 는 EEPROM 을 바이트 단위로 아무 때나 읽고 쓴다. NOR 플래시는 그렇게 못 쓴다.

```
읽기   RAM 섬도에서 바로. 플래시 접근이 없다
쓰기   섬도를 고치고 그 섹터를 dirty 로 표시만
플러시 조용해지고(200ms) 나서 dirty 섹터 하나씩 소거+기록
```

**지연 플러시가 핵심이다.** VIA 로 키맵을 바꾸면 바이트 쓰기가 수백 번 연달아 온다.
매번 플래시에 쓰면 같은 섹터를 수백 번 지우게 되고(수명), 그동안 인터럽트가 막혀
USB 가 멈춘다.

**한 번에 한 섹터만 쓴다.** XIP 라 소거·기록 동안 인터럽트를 막아야 하는데(3편의
함정 ②), 16KB 를 통째로 쓰면 그 시간이 통째로 정지 구간이 된다.

```
cli# qmk info
EEPROM        : 16384 B, 소거 0 회, dirty 0x0     <- 재부팅 후. 다시 안 굽는다

cli# flash read 0xC4000 32
0x0C4000  E6 FE 00 01 ...                        <- QMK eeconfig 매직
```

## 검증 — 걱정하던 숫자

얹기 전에 "`keyboard_task()` 한 바퀴가 몇 us 인지는 얹어봐야 안다. 200us 를 넘으면
125us 폴링의 의미가 줄어든다"고 적어뒀다. 그래서 그걸 재는 명령부터 넣었다.

```
cli# qmk info
keyboard_task : last 16 us, avg 8 us, max 111 us  (n=52524)

cli# matrix info
matrix_scan : last 3 us
디바운스    : 없음 (HE 는 바운스가 없다)
```

**평균 8us.** 폴링 주기의 6% 다. 디바운스를 뺀 것도 여기 기여했다.

그리고 실제로 타이핑된다. 스캔 → 매트릭스 → 키맵 → 레이어 → HID 경로가 끝까지
동작한다.

### 그런데 스캔 주기는 느려졌다

`keyboard_task` 자체는 싼데, 슈퍼루프 한 바퀴로 보면 이야기가 다르다.

```
              스캔/초     주기      8kHz 예산(125us) 대비
QMK 전       25,796      38 us     30 %
QMK 후       16,090      62 us     49 %
```

**우리 구조에서는 스캔이 자유 구동이 아니다.** `update()` 가 `keysUpdate()` 와
`qmkUpdate()` 를 차례로 부르는 한 바퀴짜리 슈퍼루프라, QMK 가 늘어난 만큼 스캔 주기도
늘어난다. "QMK 가 느려도 판정은 제 주기로 돈다"는 것은 **아직 구조가 아니라 의도**다.

지금은 문제가 안 된다 — 62us 는 폴링 주기의 절반이고 타이핑도 정상이다. 그런데
13편에서 래피드 트리거를 넣으면 판정이 스캔 주기에 묶이므로, **12편에서 스캔을 진짜로
떼어내야 한다.** ADC 완료를 인터럽트로 받아 판정까지 거기서 끝내면 QMK 루프와 무관해진다
(7편에서 "하는 일이 플래그 하나뿐"이라 없앤 그 인터럽트를, 이번에는 판정을 실어서
되살리는 셈이다).

## 겪은 함정

### ① 부팅이 죽었다 — 캐시라인 정렬 assert 두 개

QMK 를 링크하자 보드가 USB 에 아예 안 나타났다. **QMK 를 실행하지 않아도** 그랬다.

```
[OK] flashInit()
[E_] assert : hpm_l1c_drv.c:111 l1c_dc_writeback() : address % 32 == 0
```

`l1c_dc_writeback()` 은 시작 주소가 캐시라인(32B) 경계일 것을 요구하는데, WS2812
프레임버퍼가 어긋나 있었다. **그전까지는 우연히 맞아 있었다.** QMK 의 EEPROM 섬도
16KB 가 `.bss` 에 들어가면서 버퍼가 밀린 게 방아쇠였다.

고치고 나니 다음 것이 나왔다.

```
[E_] assert : hpm_l1c_drv.c:105 l1c_dc_invalidate() : size % 32 == 0
```

`flashRead()` 가 크기를 `length + 32` 로 넘겼는데, `length` 가 32 의 배수가 아니면
크기 쪽에서 걸린다 (설정 레코드 536B → 568, 568 % 32 = 24). 이것도 원래부터 있던
버그였고, ①에 먼저 걸려 도달하지 못해 안 보였을 뿐이다.

```c
static void flashCacheInval(uint32_t xip_addr, uint32_t length)
{
  uint32_t start = HPM_L1C_CACHELINE_ALIGN_DOWN(xip_addr);
  uint32_t end   = HPM_L1C_CACHELINE_ALIGN_UP(xip_addr + length);

  l1c_dc_invalidate(start, end - start);
}
```

> **LED 와 상관없는 변경이 LED 버퍼를 깨뜨렸다.** 코드만 봐서는 못 찾는 종류다.
> USB 가 안 뜨니 로그도 볼 수 없어 **JTAG 을 다시 물려야 했다.** 8편에서 "필요할 때만
> 연결"로 정했는데, 이 국면이 그 "필요할 때"였다.

### ② assert 가 곧 벽돌이었다

찾고 보니 assert 의 뒷처리가 문제였다.

```c
__asm volatile("ebreak");
while (1) { }        /* 여기서 끝. USB 가 안 올라온다 */
```

예외 핸들러는 더 나빴다 — `ppor_sw_reset()` 이라 **리셋 → 다시 예외 → 리셋**의 무한
루프였고, 그동안 USB 열거가 끝나지 않아 겉으로는 그냥 죽은 보드였다.

둘 다 **부트로더로 넘긴다.** 그러면 USB 업데이트 채널이 떠서 다시 구우면 된다.

```c
if (flashIsReady())      /* 초기화됐고 + 소거·기록 중이 아님 */
{
  resetToBoot();
}
while (1) { }            /* 못 넘어가면 멈춘다. 재시도도 리셋도 안 한다 */
```

조건을 거는 이유는 8편에서 배운 것이다. 그때 안전망이 브릭을 만든 원인은 **아주 이른
시점에 플래시를 건드린 것**이었다. `flashIsReady()` 가 그 두 가지를 확인하고, 못
넘어가면 조용히 멈춘다 — **리셋 루프가 가장 나쁜 결말이다.**

### ③ 이식 중에는 QMK 를 CLI 로 켰다

`qmkInit()` 안에서 죽으면 USB 가 통째로 안 올라온다. 그래서 이식하는 동안에는 부팅 때
켜지 않고 `qmk start` 로만 켰다. 보드는 언제나 살아서 뜨고, 죽어도 전원만 다시 넣으면
됐다. 지금은 동작이 확인돼 자동으로 켜지만 **명령은 남겨뒀다** — 다음에 QMK 쪽을
건드리다 부팅이 막히면 다시 수동으로 돌리는 게 싸다.

      늘어난다 (38us → 62us). 래피드 트리거 전에 해야 한다
- [ ] `keyboard_task` 최악값 — 평균 8us 인데 드물게 수백 us 가 나온다. 15만 번 중
      몇 번이라 급하지 않지만 그 순간 폴링을 놓친다
