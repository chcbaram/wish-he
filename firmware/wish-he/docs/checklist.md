# 펌웨어를 고쳤으면 이것부터 — 점검 목록

키보드 펌웨어는 **틀려도 조용하다.** 컴파일도 되고 화면도 멀쩡한데 사용자 손끝에서만
글자가 하나 빠지거나 키가 눌린 채로 굳는다. 그래서 "돌아간다" 는 확인이 아니다.

아래는 이 저장소에서 실제로 당한 뒤에 생긴 목록이다. **각 항목은 한 번씩 사고를 낸
자리다.** 순서대로 하면 30분, 안 하면 반년 뒤에 원인을 못 찾는다.

---

## 0. 고치기 전에

- [ ] **증상을 재현했나** — "굳는다", "값이 이상하다" 는 원인을 안 알려준다.
      웹 도구로만 보면 펌웨어가 잘못한 것인지 앱이 잘못한 것인지 못 가린다
- [ ] **가설을 세웠으면 고치기 전에 재서 확인했나** — 짐작으로 고치면 대개 빗나간다
- [ ] **기준선을 남겼나** — 고치기 전 숫자를 적어 두지 않으면 나중에 "좋아졌나" 를
      말할 수 없다

> ★ 아니라고 나오면 **그 사실도 남긴다.** 안 되는 길을 적어 두는 것이 되는 길만큼
> 값지다. 실제로 "버그인 줄 알았는데 재보니 아니었다" 가 두 건 있었다 —
> 없는 것을 고칠 뻔했다.

## 1. 굽기 전 · 굽고 나서 — 재서 견주는 항목 (예외 없음)

**아래 표를 굽기 전에 한 번, 굽고 나서 한 번 채운다.** 하나라도 움직이면 왜 움직였는지
답할 수 있어야 한다.

### 읽는 순서가 있다

```
1) qmk reset            창을 잡는다 — 통계는 누적이다
2) 20~30초 그냥 둔다     아무도 안 치는 상태
3) qmk info             ★ 루프 한 바퀴를 여기서 읽는다
4) keys info
5) usb stat
6) keys time            ★ 마지막. 이 명령이 루프를 0.67초 멈춘다
7) keys lat run 200 8  ->  keys lat
8) python3 tools/he_test.py
```

> ★ **진단 명령이 지표를 오염시킨다.** `keys time` 은 2000 스캔을 몰아 돌리고,
> `keys noise`·`keys cal` 도 마찬가지다. 실제로 —
>
> ```
> keys time 전   루프 한 바퀴 max     186 us   초과 0
> keys time 뒤   루프 한 바퀴 max 666,271 us   초과 1
> ```
>
> 666ms 는 우리 명령이 만든 것이지 펌웨어 결함이 아니다. **순서를 지키거나, 읽고
> 나서 `qmk reset` 을 한 번 더 한다.**

### 스캔 — `keys time` (타이트 루프)

| 항목 | 지금 | 움직이면 |
|---|---|---|
| `mux+settle` | 1.33 us | 세틀링을 건드렸다 |
| `+adc 변환` | 19.16 us | ADC 클럭·샘플 창·시퀀스 길이가 바뀌었다 |
| `+filter` | 3.82 us | 데드밴드·누적 필터를 건드렸다 |
| `+track` | 12.49 us | **판정 코드가 무거워졌다** — 여기가 제일 자주 는다 |
| `keysUpdate` | **26 us** | 위 넷의 합. 30us 를 넘으면 파고든다 |
| 회/초 | 38,000 대 | |

### 스캔 — `keys info` (실제 루프 문맥)

| 항목 | 지금 | 움직이면 |
|---|---|---|
| `scan` | **26~31 us** | 타이트 루프 값보다 크면 **캐시에서 밀려나고 있다** |
| `scan max` | ~600 us | 플래시 쓰기가 낀 것. 수치보다 **횟수**를 본다 |
| `60us 초과` | 백만 회당 한 자리 | 늘면 루프에 무거운 것이 들어왔다 |
| `timeout` | **0** | 0 이 아니면 ADC 가 죽고 있다 |
| `안전 해제` | **0** | 0 이 아니면 스캔이 죽어 키를 강제로 놓았다 |
| `calibrated` | **1** | 0 이면 전 키 무반응이다 |

### 루프·태스크 — `qmk info`

| 항목 | 지금 | 움직이면 |
|---|---|---|
| `keyboard_task avg` | **2 us** | **최대치 하나로는 아무것도 못 정한다. 평균이 늘면 진짜 회귀다** |
| `keyboard_task max` | 30 us 대 | 키를 처리한 바퀴가 여기 남는다 |
| `125us 초과` | **0** | 폴링을 놓친 횟수 |
| `루프 한 바퀴 max` | **200 us 대** | task 시간엔 **안 남는 정지**가 여기 남는다 |
| `20ms 초과` | **0** | 플래시 쓰기(30ms)면 정상, 그 밖이면 파고든다 |
| `rgb_task avg / max` | 1 / 4 us | 효과에 따라 5 / 38 us 까지. 지연에는 안 닿는다 |
| 연타 `박자당` | **2.00** | 2.00 이 아니면 리포트가 사라지고 있다 |
| `EEPROM 소거` | 창 안에서 0~2 | 갑자기 늘면 어딘가 계속 쓰고 있다 |

### 반응 속도 — `keys lat run 200 8` → `keys lat`

| 항목 | 지금 (평균) | 움직이면 |
|---|---|---|
| ① 스캔 + 누적 | 51 us | 누적 탭 수·스캔 주기가 바뀌었다 |
| 루프 대기 | 21 us | 스캔 한 바퀴가 길어졌다 |
| ② 키변환 | 2 us | |
| ③ 키코드까지 | 4 us | **10us 를 넘으면 코드가 캐시 밖으로 나갔다** |
| ③ 훅 + 리포트 | 5 us | 〃 |
| ④ 폴링 → ACK | 65 us | 8kHz 의 절반. **여기는 안 움직이는 게 정상** |
| **판정 → ACK** | **97 us** | 견줄 때 쓰는 눈금 |
| 흔들림(σ) | 35 us | 폴링이 만드는 폭. 커지면 어딘가 불규칙해졌다 |
| 주입 → ACK | 148 us | ① 포함 |

### 판정 건전성 — `keys info`

| 항목 | 지금 | 움직이면 |
|---|---|---|
| `latch` | **0** | 기준값이 글리치로 끌려 올라갔다 — **스턱 키의 씨앗** |
| `drift 위 / 아래` | 서로 비슷 | 한쪽만 크면 기준값이 한 방향으로 흐른다 |
| `ISR 미루기` | 설정 명령 뒤 늘어야 정상 | **안 늘면 ISR 이 표를 직접 만들고 있다** |

### USB — `usb stat`

| 항목 | 지금 | 움직이면 |
|---|---|---|
| `KBD lost` / `EXK lost` | **0** | 전송 완료를 놓쳐 되살린 횟수 |
| `EXK sent` | 타건하면 는다 | 안 늘면 리포트가 안 나가고 있다 |
| `KBD sent` | 부트 화면에서만 는다 | |

### 메모리 — 빌드 로그

| 항목 | 지금 | 움직이면 |
|---|---|---|
| `FLASH` | 81 KB / 384 KB (21%) | |
| **`ILM`** | **87 KB / 128 KB (66%)** | **넘치면 링커가 잡지만 뺄 것을 정해 두지 않았다** |
| `DLM` | 105 KB / 130 KB (80%) | 여유가 적다 |
| `AHB_SRAM` | 12 KB / 32 KB (38%) | |

> ★ **"같은 조건에서" 잰다는 뜻이지 "시간순으로" 가 아니다.** 굽기 전 값을 8분 돌던
> 장치에서 얻고 굽고 난 값을 부팅 100초짜리에서 얻으면 엉뚱한 결론이 나온다.
> 의심스러우면 **이전 펌웨어를 다시 구워 연달아 잰다.**
>
> ★ **굽고 난 직후 한 번은 못 믿는다.** 두 번 겪었다 — 같은 펌웨어로 두 번 재니
> 지표가 20배 흔들렸다. 세 번 재서 뭉치는 값을 쓴다.
>
> ★ **평균은 뭉갠다.** 갈라지는 것은 최소값에서 먼저 보인다 — 캐시 문제를 평균으로만
> 보고 "아니다" 로 접었다가 최소값에서 갈렸다.

## 2. 그리고 동작 — 자동 점검

```
python3 tools/he_test.py          전 항목
python3 tools/he_test.py <무리>   빠른 확인
```

- [ ] **통과 수가 기준과 같은가** (지금 25 · 알려진 문제 1)
- [ ] **고친 것의 재현 절차를 시험에 더했나** — 손으로 확인하고 잊으면 반년 뒤에
      조용히 되살아난다
- [ ] **아직 안 고친 것은 `xfail` 로 뒀나** — **늘 빨간 검사는 아무도 안 본다.**
      알려진 문제는 "알려진 대로 재현됨" 이 통과다

> ★ **성능 비교는 "느려졌나" 만 본다.** 오입력과 키씹힘은 느려지지 않아도 난다.
> 실제로 기준값이 얕은 설정에서 키를 저절로 떼던 버그가 태스크 시간에는 한 글자도
> 안 나타났다.

## 3. 반응 속도

```
keys inject live on
keys lat run 200 8       장치가 스스로 두드린다
keys lat                 구간별 최소·평균·최대
keys lat dump            표본 하나씩
```

- [ ] **1절의 지연 표를 채웠나**
- [ ] **어느 눈금으로 말하는지 적었나** — "판정부터" 와 "값이 바뀐 순간부터" 는
      두 배 가까이 다르다
- [ ] **간격을 무작위로 뒀나** — 고정 간격은 폴링 위상과 묶여 **실제보다 좁게 나온다**

> ★ **재는 도구가 측정 대상 안에 있으면 안 된다.** CLI 로 한 번씩 눌러 재면 CLI
> 자신이 측정 창에 들어가 값이 두 배가 된다.

## 4. 되돌리기 — 가장 자주 빠뜨리는 것

시험은 설정만 바꾸는 것이 아니다. **누적 카운터 · 기준값 · 리포트 상태**도 바꾼다.

- [ ] **눌린 키가 없나** — `qmk held` 로 **호스트가 아는 것**을 본다
- [ ] **주입이 꺼졌나** — `keys inject`
- [ ] **설정·프로파일이 시험 전 값인가** — `keys prof`, `keys cfg`
- [ ] **기준값이 실제 값에 붙어 있나** — 갇힌 기준값은 리포트에 안 나타난다
- [ ] **시험이 만든 카운터를 지웠나** — 다음 실행이 그걸 보고 오판한다
- [ ] **키코드를 되돌렸나** — 시험용으로 바꿔 놓았으면

> ★ **순서가 있다.** 설정을 먼저 되돌리고 주입을 나중에 끈다. 반대로 하면 그 사이
> 리포트가 살아나 **스턱 키가 호스트로 샌다.** 실제로 흘렸다.
>
> ★ 하루에 같은 부류를 넷 빠뜨린 적이 있다 — 프로파일 · 스턱 키 · 기준값 · 카운터.
> **시험을 새로 쓸 때 "무엇을 바꾸는지" 를 먼저 적고 하나하나에 되돌리기를 짝지운다.**

---

## 5. 재는 도구를 먼저 의심한다

**세 번 거짓말했다.** 전부 원인이 같았다 — **지우는 자리가 두 곳**이었다.

- [ ] **지우는 함수가 하나인가** — 다른 곳은 그것을 부르기만 해야 한다
- [ ] **새 카운터를 지우는 목록에 넣었나**
- [ ] **값이 안 변하면 의심한다** — 두 조건이 소수점까지 같으면 안 지워진 것이다
- [ ] **값이 너무 크면 의심한다** — 창을 안 잡았을 수 있다

> ★ 하마터면 "왕복이 루프를 669ms 멎게 한다" 고 적을 뻔했다. 실제로는 굽고 부팅하며
> 생긴 값이 안 지워지고 있었을 뿐이다.

---

## 6. 호스트가 보는 것을 본다

**매트릭스와 호스트는 다른 것을 본다.** 둘이 갈리는 자리가 버그다.

- [ ] **`keys show`(매트릭스) 와 `qmk held`(호스트) 가 같은가**
- [ ] **프로파일을 바꿔도 눌린 키가 안 남나**
- [ ] **기능을 껐다 켜도 눌린 키가 살아나나**

> ★ 프로파일 전환 스턱 · SOCD 억눌린 키 · 부트 프로토콜 — 셋 다 `qmk held` 없이는
> 못 잡았다. 매트릭스는 내내 정상으로 보였다.

---

## 7. 손으로만 되는 것

자동 시험이 못 하는 자리다. USB 를 만졌으면 반드시 한다.

- [ ] **뽑았다 꽂아 본다** — 재열거 뒤 상태
- [ ] **호스트를 재웠다 깨워 본다** — 키로 깨워지나, 깨어난 뒤 키 상태가 맞나
- [ ] **부팅 화면(BIOS)에서 키가 먹나** — 그 화면은 다른 방식을 쓴다
- [ ] **설정 도구를 켜 둔 채 타자해 본다** — 실사용에서 가장 흔한 조합이다

---

## 8. 시험 키는 이름이 아니라 번호로 고른다

- [ ] **호스트 OS 가 그 키를 특별 취급하지 않나**

> ★ **"무해" 는 호스트가 정한다.** `F13~F15` 가 macOS 에서 화면 밝기·스크린샷이라
> 시험이 수십 번 쏘아 화면이 캄캄해졌다. 그걸 적어 두고도 **`Scroll Lock`(usage
> `0x47`)이 같은 F14** 인 줄 몰라 또 당했다.
>
> **무해한 키 목록은 이름이 아니라 HID usage 번호로 적는다.** 지금 쓰는 것은
> `F23`(`0x72`) · `F24`(`0x73`).

---

## 9. 손대면 안 되는 것

- [ ] **플래시 `0x080000 ~ 0x0C0000` 을 안 건드렸나** — 기존 데이터 영역이다.
      `flashWrite()`/`flashErase()` 에 주소 검사가 없으니 규율로 지킨다
- [ ] **부트로더 영역을 안 건드렸나** — 바꿀 수 없다
- [ ] **ILM 이 넘치지 않았나** — 빌드 로그의 ILM 줄 (지금 66%)
- [ ] **`.ld` 를 만졌으면 `build/*.elf` 를 지우고 다시 빌드했나** — 안 그러면
      재링크가 안 걸린다

---

## 10. 배포한다면

- [ ] **버전이 한 곳에서 나오나** — `src/hw/hw_def.h` 하나가 출처다
- [ ] **장치가 보고하는 값과 배포 목록의 값이 같나** — 실제로 구워서 확인한다
- [ ] **사본을 두 곳에 두지 않았나** — 두면 반드시 갈라진다
- [ ] **릴리즈 노트가 화면에 다 보이나** — 안 보이는 줄은 없는 줄이다

> ★ 버전이 두 번 되돌려져 **장치가 보고하는 버전과 배포된 코드가 다른** 상태로
> 한동안 있었다. 그러면 "어느 빌드의 증상인지" 를 못 가린다.
>
> ★ 배포본을 두 곳에 두었다가 실제로 갈라진 적이 있다 (한쪽 R38 / 다른 쪽 R1).

## 한 줄 요약

| | |
|---|---|
| 짐작하지 말고 **잰다** | 고치기 전에 한 번, 고치고 나서 한 번 |
| **같은 조건**에서 잰다 | 시간순이 아니다. 필요하면 옛 펌웨어를 다시 굽는다 |
| 재현 절차를 **코드로** 굳힌다 | 손으로 확인하고 잊으면 되살아난다 |
| 바꾼 것은 **되돌린다** | 순서가 있다. 무엇을 바꾸는지 먼저 적는다 |
| **재는 도구를 먼저 의심한다** | 도구가 거짓말하면 그 뒤는 전부 헛일이다 |
| **호스트가 보는 것**을 본다 | 매트릭스는 멀쩡한데 호스트만 어긋난 버그가 셋이었다 |
| 틀렸으면 **틀렸다고 남긴다** | 안 되는 길이 되는 길만큼 값지다 |
